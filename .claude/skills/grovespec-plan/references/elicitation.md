# elicitation — drawing out a want the user can't yet state

> explore (`explore.md`) reaches for this when forward questions stall — when the user "doesn't really know what they want." Distilled from BMAD's brainstorming *facilitation* (the how, not its session-theater). Reach for ONE move at a time; never run the list — pick the move by the **facet you still need to cover** (`explore.md`), not down this menu. Each move is a way to draw out a blank facet, not an end in itself.

## Facilitation (how to run any move)
- **Facilitate, don't generate for them.** Your job is to make *them* produce the idea — you prompt, prime, build. Generate *for* them only if they're stuck and ask.
- **Multi by default for wants.** "What do you want / why does it matter / who for" are usually *several at once* — default to **multi-select** + a real free-form escape. Use single-select **only** for an explicit "which *one* matters most." Forcing single on a want quietly **drops real motives and you won't see what you lost**. Got several back? *Then* ask "which is primary?" — focus without losing the rest.
- **Design the question before you ask it.** One beat, every time, never reflexive: is this *which apply* (multi) or *which is most* (single)? Are the options genuinely divergent (not bland coverage)? Is the escape real? Get this wrong and it silently corrupts everything downstream — so it is the *most* deliberate part, not the most improvised.
- **Recommend, and always leave a way out.** Putting a decision to the user (tech stack, scope, approach…)? Use the **AskUserQuestion tool** for discrete options; **mark your recommended option** — append `(추천)`/`(Recommended)`, put it first, with a one-line why; and **always** keep a free-form answer open (the tool's built-in *Other*, or an explicit free-form choice in an inline list). Never force a closed pick.
- **Prime, then hand it back.** Give ONE concrete example to start the pump, then return it: "…that's one — what else comes to mind?" Spark, don't enumerate.
- **One move, and stay with it.** Don't mix moves in a breath. Pull one thread until it's dry or they want to switch — depth before jumping.
- **Ask → wait → build.** Turn-taking, not a monologue. "Yes, and…" their answer — extend it, don't replace it.
- **Diverge before you judge.** While generating, welcome the weird and the many; defer critique. Narrowing is a *separate, later* pass — don't kill an idea as it's born.
- **Follow the heat.** If a thread flags, go deeper ("tell me more") or switch the move. Chase what has energy.
- **Then converge to the brief.** When wants are surfacing, group them and land the lean brief (Direction · Scope · Risks). That — not a brainstorming report — is explore's only output.

## Moves (reach for one when stuck)
- **Why-ladder** — ask "why" *past* the first answer, one at a time, until the real motive shows (to relax? to win? to improve? to show off?). The motive reshapes the product more than any feature.
- **Extremes** — strip or stretch to provoke: "only $10 and an hour?" · "in 2035?" · "if it had to fit one screen?" Offer one; let them react.
- **Flip** — pose the reverse: "the opposite app?" · "if there were *no* ranking, what's left worth keeping?"
- **Analogy** — "what if this were a [gym membership / a diary / a roguelike]?" Give one; ask them for the next.
- **Their eyes** — name ONE concrete user ("someone solving 5 minutes on the commute"); ask what *they'd* want here that hasn't been said yet.

## Not from BMAD (deliberately dropped)
