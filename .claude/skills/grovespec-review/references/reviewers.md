# reviewers — the cold-review engine (shared by verify + review)

> `grovespec-verify` (spec) and `grovespec-review` (code) both load this to run a cycle. The SKILLs hold the *rules* (levels, phase ends); this holds the *mechanics + the bar + the categories + the lenses*, so every node's review comes out the same shape. The two callers differ in lens set, read-scope, and (verify) the checklist.
> A cycle is **two phases — find → fix** (§The cycle): finders sweep a frozen target in waves, every wave's finds are **classified by category at that wave's boundary** (§Categories — fixed handling, no severity to argue), find closes when **`find_streak` consecutive waves confirm no new must-fix finding**, and the fix phase then closes the confirmed items **one at a time** (plan → plan review → apply → confirm). Finding is repeated generously; fixing is bounded strictly — that split is the whole design.
> Reviewers write findings in the project's language (`config.language`).

## THE BAR — read first. *Sufficient*, not exhaustive.
You review for a **competent implementer/consumer** who will research, make reasonable decisions, follow the project's conventions, and ask only when *truly* stuck. So:

- A finding is a real flaw **only if that implementer would be blocked or build the wrong thing.** "I can imagine an unhandled edge / an unspecified detail" is **not** a flaw if a competent implementer would reasonably handle or decide it.
- Yes, go in adversarially ("try to break it") — **but a kept finding must name *who is blocked, and on what decision*.** *What is merely unstated* is not enough.
- You are checking for **sufficient** context, not exhaustive detail. Perfect specs don't exist; "enough to build the right thing without a mess" is the target. (This is the single rule that stops a review from churning for rounds.)

## SCOPE — what a spec may and may not contain
- A spec states the **contract** — what it *takes · gives · guarantees* — and the line is **what a consumer can observe**: the public names it calls, the shape of what crosses the boundary, error behavior, ordering, and any atomicity/concurrency promise a consumer can see and rely on. It does **not** state the unobservable inside — algorithms, private structure, a store's internal schema, how a transaction is implemented. Those belong to the node's own *implementation* or to a *child*. The same topic falls on either side by observability: "the file is valid JSON after every add" is contract; "writes go through a temp-file rename" is mechanism.
- A **skeleton**'s spec states only: its child pieces (by role), the boundaries between them, and the **cross-cutting invariants** all children must respect — and **defers the rest to named children**.
- **An unspecified mechanism, an edge a child owns, or an explicitly deferred detail is NOT a gap — do not raise it.** A spec line like `[→ child/deferred: …]` is *correct delegation*, not a hole — **when it points down** (own child/implement). One naming another existing node is the parked obligation the wait ledger (`grovespec wait`) replaces — **raise it** (repair: a wait or a revise; `validate` flags it too). Demanding such detail is over-reach; classification will strike it, so don't raise it in the first place.

## Which lens set · scale · read-scope · do-not-raise
- **verify-tree** (`target_type: tree`) — one target, **two questions**; the tree's state picks (`grovespec next` names which gate is armed):
  - **decomposition** (sketch nodes exist) — the **decomposition lenses** + **D1–D5**: is this the right decomposition and source→node assignment? Runs at plan #0 (and after a structural/source-assignment `plan`/`revise`), before the per-node build. Read: the whole sketch tree (`tree.md` + every sketch Task — *cheap, one-liners plus frontmatter `refs`*) + the brief + the ref intent records (current ones via `ref/index.md`).
  - **fidelity** (a pristine mapped/brownfield tree) — the **fidelity lenses** + **F1–F4**: is the survey an accurate photograph of the code? Runs once per adoption, right after a brownfield init. Read: the tree + every mapped Task (id·name·Overview·Contract) + **the code itself** + the backlogs (findings/restructuring.md). **Criteria = the code, not any intent doc.**
  - Count from `config.yaml` `verify.scale`. On a post-`revise` re-verify of a *built* tree, read each Task's **id·name·Overview + `refs` only** (not full contracts), keeping the same economy while still exposing the source map D1 must check.
- **verify** (`target_type: spec`) — the **spec lenses** + the **verify checklist** (below); count from `config.yaml` `verify.scale`. Read: the draft Task + the parent's Contract + **the original ref intent clauses assigned by this Task's `refs`** + the relevant `conventions.md`. The caller runs `grovespec source TASK-N` and hands every reviewer that round's entire canonical packet; each reviewer opens the packet's original coordinates itself, and a caller-written summary is not criteria. (Not every sibling — only what the contract references.)
- **review** (`target_type: result`) — the **code lenses**; count from `config.yaml` `review.scale`. Read **ONLY this node's changed files (its diff) + its AC·Contract + the test results** — never the wider codebase. (This bound keeps review's cost flat as the project grows.)
- **do-not-raise**: the caller passes the state file's `adjudications` **itemized — each entry's claim (one line) + verdict + recorded reason** — plus the shape-level entries the two-strike rule wrote (out-of-scope boundaries + accepted gaps — e.g. "internal schemas · transaction mechanics · timezone/month = child/impl scope") **and every scope the user excluded** (`excluded-by-user`). **Do not re-raise a listed claim, or a new instance of a listed shape** — already decided. A user-excluded scope in particular is never revived because this cycle touched related code; only new evidence of a *current* must-fix problem reclassifies it, and that goes to the human, not past them. These are *verdict records, not clean-claims*: each settles one claim and says nothing about the area around it, which stays as open as anywhere else. (Why itemized, not condensed: METHODOLOGY §6.)
- **Model (optional)**: each reviewer's model = `config[verify|review].models[<lens>]` if set, else `models.default`, else **inherit the session model** (the portable default). A defender spawned for a contested classification uses `models.default` (same fallback). Model ids are host-specific; if the config names one the host cannot select for a subagent, stop and name it instead of silently inheriting a different model.

## Spawning
- **Count** from `config.yaml` (`verify.scale[level].reviewers` / `review.scale[level].reviewers`) — the SSoT; don't hardcode here.
- **Which lenses** spawn at that count: the **check-assignment table** below (verify/verify-tree), or the fixed order (review/code). *Which checks each carries* then follows from that section's coverage invariant.
- **Spawn as parallel subagents** with the host's subagent tool — one batch, concurrent. Each starts from an **empty context**; that's what makes them cold. The host must provide at least the configured reviewer count as concurrent child slots; if it cannot, stop and name that capacity gap instead of serializing the wave or silently shrinking it — but first tell a real gap from the skill's own residue (next two bullets). (Main session only — see each skill's invocation contract.)
- **Talk to a reviewer once: the spawn prompt. Then take its result.** A reviewer is spawned cold and reports back; after the spawn, send it **no queue-only message** (a host tool that enqueues text into a child's inbox without starting a turn on it). A prompt that turned out short is **not** topped up by message — spawn a fresh reviewer with the full prompt. If a follow-up instruction is truly needed, use only the host's **turn-starting** follow-up tool (one that starts a turn on the child, so the child actually reads and answers).
- **"Over the limit" has two cases — read the host's agent list before calling it a gap.** (1) **A real capacity gap**: the host's concurrent-child limit itself is below the configured reviewer count → stop and name it, as above. (2) **Own residue**: the spawn was refused, yet agents this skill spawned in an *earlier* wave still appear in the host's agent list (done, but not reaped) → **not** a capacity gap. Give each resident agent one short **closing turn** through the turn-starting follow-up tool — "process any pending messages and finish; no further work" — then retry the wave spawn **exactly once**. If the retry is refused too, now it is a capacity gap: stop and name it. A resident agent is **never reused as a new reviewer** (cold means a fresh context, always); the closing turn only empties the slot. One retry, no loop.
- **Wave hygiene — check the list before each wave.** Before spawning a new wave, read the host's agent list (where the host offers one): every agent of the previous wave must be gone. Any still listed gets the closing turn above *first*, then the wave spawns. A host without an agent-list tool skips this check — the residue case above still applies if its spawn is refused.
- For `skip`: spawn none; the caller self-checks against the checklist.
- Each reviewer's prompt = **common preamble** (incl. THE BAR + SCOPE + the do-not-raise list) + the **found list** + the **strategies already run** (§Search strategies) + its **role lens** + the **findings format**. Never give them how the target was built, the author's reasoning, or any **clean-claim** ("area X is verified clean") — other reviewers' *output* (finds · ran strategies) travels; the author's narrative and innocence claims never do.
- **Spec source hand-off is one exact packet, never excerpts or a summary.** The main session generates it with `grovespec source TASK-N`; the runtime derives coordinates from the Task's structured `refs` (or the bounded legacy rule), validates them through `ref/index.md`, and emits the packet. Paste it once in the current find brief and give that whole fence to every spec reviewer. Reviewers open its original coordinates and may return **only disposition fields**: the C1 owner fills `c1`/`c1_case`/`c1_basis`, the C3 owner fills `c3`/`c3_basis`; nobody changes ids, source text, digests, scope, protocol, or schema. If an original or its location cannot be opened, report `missing` plus a real finding id; it cannot be reconstructed from the Task being checked.
- **Don't end the turn while anything this step started is still running** — a wave out, a test or a measurement in the background. Wait for it to return, or stop it and see its processes gone, then end the turn.
- **An experiment follows `FORMATS.md` "The person's machine"** — every reviewer's, like every run a step makes: a mutation in a temp copy of your own (one per reviewer, named for it), a time and a memory limit with a means, stop or delete only by the id you started, clean up before you report, and the person's machine itself only with their OK. A lens that reports an observation the committed source cannot produce has almost certainly read a neighbour's mutation: re-measure in a copy before writing it down.

## The cycle — find → fix
One gate = one cycle of two phases. **Find repeats until it stops producing; fix closes what find confirmed, one item at a time, and never re-opens the sweep.** The state file's counters (`no_new_streak` · `plan_clear_streak`) are what a resumed session continues from — a new session never restarts a phase the record shows in progress.

**1 · find — waves over a frozen target, until `find_streak` consecutive waves confirm nothing new.** Nothing is fixed while finding, so every wave reads the same bytes. Spawn a wave (the level's lens count), **classify its finds at the wave boundary** (§Classification — every find gets its category *now*, never after all waves), then count — **the counter moves once per completed wave, on exactly one question: did this wave confirm a NEW must-fix finding?**
- **Yes** — a new `family` in a must-fix category, **or** an already-listed record item promoted to must-fix by new evidence of a *current* problem (§Classification's UPGRADE — same family, first must-fix confirmation) → `no_new_streak: 0`.
- **No, and nothing is unresolved** → `no_new_streak + 1` — whatever else the wave found. Re-finds of listed items, record-only finds (improvement · harmless-bug), and struck non-findings **do not make a wave loud**: a wave of nothing but improvements still advances the streak.
- **The wave failed, was cut short, or left a candidate's classification `pending`** → the counter holds where it is; the wave is not "quiet" until the candidate is settled (a targeted measurement, or a cold defender ruling).
`no_new_streak` reaching **`find_streak` (N, config)** closes find and confirms `open_issues` as the fix list. For **spec/tree** targets, find additionally requires the checklist fully *worked* (every evidence-capable check shown, or FAILed into a finding — C6 needs only its read-through) — the checklist is evidence the pass must still show; the streak is what says the hunting is done. Each wave's payload adds three lists to the preamble:
- **the found list** — every finding raised so far (id · where · one line): *do not re-report these, or new instances of their shape; find what is NOT on this list.*
- **the adjudicated list** — every claim already settled (`adjudications`, surviving from prior cycles): claim + verdict + reason. *Do not re-report these or new instances of their shape either — but the area around a settled claim stays open; a verdict record settles one claim, never an area.*
- **the strategies already run** (§Search strategies): *arm this wave differently.*
**Never hand a finder a clean-claim** — a ran strategy and an earlier wave's silence tell the next finder what not to repeat, **never that an area is safe** (a prior wave's "found nothing" is not evidence and never travels as a conclusion).

**2 · fix — one item at a time: plan → plan review → apply → confirm.** Never batch: applying every fix and then reviewing the pile is how a wrong fix hides behind a right one. The caller's fix step (`grovespec-fix` for code; verify's own fix step for a spec) works the confirmed list item by item — the full per-item protocol lives in that skill; what the engine fixes here is the shape. **`plan_streak` (M) applies to result (code) cycles only — a deliberate bound, not an omission**: a spec fix's plan is its stated edit (a sentence or two), checked against the same four questions by the caller and confirmed cold per item; spending M cold laps on a document edit buys nothing the item confirmation doesn't already give.
- **plan first, apply after.** The item's fix plan (condition → cause · the change · its direct blast radius · how closure will be measured) is **cold-reviewed before any code moves**, and applied only after **`plan_streak` (M, config) consecutive clean plan reviews** — a blocking flaw in the plan revises the plan and resets `plan_clear_streak` to 0. A plan review asks four questions and no more: does this plan remove the *current* problem's cause? does it mask the shown repro while leaving the same cause? does it break an existing requirement or the ordinary use path? does it add machinery the current problem doesn't need? **"It could break under a future change" is not a plan-blocking answer** — the plan owes the current problem, current requirements, and ordinary use, nothing further.
- **confirm the item, not the target.** After apply, ONE cold confirmation scoped to **this item's own diff + the item it claims closed + the in-node use-sites of what it changed**: did the fix close it (re-run the finding's own measurement)? does the same cause still reach a current wrong result by another path? did the fix directly regress what it touched? **A failed confirmation returns to the item's plan** — first name *which* it was: a mis-diagnosed cause, a symptom-only patch, or an implementation slip — never a patch stacked on the spot.
- **a stacked mutant is closure evidence for nothing** — a mutation carrying several components dies by its first caught one, so its death shows that component alone. Plant components separately; count a component closed only when its own solo mutant dies.
The confirmation spawns **the lens that raised the item** (when in doubt, correctness for code · coherence for spec/tree), cold as ever. **A confirmation finding may be dropped only by a cold defender** — the caller, often the fix's own author, never self-drops what a confirmation raised (self-KEEP is always allowed). A confirmation reviewer who stumbles onto a real problem **outside its scope** still reports it — classify it like any find: a new must-fix becomes its **own** `open_issues` item, worked after the current one (never silently widening the current item, and never reopening the find phase). A confirmation reports must-fix candidates only. **A revert reopens every item that fix had closed** — restore them to `open_issues` on the spot (the no-re-report rule never applies to a reopened item). **Every item closed ends the cycle** — no closing re-sweep, no batch confirmation: each item's own cold confirmation already was the check.
This is narrower than re-sweeping after every fix **by design**: a defect find missed in *unedited* code stays unseen until the next cycle. That residual window is the accepted price of a terminating cycle — the recall duty lives in find's streak of differently-armed waves, not in fix.

`max_rounds` budgets **find waves** only — `round` still numbers every spawned pass, but plan reviews and confirmations don't spend the budget. Past `max_rounds` find waves → escalate. **A fix that won't converge escalates alone**: when the current item's confirmation fails twice in a row, stop and put that one item to the person — never a question about raising the budget. Reaching a cap is never a pass, and the counters (streaks = the success conditions, the budgets) never substitute for each other.

## Search strategies — arming the waves differently
A wave that repeats the last wave's method measures luck, not the target: **recall is bought by strategy diversity**. The caller assigns each wave a strategy earlier waves didn't run and records it in `strategies[]` — that record is what makes "N consecutive quiet waves" mean *differently-armed looks found nothing new*, not *the same look shrugged N times*. The seeds below are **aids, not obligations**: no node owes a mutation campaign, an exhaustive combination walk, or a reference model by default — reach for a seed when the diff's risk calls for it, and stop when the streak closes find.

Seeds — code (`result`):
- `clause-walk` — every Contract/AC clause held against the diff, one by one.
- `single-axis-sweep` — mutate/weaken/delete along one axis at a time; do the tests bite? (What a surviving mutation *means* is bounded — §Categories: a mutation-only hole is an improvement, not a must-fix.)
- `axis-product` — mutations that survive only at the *intersection* of two separately-pinned axes. Use it **when a confirmed problem or a contract clause names the interaction** — never as a default combinatorial walk.
- `reference-model-fuzz` — implement the contract independently; randomized differential runs against it. Expensive — for genuinely calculation-heavy contracts.
- `boundary-probe` — pathological/boundary inputs at the public surface (empty · huge · unicode · path shapes · limits) — held to the product's stated reality (§Categories: input outside it is not a must-fix).
- `harness-audit` — the suite itself: hollow asserts, fixtures that pin a contract-named axis to one value, isolation leaks.

Seeds — spec/tree: **the checklist doubles as the strategy list** (C1–C6 / D1–D5 / F1–F4) — each check is an instrument with one owner, waves work what is still PARTIAL, and the check-assignment invariant (every check exactly one cold owner) holds **across the find phase**, not per wave: wave 2 owns what wave 1 left unshown; it does not re-earn what is already shown.

## Categories — what kind of problem is it, and the handling is fixed (name the victim)
Findings are not graded on a severity ladder — they are **classified by the kind of problem**, and each category's handling is fixed. "How serious does this look?" was a judgment an agent re-made every round, and it drifted; "which of these seven is it?" is a definition. **Five categories are must-fix** (they go to `open_issues` and block the gate); **two are record-only** (they go to `followups` and never block, never queue).

| category | it is one when | handling |
|---|---|---|
| `crash` | in a supported environment, the program cannot run, a required test cannot proceed, or it terminates abnormally | must-fix |
| `requirement-unmet` | a behavior/result the **user's requirement** states is missing or implemented differently — cite the requirement (`requirement:` names the ref clause / Contract·AC line) | must-fix |
| `normal-use-bug` | an ordinary sequence of actions and inputs produces a wrong result, wrong state, or wrong data | must-fix |
| `easy-abuse` | a simple, realistic action bypasses a feature's limits, permissions, or conditions of use | must-fix |
| `security-hole` | the **current implementation** has a concrete, realistic exploit path — auth bypass, sensitive-data exposure — that cannot be accepted | must-fix |
| `improvement` | the feature holds, but structure · performance · tests · readability could be better | **record only** |
| `harmless-bug` | something is genuinely wrong, but it has no real effect on task completion, results, data, or security | **record only** |

Every kept finding also needs lane fields:
- `kind: defect|contract-gap|concern`
- `family: <the underlying hole, not the path that showed it>`

Lane rule — **`kind` names where the flaw lives; `category` alone decides whether it blocks**:
- `defect` = the current review target itself is wrong. A must-fix defect blocks in `open_issues`; a defect in a record category — a real but harmless slip in current code (a label typo) — is recorded in `followups` like any record item.
- `contract-gap` = a real issue, but it belongs in later revise/verify work rather than this code gate — the one way a must-fix category may sit in `followups` (a `contract-gap` in a record category is just a record item).
- **A must-fix only a contract change closes** — another node's, done or not, or this node's own Contract — is a `contract-gap` here: this gate blocks only on what the current cycle can fix, and **the caller asks *now or next milestone* on the spot** (`FORMATS.md` "A defect only a contract change closes"); *now* reopens that node through `grovespec-revise` once this step ends, and the item leaves `followups`.
- `concern` = a note or suspicion; never a blocker (record categories only).
- If the flaw is in the current cycle's diff or in the text under review right now, it is `defect` even if the eventual repair also needs a spec change.
- A review file may name a `family` only once across `open_issues` + `followups`; the same hole re-shown through a second path is one finding, not two.

One finding per entry:
```
- [<category>] <C# / where: §section · file:line> — <what exactly is wrong: expected vs actual, and who meets it first>
  condition: <the ordinary situation/steps that produce it — for abuse/security, the realistic path>
  impact: <what reaches the user — wrong result, lost data, blocked work, bypassed limit>
  <requirement: <the ref clause / Contract·AC line> — required for requirement-unmet>
```
A finding with no condition, no impact, or (for `requirement-unmet`) no cited requirement is **not classifiable** — the caller cannot record it, so it dies at aggregation. State them.

**Classification boundaries — the lines that keep the categories from re-growing a severity ladder:**
- **The requirement has an owner — the user.** `requirement-unmet` cites the user's requirement or the contract derived from it. A duty a reviewer or an earlier round invented ("every combination must be tested" · "every branch must be measured") is **not** a requirement and never becomes one by repetition — a verification obligation the spec's own text does not carry is an `improvement` at most.
- **The current implementation vs. future changes.** A problem that only exists after someone *deliberately breaks the code* — a surviving mutation, a "what if a future edit removes this check" — is not a defect of the current product. **A test gap shown by mutation alone is an `improvement`**; it becomes must-fix only when it currently hides a real wrongness (then *that* wrongness is the finding, in its own category). A security `condition`, by contrast, does not require realized damage — a concrete exploit path in today's code suffices; what it may not be is a path that exists only in a hypothetical future version.
- **Reproduced ≠ must fix.** Reproduction, several reviewers agreeing, and repeated rediscovery establish that a problem is *real* — they never move it between categories. A reproduced cosmetic slip is a `harmless-bug`; classification comes from the definition table, not from how much evidence piled up.
- **Ordinary vs. abnormal is judged against the product's stated reality** (brief · Contract · conventions): for an internet-facing service a hostile caller is ordinary; for a single-user local tool, self-sabotage is not. Input or scale outside the stated reality does not make a must-fix.
- **Same cause, one item.** Several symptoms of one cause merge into one finding (one `family`); different causes stay separate even inside one feature.
- **Unclear stays unclear.** A candidate whose category cannot be settled from its evidence is held as `pending` — measured further or ruled by a cold defender. It is never rounded down to `improvement` to let a wave count as quiet, and never rounded up to must-fix on possibility alone; an unresolved candidate blocks the find streak from advancing (§The cycle).

**For a spec/tree target the categories read at spec altitude**: the run-time categories (crash · normal-use · abuse · security) describe running code, which does not exist yet — **never demand execution evidence from an unbuilt node**. A spec finding is must-fix as `requirement-unmet`: a user requirement omitted, contradicted, silently narrowed, or a decision this node owns left so open that a named builder cannot proceed (the checklist C1–C6 / D1–D5 / F1–F4 are the instruments that show it). Wording, structure, and readability findings are `improvement` (C6's FAIL — a shown misreading — is the exception: a misread contract builds the wrong thing, so it rides as `requirement-unmet`).

**Name the victim** — the rule that kills non-findings. Every finding names *who meets the failure first* and *what exactly goes wrong*: the next builder (spec), whoever runs the code, the maintainer who reads it. "This seems unclear" / "what about X edge?" with no victim is a **non-finding** — drop it at the wave boundary. If a lens finds nothing, it returns `none` with a one-line note on what it checked. The reviewer's final message **is** the result — no greeting.

Examples — spec:
- ✅ `- [requirement-unmet] C2 §Contract — the *stats* child can't tell from this contract whether month totals are per-calendar-month or rolling-30d; it owns that and would guess.` *(named victim + decision)*
- ✅ `- [requirement-unmet] C1 — the rules use *hire-date* (leave→accrual) and *team·rank* (approval→routing), but no child or foundation owns an employee master that creates them → prerequisite gap the source doc assumed.` *(noun the rules lean on, no owner)*
- ✅ `- [requirement-unmet] D2 — no node owns *system settings*: core-time hours·rate multipliers·thresholds are regulation values that must be admin-editable, not hardcoded; a rules-driven system needs a settings store the source doc never mentions.` *(infra the domain doc omits)*
- ✅ `- [requirement-unmet] D5 — "approval" is one flat sketch, but routing is org-chart-derived + rank-constrained (the approver must outrank the requester) → it hides a subtree; split it before building, not mid-build.` *(one-liner flattening real complexity — building on it builds the wrong thing)*
- ❌ `- [normal-use-bug] concurrency: what if two users disband at once?` *(mechanism / child-owned → out of scope, do not raise)*
- ❌ `the contract is a bit long` *(no victim/decision)*

Examples — code:
- ✅ `- [normal-use-bug] tests/helpers/x.js:88 — the harness drops TIMELOG_FILE before a child's own teardown hook runs (t.after is FIFO), so a child test that writes on teardown hits the developer's real ~/.timelog.json. Reproduced at 6 files / 42 tests — suite still green, exit 0, and the real file is modified.` *(an ordinary test run corrupts the user's data → must-fix; had it also broken the run, `crash`)*
- ✅ `- [improvement] tests/helpers/x.js:95 — the exit-hook diagnostic asserts "the home file is still there", but the drift bit also turns on when the baseline file is *deleted*; a committed test prints that false line on every run. Nobody's work, result, or data is touched — the harness states what it never measured.` *(real, reproduced — and record-only, because nothing reaches the user)*
- ✅ `- [improvement] tests/helpers/ — 216 lines of harness against 106 lines of product, and ten straight rounds found defects in the harness rather than in the product. It defends the tests, not the behavior — cut it, don't review it deeper.` *(no lens bounded to one diff can see this; the caller must raise it)*
- ❌ `- [requirement-unmet] the CLI has no --json flag yet` *(no requirement states it — a missing want is not a defect; it is scope.)*

## verify — the checklist the lenses fill (don't hunt open-endedly)
A spec passes when this finite list is **affirmatively satisfied** — NOT when "no reviewer can imagine an edge," and **NOT when a reviewer merely 'found nothing'.** Each lens marks **PASS / PARTIAL / FAIL** *with the evidence that earned it*: a bare "looks fine" is **not** a PASS. **An unshown check is PARTIAL, never PASS.** The cycle's verdict is the table.

**Evidence accumulates across the find waves** — the target is frozen, so a check shown in wave 1 stays shown; a later wave fills what is still PARTIAL instead of re-earning what isn't. Each shown check records **what its evidence cites** (`checks[].basis` — the clauses/lines the map or sketch leaned on). Fixes change bytes: a fix **touches** a check when it edits anything that check's `basis` cites, **or adds material the check's instrument must cover** (a new clause enters C1's reverse map · a new edge enters C3's walk) — those checks revert to PARTIAL and the confirmation round re-works exactly them (a *cut* clause therefore un-shows the C1/C3 maps that cited it, and an *added* clause un-shows them too).

**Two classes of check.** C1–C5 (and every D/F check) are *evidence-capable* — a pasted map, a built consumer, a pointed-at AC can show them; there PARTIAL blocks like a must-fix item, so nobody passes by not looking. **C6 is *evidence-incapable*** — "reads in one pass" has no finite positive proof, so demanding one only makes a reviewer invent grounds. For C6, **only FAIL blocks** (quote the line, name the misreading it causes); PARTIAL counts as PASS at judgment. **Comparative metrics are banned grounds** — length/density relative to siblings, or to the document's own longest line, manufactures a FAIL against any document (every document has a longest line; shrink it and the next line is the new longest).

One list, six checks. Written for a `skeleton`; where a **leaf** (`feature`) differs, the **leaf:** clause says how (a leaf *pins* behavior, so its deferral tolerance is lower).

- **C1 Coverage — mechanical, *paste the map*** — enumerate the brief/parent scope items and map each to **exactly one** child role: **0 unmapped (gap), 0 double-owned (overlap)**. And the *reverse*: every Contract clause must trace back to a brief scope item — **a clause outside the brief's Does/Doesn't is scope-creep → flag it** (cut it, or revise the brief; the brief is the scope SSoT). Assert nothing; show the mapping. **leaf:** map the parent-contract clause this node fills + its Requirements onto its Contract·AC — every behavior it owns appears once, nothing double-owned with a sibling. *(coherence)*
  - **Actor & prerequisite closure — map the *nouns the rules lean on*, not just the scope items.** List every actor the spec names (employee · manager · admin …), every entity/attribute its rules depend on (hire-date · team · rank · auth identity …) and every deliverable its features consume (sprites · sounds · level data …); each MUST be *owned* by some child or the foundation — a deliverable by its maker, which may be a named production process outside the tree (D2). A noun the rules use but **nobody creates/owns** is a gap — the source doc assumed it, the tree forgot it. Show the noun→owner table. **leaf:** those nouns must be *declared inputs/dependencies* (owned by a sibling·ancestor·foundation, or by that named process), not silently assumed; a consumed deliverable's format is this node's Contract, and its AC is met by any deliverable in that format — a placeholder included. *(coherence)*
  - **Own structural deliverable — the skeleton must build *something itself*, not only delegate.** Check the AC/Subtasks (not the Contract): does *this* node build the glue/shell its children slot into? For the **root** detailed from its sketch, that is the **base environment + the walking skeleton** (one real path through the main components, tested end to end that it connects — not a boot alone, not what an empty slot gives); a root reopened later keeps the deliverable it was built with. A **pure-delegation skeleton** — AC/Subtasks are only "grow child X", so `implement` would build nothing — is a **FAIL**; name it. (This is about the *deliverable*, not the Contract — the Contract still stays lean/deferred per C4.) **leaf:** n/a. *(coherence)*
  - **Ref fidelity — fill C1 in the packet.** The draft was written *from* the ref intent records, and every gate after this one reads the Task as its yardstick — so this is the one check that holds the yardstick against its source. Open every packet coordinate and read each clause in its machine-carried `heading` path; do not accept the caller's prose as a substitute. For every canonical clause id return `c1: carried|deferred|divergence|excluded|missing` plus, for `carried`, a **`c1_case` walk** — `<the condition the clause names> -> <what the Task's own lines then make observable>`. **`carried` is reachability, not presence**: walk the case from what the Task *takes* to what it *gives*, and check the line that **admits the case into the output** (the row set · the selection · the quantifier), not only the line that handles its topic. If a selection line excludes the case before the handling line could run, the disposition is `divergence` (deliberate, with the Change Log entry) or `missing` — **never `carried`**. The runtime refuses a `carried` with no walk. Plus `c1_basis`: `Contract:<n>` / `AC:<n>` for carried, an explicit `[→ child/deferred: ...]` Contract/AC line for deferred, `Change Log:<n>` for divergence, `adjudication:<n>` for excluded, or `finding:<id>` for missing. Numbers are 1-based non-empty logical blocks inside that named section. Never change or omit a roster row. `missing` is always a finding; PASS requires zero terminal missing rows. The state file keeps this bounded: `checks[C1].shown` records disposition counts + the round-brief packet pointer, and `basis` names that packet rather than claiming "all clauses." Bounds: only the packet clauses this node covers, never the whole ref; source `(gap)` candidates are already omitted from dispositions but remain bound by `source_digest`; the demand is presence-or-deferral — **never** "an AC that measures it" (that is C5's own bounded rule). An empty roster is honest only with the packet's own state: empty `scope` = intentional no-ref; non-empty `scope` = assigned headings whose candidates are all `(gap)`. **leaf:** this is where it bites — a leaf *pins* behavior, so a silently narrowed clause ships as missing behavior. *(coherence)*
- **C2 Buildability — show it** — name a consumer/child and *sketch building its part* from this contract alone; the only hole is a spot you'd be **blocked** (not one you'd reasonably decide). **leaf:** sketch building the leaf itself. *(consumer-impersonator)*
- **C3 Boundaries & invariants — fill C3 in the same packet.** Are the child boundaries + the cross-cutting invariants all children must respect stated? For **every** packet clause return `c3: handled|deferred|divergence|excluded|not-edge|missing` plus `c3_basis`. `handled`, deferred, divergence, excluded, and missing use the same exact anchor classes as C1; `not-edge` uses that clause's own exact `source` coordinate. A source-stated empty/none-set/failure case cannot become `not-edge`: only handled, an explicit deferral/divergence, a recorded exclusion, or missing is honest. At aggregation the main session joins C1/C3 by stable clause id: carried↔handled, deferred↔deferred, divergence↔divergence, excluded↔excluded; `not-edge` accepts any non-missing C1. A conflict leaves both checks PARTIAL and creates one finding. **leaf:** the standard edges (empty · not-found · failure · none-set) are answered *here* unless explicitly deferred **to implement** with a marker (a leaf has no children to defer to) — unmarked silence weighs heavier than in a skeleton. *(gap-finder, at THE BAR)*
- **C4 Scope discipline** — is mechanism/child-detail deferred (markers), not pinned? **An over-stuffed contract FAILs here** (too detailed for a skeleton → delegate). **leaf:** inverted — is anything here actually a parent's/sibling's job? (Rare.) *(breaker — hunt unbuildable holes AND over-reach)*
- **C5 AC testable** — is each AC measurable/verifiable (NFR as a checkable item)? **An AC states the result required, not the wrong implementations forbidden.** Coverage is judged by **consequence, not completeness**: what must be pinned is where a wrong answer reaches a person *as a plausible-looking value* — a silently wrong number, lost or corrupted state, a normal path wrongly passed or blocked. A promise no AC measures is a finding **only when breaking it produces one of those**; otherwise it is an `improvement`, recorded and never blocking. **Never ask the AC to enumerate the implementations that must die** — that is *implement*'s job (tests first) and *review*'s (run the tests, compare to the AC), and those two read real code instead of imagining it. *(gap-finder)*
  - **Stop rule — the generator smell.** If a round's findings all read *"rule R isn't measured at spot P"* and the fix is to **widen a coverage rule inside the spec** ("measure every branch" → "…at every spot"), the spec has begun specifying its own test matrix: rules × outputs × sub-cases grows faster than rounds can close it, and each round's tail gets thinner. **Bound the rule instead of widening it** — each promise observed once, from what a consumer sees — and move mutation-killing to implement/review.
- **C6 Confirmable at a glance** *(evidence-incapable — FAIL-only, see above)* — readable in one pass; if a Contract is a dense wall, it's over-specified → FAIL. A C6 FAIL quotes the line and names the misreading it causes — never a length comparison. *(non-expert)*

## verify-tree — the decomposition checklist (D1–D5)
Runs on the whole **sketch tree** (at plan #0, and after a structural plan/`revise`), before any node is built — the cold gate on the *decomposition itself*. Same rule as the spec checklist: each lens marks **PASS / PARTIAL / FAIL** *with shown evidence*; an unshown check is PARTIAL, never PASS.
- **D1 Source→node scope assignment — paste the map from `refs`.** Open every exact heading named by every Task's `refs` through current `ref/index.md`. Map each current in-scope ref behavior to ≥1 owning node, and every non-empty Task assignment back to behavior that node actually owns: **0 uncovered, 0 wrongly assigned, 0 unexplained overlap**. A heading may feed more than one node only when the sketches show the responsibility split; name that split. `refs: []` is valid only for an intentionally no-ref node (for example D2 system scaffolding), never an undecided source. A non-empty heading whose included content is all `(gap)` remains assigned scope — deliberately undefined is not no-ref. Also map each brief-only scope item to ≥1 node and every node to brief/ref scope: **0 scope-creep**. (C1, at tree scale.) *(coverage-mapper)*
- **D2 System completeness — what the domain doc omits** — a real multi-user / rules-driven system almost always needs infrastructure the *source doc never mentions* (the doc describes the *domain*, not the *system*): **settings/configuration · admin & role management · audit log · org & user management · authentication · notification delivery**. A product also ships **deliverables made outside code**: **art · sound · translated text · content data (levels · dialogue) · fonts**. For each: is it needed here, and who owns it? Infrastructure is owned by a node; a deliverable by whoever **makes** it — a node, or a production process outside the tree **named in the Task that takes it in**. Showing it, or defining what it depicts, is not making it; and a placeholder that lets its consumers build does not stand in for a maker. A needed-but-ownerless one is a gap — and the source doc *won't* list it, which is exactly why domain-coverage (D1) misses it and this lens exists. *(system-architect)*
- **D3 Prerequisite & actor closure — tree-wide** — every actor the system names + every entity/attribute its rules lean on (hire-date · team · rank · auth identity) is *owned* by some node, and every deliverable a feature consumes (sprites · sounds · level data) has a maker (D2). (C1's actor-closure, across the whole tree.) Show the noun→owner table. *(coverage-mapper)*
- **D4 Boundaries & shared-state ownership** — node responsibilities split cleanly (no two nodes own the same thing); each piece of *mutable shared state* (a balance ledger · the audit log · the calendar · the settings store) has exactly one owning node. *(boundary-checker)*
- **D5 Depth sanity — a one-liner hiding a subtree** — does any sketch *flatten real complexity* that should be its own decomposition? An approval *routing* that's actually org-chart-derived + rank-constrained; a *calculation engine* with overlapping rate rules. Name the node **and** the complexity it under-models, so grow splits it instead of discovering it mid-build. *(depth-breaker)*

(Readability is the **non-expert** lens: the decomposition must be confirmable by a human at a glance — flag undefined/duplicate node names, a tangle, or two nodes that are really one.)

## verify-tree fidelity — the survey checklist (F1–F4)
Runs **once per brownfield adoption**, on the mapped all-`done` tree, before any node work — the cold gate on the *survey itself*: the map is an agent's claim too, and every later `revise` computes blast radius by trusting these Contracts. **The criteria is the CODE** — every check is answered by reading (or running) it, never by the map's own say-so. Same rule as every checklist: PASS only with *shown* evidence; unshown = PARTIAL.

- **F1 Code↔tree coverage — paste the two maps** — every source file/module → an owning node, and every node → the real code it names: **0 unowned files, 0 code-less nodes**. *(coverage-mapper)*
- **F2 Contract↔behavior fidelity — sample and show** — pick the highest-risk nodes (entry points · shared state · the biggest), read their code, and check each sampled Contract states what the code *actually does*. A Contract promising what the code doesn't do — or a behavior consumers visibly rely on that no Contract names — is the finding: name node + clause + code line. *(code-reader)*
- **F3 No beautification** — the tree mirrors the real structure: a tangled module maps to a tangled node; shared state appears where it really lives. **A tree cleaner than its code is a falsified survey.** *(honesty-auditor)*
- **F4 Backlog honesty** — what the survey noticed as wrong is actually *parked* (findings/restructuring.md), not smoothed over. Spot-check the code for defects the backlog never names. *(honesty-auditor)*

(Fidelity spawns at most the `standard` lens count — a big survey rounds **up by widening F2's sample**, not by adding lenses.)

## Check assignment by level — every check always has a cold owner (verify & verify-tree)
**Invariant: every check (C1–C6 · D1–D5 · readability) is carried by exactly one spawned reviewer.** The level sets the reviewer *count*, never the checklist's *coverage* — an unowned check would sit PARTIAL forever and block every round (or invite passing by not looking).
- If a check's home lens (tagged in the checklist) isn't spawned at this level, **assign it to one of the spawned lenses** — any of them; the absorbing reviewer applies that check's criteria *as written in the checklist*, not its own lens's framing. What must hold is the count (**exactly one owner, never zero, never two**), not which lens gets it.
- `models[<lens>]` keys keep working — only spawned lenses are looked up.

Which lenses spawn (each level adds to the one above):

| level | verify (spec) | verify-tree (decomposition) | verify-tree (fidelity) |
|---|---|---|---|
| light (2) | consumer-impersonator · coherence | coverage-mapper · system-architect | coverage-mapper · code-reader |
| standard (3) | + gap-finder | + boundary-checker | + honesty-auditor |
| full (5) | + non-expert · breaker | + depth-breaker · non-expert | (capped at standard — widen F2's sample instead) |

(review/code has no checklist — its lenses spawn in fixed order, first *N*; its pass judgment is findings-based.)

## Role lenses — verify (spec) — spawned per the check-assignment table
- **consumer-impersonator** (C2) — *you are a node that will use this contract.* Try to write your code against it alone. A hole = a spot where you'd be *blocked* (can't pick a return shape / don't know who outputs what), not a spot you'd reasonably decide.
- **gap-finder** (C3) — walk the standard edges (empty · not-found · failure · none-set). Flag one **only if** the contract leaves a competent implementer unable to proceed on an *in-scope* case. A child-owned or deferred edge is not a gap.
- **coherence** (C1) — check against global rules + parent/sibling contracts. **(up)** does this node fill the clause its parent assigned it — and does the draft **carry, defer, or note every behavior the ref intent record states for this node's scope** (the narrowing map: a silently dropped/shrunk ref clause is the finding; show the pair)? **The narrowing to hunt is a shrunk *set*, not a missing topic**: the source says *all X* (or *X with no Y is still …*) and the draft answers *X that have Y*. That draft still discusses the topic — often correctly — so a topic-level read passes it. Walk each case against the draft's own row set. **(down)** if a skeleton, do its children's roles cover it cleanly (no gap/overlap), **and does every actor/entity/deliverable the rules lean on (hire-date · team · auth identity · sprites) have an owner**? — judged from the contract; the children are only sketches (their contracts aren't written yet), so check the decomposition, not their detail.
- **non-expert** (C6) — you don't know the jargon; the spec must be confirmable at a glance. Fail undefined terms, fluff, a dense wall, the same concept under two names. Quote the line.
- **breaker** (C4) — you came to break the contract *and* to catch over-specification. A break counts only if a named consumer is blocked; flag any mechanism/child-detail that's been pinned into the contract (it should be deferred).

## Role lenses — verify-tree (decomposition) — spawned per the check-assignment table
Each reads **the whole sketch tree (including every Task's `refs`) + brief + ref spec** (cheap — sketches are one-liners).
- **coverage-mapper** (D1, D3) — paste two maps: current ref heading/behavior + brief-only scope → node using the Tasks' exact `refs` (0 uncovered/wrongly assigned/unexplained overlap), and actor/entity/deliverable-the-rules-lean-on → owner. Treat explicit `[]` as intentional no-ref and keep all-`(gap)` headings distinct from it. A blank cell in either is the finding.
- **system-architect** (D2) — *you are shipping this for real.* What does the live product need that the domain doc never mentions — D2's scaffolding and its deliverables made outside code? Name each one that's needed but has no owner — for a deliverable, no maker.
- **boundary-checker** (D4) — two nodes that own the same thing (overlap), or a mutable shared state with no single owner. Name the collision.
- **depth-breaker** (D5) — a one-line sketch that hides a real subtree. Name the node + the complexity it flattens (routing rules, calc overlaps, multi-step workflows), so grow splits it instead of discovering it mid-build.
- **non-expert** — the tree must be confirmable at a glance: undefined/duplicated names, a tangle, the same concept as two nodes. Quote the node.

Fidelity-only lenses (the survey gate — criteria = the code):
- **code-reader** (F2) — *you verify claims against the code.* Read the sampled nodes' code and compare each Contract clause to actual behavior; scale a big survey by widening the sample, never by trusting the map.
- **honesty-auditor** (F3, F4) — *you assume the surveyor wanted the map to look good.* Hunt beautification (a tree cleaner than its code) and smoothing (code defects the backlog never names). Quote the code that contradicts the map.

## Role lenses — review (code) — fixed order, first *N* = `review.scale[level].reviewers`
Each reads **only this node's diff + AC·Contract + test results**.
- **correctness** — does the diff meet the AC·Contract? Logic errors, off-by-one, wrong branch, broken invariant.
- **security** — injection, auth/authz gaps, secrets, unsafe defaults/deserialization/path handling — in this diff.
- **the-6-month-maintainer** — hidden coupling, surprises, and **duplication of code that already exists** (Principle 3 — did this reimplement something?).
- **breaker** — edge·failure inputs the running code mishandles. Same BAR: name the input → wrong behavior.
  > **What the code lenses can't see:**
  > - **Aesthetics · design direction · look-and-feel** — the diff carries no rendered output, so these are **the person's to judge, asked up front as a decision** (implement's reversibility gate handles them before the code is written; review does not re-check).
  > - **Security sees only this node's diff** — an exploit living in the *interaction* with unchanged code (a misused existing sanitizer, a bypassed existing check) is outside its read-scope. That bound is the deliberate cost trade; contract-level security invariants belong in `conventions.md` and are probed at *verify*.
- **test-quality** — are the tests *real* (exercise the path) or hollow/tautological? Every AC item backed by a passing test? A green-but-empty suite is an `improvement` — unless it masks an AC currently unmet, which is that wrongness's own must-fix finding (`requirement-unmet`).

> **A coverage finding must name its clause — review's Stop rule.** "The tests don't measure axis X" is must-fix material only when the Contract/AC **names** X (an expected input · a promised output · a listed edge) *and the gap currently hides a real wrongness*: cite the clause, and fix with the *minimal* test for that clause, not a matrix. An axis no clause names is owed no test — raising it is over-reach (struck at classification), and *writing* such tests is itself a finding (scaffolding beyond the contract → cut). Combinations follow the same line: a combination check is owed only where a clause or a confirmed problem names the interaction — a product of *unnamed* axes is never owed, and "nothing else does X"-style contract wording alone does not conscript a walk of every state × error × history cell. This mirrors C5's Stop rule: the spec doesn't enumerate the implementations to kill, and the review doesn't demand tests beyond the contract — both cut off an infinite supply.

> **When the target is a rule someone else will implement, vary the implementations — not just the inputs.** A rule that demands a check ("the AC must carry a test that catches X") is satisfied by more than one test setup: which process it runs in, which environment it starts from, which import order, when it observes. Building *one* setup and finding it sound shows **that setup** works — not that the rule holds. Spread that axis before calling a round clean, and try first the setups a convention-following implementer would naturally reach for: those are where a rule stated as intent-plus-hints goes blind.

## Aggregate
Merge findings; dedupe by (where + what). When duplicates disagree on category, keep the classification the *definitions* give the strongest evidence — never the more alarming label for its own sake.

When two findings are the same underlying hole through different paths, collapse them to one record, give it one `family`, and keep the clearest `where`/`what`/`measured`.

## Classification — at every wave boundary, never deferred
The caller classifies **each wave's finds as the wave closes** (§Categories) — deferring classification to the end of find is what let unclassified piles masquerade as progress, and the streak cannot be counted without knowing whether the wave produced a new *must-fix*. Per wave:

- **Strike first, before classifying**: anything asking for mechanism or child-owned detail (out of scope by the SCOPE rule); anything failing the *name-the-victim* test; anything a competent implementer would reasonably decide; anything on the do-not-raise list; duplicates (merge into the listed id).
- **Also strike "the child would stumble, so this node must build scaffolding for it"** — demanding ergonomics on behalf of an unbuilt consumer is the same over-reach as deciding *for* it.
- **Classify the rest** by the category table — set `category` + lane fields + `condition`/`impact` (+ `requirement`) on every keep. `validate` refuses a record category in `open_issues` and a bare must-fix category in `followups`, so the lane follows the class mechanically.
- **A record-category keep gets a second question: is it worth the person's look?** Does it change a result a user meets — behavior · data · screen · security? **Yes** → `followups`, for the person's pick at the next plan (a drop there becomes an adjudication, raised never again). **No** → discard it now: it stays in this cycle's `found` as `judged: dropped`, so no later wave re-raises it, and never enters `followups`.
- **UPGRADE folds in**: a stronger submission attached to a listed entry (a live repro where it lists a mere coverage gap) upgrades that entry — the strongest evidence is what gets classified, never a duplicate.
- **Contested or thin evidence → `pending`**, not a guess: hold the candidate, settle it by a targeted measurement or ONE cold defender ruling, and do not let the wave count toward the streak until it is settled (§The cycle). Never round a candidate down to close a wave or up to be safe.
- **Two strikes closes a shape.** When two findings fall to the same reason — same shape, new instance (a second length-comparison readability complaint · a second no-named-clause coverage demand) — write ONE adjudication at the *shape* level and add it to do-not-raise on the spot; a third instance is struck on sight, unargued. **Two bounds on the strike:** the shape is written **at the altitude of the two instances, no broader**, and it records *why* they fell (the reason profile — "outside this product's stated reality", not just the topic); and an instance arriving with **evidence of a current must-fix problem always reaches the classification** — a strike suppresses re-litigation, never live evidence. Pre-seeded banned shapes: comparative-metric readability grounds · coverage demands naming no clause.

For **result** reviews, only `kind: defect` may stay in `open_issues`; move `contract-gap` and `concern` to `followups`. For **spec/tree** reviews, `defect` and `contract-gap` may stay in `open_issues`, while `concern` still belongs in `followups`.

**`followups` is a record, not a queue.** It holds the record categories (`improvement` · `harmless-bug`) that passed the second question — whatever their `kind`, a harmless current-code defect included — and must-fix work routed to another gate (`contract-gap`). Nothing promotes an item out of it automatically — not `next auto`, not a later cleanup batch, not several reviewers having noted the same one; only the user's explicit pick at a planning pass makes one into work. A drop whose reason should outlive the list is an `adjudications` entry instead.

## Cycle hand-off
If a phase surfaced real but non-blocking later work a user would meet, record it in `followups` (a record category, or a routed `contract-gap`) rather than forcing it into `open_issues`; a drop that should stay settled is an adjudication, not a queue item.

> **The confirmation round's diff is assembled by hand — hold the gate records out of it yourself.** `grovespec diff` excludes everything under `paths.review`, but a confirmation pass is scoped to *the fix's own diff*, which no command derives. The fix commit rightly carries the round record it just updated, so handing that diff over raw shows the confirming lens the verdicts and dropped findings of the round it is confirming. Same blankness, same rule: pass the code, never the record.

Write `.grovespec/review/<id>.verify.yaml` (verify), `<id>.review.yaml` (review), or `tree.verify.yaml` (verify-tree) — template `review-state.yaml`. It holds:
- `phase` (find | fix) + the live counters (`no_new_streak`; fix: `current_item` · `item_phase` · `plan_clear_streak`) + one `rounds[]` entry per spawned pass. **A round entry is the countable result, never the story of it**: `n` and `outcome` required, `phase` · `found` · `item` · `note` optional. The entry is **flat** — every field on one line at its own indent, `found` as a one-line flow map — and the pass's reasoning goes in its own file (`<id>.round<n>.brief.md` · `.plan.md` · `.confirm.md`; the result gate's as **`<id>.review.round<n>.*`**, so a code-review round never overwrites the brief a spec seal pinned) with a **one-line** `note` pointing at it. `validate` reads depth, so a block scalar, an indented paragraph and a nested mapping are each refused — and every list in the record is block style (a flow list is refused: it would turn each per-item check off instead of failing it). A quoted value stays one strict-YAML line: in `"…"` write `\` as `\\` and `"` as `\"`; in `'…'` double the `'` (`''`) — prose citing Windows paths reads best single-quoted; `validate` notices breakage (`FORMATS.md` "review-cycle state"). Unbounded, this is where the narrative actually moved in — 394 lines of it in one node — and every later cold session reading this file had to carry all of it. **A changed fix plan never inherits the old plan's counter** — `plan_clear_streak` restarts at 0 with the edit, in this session or the next;
- `found` (the raw find list, growing through the waves, each entry classified at its wave's boundary) + `strategies` (which waves ran which — what makes the streak mean *differently-armed looks*);
- `checks` (verify/tree: the C#/D#/F# table — per check `verdict` PASS|PARTIAL|FAIL, one-line `shown` evidence, its `basis`, the wave) — the accumulation's persistent home, and what a new session resumes find from;
- for a spec find round, its brief contains exactly one `grovespec-source-evidence/v1` packet generated **before** the cold reviewers from the Task-owned `refs`. The main session persists the exact immutable roster and merges only the C1/C3 disposition fields returned for every clause; `checks[].shown` carries their counts + packet pointer and `basis` names that packet. Before a C1/C3 PASS is persisted, join the two dispositions by stable clause id — an unset, unmatched, missing, or contradictory row is a finding, never prose to reconcile later. Terminal `grovespec pin TASK-N` recomputes the assignment, heading/context evidence, clauses, resolved Task basis content, and Task frontmatter before writing `spec_digest` + `task_evidence_digest`;
- for every tree pass, write `tree_evidence_mode: decomposition|fidelity` in the record before round 1. The complete read-scope above is machine-bound before human approval. `pin tree` stores `source_scope_digest` over D1's visible current catalog, canonical source material, tree order, and assignment state; an all-mapped/no-ref fidelity tree stays code-grounded through spec/result record creation but still observes catalog roster/material as a tripwire, while an actual ref assignment or non-mapped node activates ownership. `tree_evidence_digest` binds everything else the selected lens set read under the persisted mode: decomposition = tree + brief + every full sketch Task (on a built-tree re-verify, only id·name·Overview·`refs`); fidelity = tree + id·name·Overview·Contract + Git-visible src/tests + both backlogs. `approve tree` recomputes both current seals, and `validate` recomputes mode-specific evidence while the verdict is pending. A decided historical record without newer fields remains readable and is never backfilled; a pending legacy verdict cannot be approved, and any changed/partial current seal requires a fresh tree cycle;
- when find closes: the verdict (the C#/D# table) + the confirmed `open_issues` (the fix phase's whole queue — fixed one at a time, in the order the caller sets: `crash` first, then by blast radius);
- classification's strikes appended to `adjudications` — **handed itemized (claim + verdict + reason) to every later wave as the adjudicated list**, alongside the two-strike shapes and the user's exclusions (`excluded-by-user`).

The next wave/round is a new cold session reading only this file. **Adjudications never leave it**: `reopen` preserves them across cycles — a settled call is a boundary ("don't re-raise"), not evidence, so a new cycle doesn't expire it; and a copy in the Change Log would reach the cold reviewers through the Task file. **One guard, both substrates**: on a `draft` reopen the contract changed — before condensing the kept list into do-not-raise categories, drop every entry whose written reason leans on the old contract (e.g. "the contract table has no such cell" after the table gained one). The **result twin**: on a `result` reopen the code moved — drop every entry whose written reason leans on code that no longer exists ("lock.js serializes it" after lock.js is gone). A reason that died with its substrate must not suppress a now-real finding; this is why every adjudication records its reason, not just its verdict. **An `excluded-by-user` entry is the one kind this pruning never touches**: its reason is the user's decision, not the substrate — it falls only when the user reverses it, or when live evidence of a current must-fix problem is put back in front of them.
