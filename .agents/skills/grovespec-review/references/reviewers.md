# reviewers — the cold-review engine (shared by verify + review)

> `grovespec-verify` (spec) and `grovespec-review` (code) both load this to run a cycle. The SKILLs hold the *rules* (levels, phase ends); this holds the *mechanics + the bar + the lenses*, so every node's review comes out the same shape. The two callers differ in lens set, read-scope, and (verify) the checklist.
> A cycle is **three phases — find → judge → fix** (§The cycle): finders sweep a frozen target in waves, ONE triage grades everything at once, and fixes are confirmed against their own diff. No phase re-does another's work, and no phase ends on a verdict streak.
> Reviewers write findings in the project's language (`config.language`).

## THE BAR — read first. *Sufficient*, not exhaustive.
You review for a **competent implementer/consumer** who will research, make reasonable decisions, follow the project's conventions, and ask only when *truly* stuck. So:

- A finding is a real flaw **only if that implementer would be blocked or build the wrong thing.** "I can imagine an unhandled edge / an unspecified detail" is **not** a flaw if a competent implementer would reasonably handle or decide it.
- Yes, go in adversarially ("try to break it") — **but a kept finding must name *who is blocked, and on what decision*.** *What is merely unstated* is not enough.
- You are checking for **sufficient** context, not exhaustive detail. Perfect specs don't exist; "enough to build the right thing without a mess" is the target. (This is the single rule that stops a review from churning for rounds.)

## SCOPE — what a spec may and may not contain
- A spec states the **contract** — what it *takes · gives · guarantees* — and the line is **what a consumer can observe**: the public names it calls, the shape of what crosses the boundary, error behavior, ordering, and any atomicity/concurrency promise a consumer can see and rely on. It does **not** state the unobservable inside — algorithms, private structure, a store's internal schema, how a transaction is implemented. Those belong to the node's own *implementation* or to a *child*. The same topic falls on either side by observability: "the file is valid JSON after every add" is contract; "writes go through a temp-file rename" is mechanism.
- A **skeleton**'s spec states only: its child pieces (by role), the boundaries between them, and the **cross-cutting invariants** all children must respect — and **defers the rest to named children**.
- **An unspecified mechanism, an edge a child owns, or an explicitly deferred detail is NOT a gap — do not raise it.** A spec line like `[→ child/deferred: …]` is *correct delegation*, not a hole. Demanding such detail is over-reach; the triage will drop it, so don't raise it in the first place.

## Which lens set · scale · read-scope · do-not-raise
- **verify-tree** (`target_type: tree`) — one target, **two questions**; the tree's state picks (`grovespec next` names which gate is armed):
  - **decomposition** (sketch nodes exist) — the **decomposition lenses** + **D1–D5**: is this the right decomposition and source→node assignment? Runs at plan #0 (and after a structural/source-assignment `plan`/`revise`), before the per-node build. Read: the whole sketch tree (`tree.md` + every sketch Task — *cheap, one-liners plus frontmatter `refs`*) + the brief + the ref intent records (current ones via `ref/index.md`).
  - **fidelity** (a pristine mapped/brownfield tree) — the **fidelity lenses** + **F1–F4**: is the survey an accurate photograph of the code? Runs once per adoption, right after a brownfield init. Read: the tree + every mapped Task (id·name·Overview·Contract) + **the code itself** + the backlogs (findings/restructuring.md). **Criteria = the code, not any intent doc.**
  - Count from `config.yaml` `verify.scale`. On a post-`revise` re-verify of a *built* tree, read each Task's **id·name·Overview + `refs` only** (not full contracts), keeping the same economy while still exposing the source map D1 must check.
- **verify** (`target_type: spec`) — the **spec lenses** + the **verify checklist** (below); count from `config.yaml` `verify.scale`. Read: the draft Task + the parent's Contract + **the original ref intent clauses assigned by this Task's `refs`** + the relevant `conventions.md`. The caller runs `grovespec source TASK-N` and hands every reviewer that round's entire canonical packet; each reviewer opens the packet's original coordinates itself, and a caller-written summary is not criteria. (Not every sibling — only what the contract references.)
- **review** (`target_type: result`) — the **code lenses**; count from `config.yaml` `review.scale`. Read **ONLY this node's changed files (its diff) + its AC·Contract + the test results** — never the wider codebase. (This bound keeps review's cost flat as the project grows.)
- **do-not-raise**: the caller passes the state file's `adjudications` **itemized — each entry's claim (one line) + verdict + recorded reason** — plus the shape-level categories the two-strike rule wrote (out-of-scope boundaries + accepted gaps — e.g. "internal schemas · transaction mechanics · timezone/month = child/impl scope"). **Do not re-raise a listed claim, or a new instance of a listed shape** — already decided. These are *verdict records, not clean-claims*: each settles one claim and says nothing about the area around it, which stays as open as anywhere else. (Why itemized, not condensed: METHODOLOGY §6.)
- **Model (optional)**: each reviewer's model = `config[verify|review].models[<lens>]` if set, else `models.default`, else **inherit the session model** (the portable default). Triage uses `models.triage` (same fallback). Model ids are host-specific; if the config names one the host cannot select for a subagent, stop and name it instead of silently inheriting a different model.

## Spawning
- **Count** from `config.yaml` (`verify.scale[level].reviewers` / `review.scale[level].reviewers`) — the SSoT; don't hardcode here.
- **Which lenses** spawn at that count: the **check-assignment table** below (verify/verify-tree), or the fixed order (review/code). *Which checks each carries* then follows from that section's coverage invariant.
- **Spawn as parallel subagents** with the host's subagent tool — one batch, concurrent. Each starts from an **empty context**; that's what makes them cold. The host must provide at least the configured reviewer count as concurrent child slots; if it cannot, stop and name that capacity gap instead of serializing the wave or silently shrinking it. (Main session only — see each skill's invocation contract.)
- For `skip`: spawn none; the caller self-checks against the checklist.
- Each reviewer's prompt = **common preamble** (incl. THE BAR + SCOPE + the do-not-raise list) + the **found list** + the **strategy ledger** (§The cycle) + its **role lens** + the **findings format**. Never give them how the target was built, the author's reasoning, or any **clean-claim** ("area X is verified clean") — other reviewers' *output* (finds · ran strategies) travels; the author's narrative and innocence claims never do.
- **Spec source hand-off is one exact packet, never excerpts or a summary.** The main session generates it with `grovespec source TASK-N`; the runtime derives coordinates from the Task's structured `refs` (or the bounded legacy rule), validates them through `ref/index.md`, and emits the packet. Paste it once in the current find brief and give that whole fence to every spec reviewer. Reviewers open its original coordinates and may return **only disposition fields**: the C1 owner fills `c1`/`c1_case`/`c1_basis`, the C3 owner fills `c3`/`c3_basis`; nobody changes ids, source text, digests, scope, protocol, or schema. If an original or its location cannot be opened, report `missing` plus a real finding id; it cannot be reconstructed from the Task being checked.
- **The working tree is read-only for a reviewer (code review).** Concurrent lenses share one checkout, so a mutation experiment — flip a line, watch a test go red — silently corrupts every *other* reviewer's measurement at the same time. To test a mutation, **copy the project to a temp directory and mutate the copy**; never edit a tracked file in place. A lens that reports an observation the committed source cannot produce has almost certainly read a neighbour's mutation: re-measure in a copy before writing it down. *(A real round lost a measurement this way — a lens observed output impossible from the committed source and blamed the source instead of the neighbour.)*

## The cycle — find → judge → fix
One gate = one cycle of three phases. **What ends each phase is a list, not a verdict streak** — the old terminator ("N clean rounds in a row") made every round a coin flip that reset on tails; nothing here resets.

**1 · find — waves over a frozen target.** Nothing is fixed and nothing is graded while finding, so every wave reads the same bytes. Spawn a wave (the level's lens count), then another, until **the strategy ledger is exhausted AND at least `repeat` waves have run** (`repeat`'s recall duty: one full cold look that found nothing still gets a second, *differently-armed* look). Each wave's payload adds three lists to the preamble:
- **the found list** — every finding raised so far (id · where · one line): *do not re-report these, or new instances of their shape; find what is NOT on this list.*
- **the adjudicated list** — every claim already settled (`adjudications`, surviving from prior cycles and this cycle's judge where find reopens): claim + verdict + reason. *Do not re-report these or new instances of their shape either — but the area around a settled claim stays open; a verdict record settles one claim, never an area.*
- **the strategy ledger** — the strategies already run: *run one that hasn't.*
A wave's finds go onto the found list **unjudged** (the defender is paid once, at judge); aggregate/dedupe only. **Never hand a finder a clean-claim** — a ran strategy tells the next finder what not to repeat, **never that an area is safe**. *(A real cycle planted 205 mutations that "covered" a function whose live defect none of them could reach — single-axis sweeps structurally never build the two-axis cell it lived in. A clean-claim would have sent every later eye away from it.)*

**2 · judge — once.** When find closes, run the defender/triage over the WHOLE found list in one pass (§Over-strictness triage), set lanes + gate fields, run `grovespec validate`, and write `open_issues` / `followups` / `adjudications`. `(gap)` rulings with the human happen here. **Empty `open_issues` — with every evidence-capable check still affirmatively shown → the cycle passes now** — seal it; a cycle that never needed a fix gets no extra confirmation lap (the recall duty was already paid by `repeat` waves of different strategies). A check whose only *worked* status was a FAIL the judge then dropped reverts to PARTIAL — **reopen find for it** instead of passing; what a reopened find then raises goes through the same gates in mini-form (like a confirmation's finds — "once" bars re-judging the judged, not judging the new).

**3 · fix — close the list.** The caller's fix step applies the confirmed issues; then ONE cold **confirmation round**, scoped to **the fix diff + the items it claims closed + the in-node use-sites of what it changed** (callers/readers of an edited symbol · consumers of an edited clause) — not the whole target again:
- did each fix close its item? (re-run the finding's own measurement)
- did the fix open a new hole **in what it touched or in what uses it**?
The confirmation spawns **the lenses that raised the items being confirmed** (minimum one; when in doubt, correctness for code · coherence for spec/tree), cold as ever. Its mini-triage runs the same gates — and **a confirmation finding may be dropped only by a cold judge**: the defender where the level spawns one; at `light`, dropping one requires spawning a defender for it. The caller — often the fix's own author — never self-drops what a confirmation raised (self-KEEP is always allowed). A confirmation reviewer who stumbles onto a real defect **outside its scope** (not in the fix diff or its use-sites) still reports it — but after the mini-triage it lands in `followups`, not `open_issues`: it may extend *this* cycle only when it arrives with gate1 `behavior` or gate2 `yes` (a wrong behavior running, or a shown broken promise). In-scope finds — the fix's own holes and its regressions — block as ever, and the *assignment* never widens beyond the fix. Blocking finds → fix again → confirm again — **but the third fix aimed at the same `family` in one cycle ends the case-work**: the fix step must close the class or escalate (its own counted rule — grovespec-fix). **A revert reopens every item that fix had closed** — restore them to `open_issues` on the spot, and the next confirmation re-runs their measurements (the no-re-report rule never applies to a reopened item). **The list empty + the last confirmation clean ends the cycle.**
This scope is narrower than a full re-sweep **by design**: a defect the find phase missed in *unedited* code stays unseen until the next cycle. That residual window is the accepted price of a terminating cycle — the recall duty lives in find's `repeat` differently-armed waves, not in re-sweeping after every fix.

`round` counts every spawned pass (find waves + judge + confirmations); past `max_rounds` → escalate, as before.

## The strategy ledger
The find phase ends by exhausting a NAMED list of search strategies — never by rounds going quiet (quiet rounds measure luck; a ledger measures coverage of *methods*). **The caller assigns strategies wave by wave** and records each run in `strategies[]`: every seed runs exactly once across the cycle, a reviewer may carry more than one when seats outnumber the seeds left (any level), and a wave with spare seats points them at still-PARTIAL checks — never at re-running a ran strategy. (The check-assignment invariant — every check exactly one cold owner — likewise holds **across the find phase**, not per wave: wave 2 owns what wave 1 left unshown; it does not re-earn what is already shown.)

Seeds — code (`result`):
- `clause-walk` — every Contract/AC clause held against the diff, one by one.
- `single-axis-sweep` — mutate/weaken/delete along one axis at a time; do the tests bite?
- `axis-product` — mutations that survive only at the *intersection* of two separately-pinned axes (state × edit · branch × fixture-population). Build the products deliberately — single-axis sweeps structurally never reach these cells.
- `reference-model-fuzz` — implement the contract independently; randomized differential runs against it.
- `boundary-probe` — pathological/boundary inputs at the public surface (empty · huge · unicode · path shapes · limits).
- `harness-audit` — the suite itself: hollow asserts, fixtures that pin a contract-named axis to one value, isolation leaks.

Seeds — spec/tree: **the checklist IS the ledger** (C1–C6 / D1–D5 / F1–F4) — each check is an instrument with one owner; find closes when every **evidence-capable** check has been *worked* (shown, or FAILed into a finding — C6 needs only its read-through run and any FAILs filed) and `repeat` waves have run.

A reviewer may register a NEW strategy onto the ledger — only by naming **the defect class the ran ones structurally cannot reach AND one concrete spot in this target where that class could live**. **The caller rules on registrations at the wave boundary**, before spawning the next wave: no named blind class, or no candidate spot in this diff → struck. The ledger must stay finite, or it becomes the next generator — an abstract escalation ("k axes → k+1 axes") with no candidate spot is exactly the strike case.

## Findings format + severity (name the victim)
Every kept finding now also needs lane fields:
- `kind: defect|contract-gap|concern`
- `family: <the underlying hole, not the path that showed it>`

Lane rule:
- `defect` = the current review target itself is wrong.
- `contract-gap` = a real issue, but it belongs in later revise/verify work rather than this code gate.
- `concern` = a note or suspicion; never a blocker.
- If the flaw is in the current cycle's diff or in the text under review right now, it is `defect` even if the eventual repair also needs a spec change.
- A review file may name a `family` only once across `open_issues` + `followups`; the same hole re-shown through a second path is one finding, not two.

One finding per line:
```
- [critical|should-fix|nice-to-have] <C# / where: §section · file:line> — <who is hurt + what exactly goes wrong>
  proposed: <level before the gates> · gate1: <behavior|mechanism|contrived|story> · gate2: <yes|no> · gate3: <yes|no>
  <trigger: … when gate1 is mechanism · clause: … when gate2 is yes · workaround: … when gate3 is yes · harm: … for a proposed critical without a clause>
```
A finding with no lane or gate answers is **not gradeable** — the caller cannot record it, so it dies at aggregation. Answer them.

**One ladder — *how strongly must this be fixed*.** The same three levels grade a spec and code; only the *examples* differ. Do not grade on "can a consumer build it" — that is one **case** of `critical`, not the definition. (Reading the case as the definition is what leaves running code ungradeable: code is already built, so nothing in a diff ever "can't be built", and every real defect gets pushed up into `should-fix`.)

- `critical` — **must be fixed.** Something is actually wrong; shipping it is not an option.
  - *spec*: a **named** consumer/child **cannot build its part** — the contract is missing or self-contradictory on something *this node owns*, so the next builder must guess and will guess wrong.
  - *code*: it breaks a Contract/AC promise, loses or corrupts data, or fails on an input it is required to handle.
- `should-fix` — **it works today, but fixing it is strongly advised** — now or soon. Named debt, not a blocker on *working*.
  - *spec*: a normal, in-scope point is ambiguous enough that **two consumers would integrate it differently**.
  - *code*: it runs and the tests are green, but something underneath is wrong — a diagnostic that states what it never measured, a check with no teeth, test scaffolding that outgrew the behavior it defends, a reimplementation of code that already exists.
- `nice-to-have` — **fixing it is optional; it would simply be better.** Wording, clarity, a better name.

> Whether `should-fix` blocks the gate is the caller's `strength` (default `2` = yes) — **never this file's call.** Grade by what is true; blocking is decided elsewhere. Do not inflate a level to force attention, and do not deflate one to let a gate close.

**Severity gates — answer all three, and the answers decide the grade.** You state a `proposed` level (what it is on its merits) plus the gate answers; the final `severity` is whatever they allow.
1. **gate1 — what can you exhibit *today*, by running committed code?** Not "does the flawed text/code exist" — everything under review exists; the question is what goes *wrong* today, and **how the wrongness is reached**.
   - `behavior` — **the wrong behavior itself runs today** (wrong output, wrong exit, wrong state). No cap.
   - `mechanism` — **the defect is verified** — a probe or mutation shows the hole (the check that can't go red, the diagnostic printing what it never measured, the guard that guards nothing) — AND the step that turns it into wrong behavior is **one ordinary act**: a natural future edit, or an in-scope consumer doing the documented thing. **Name that step in `trigger`** (the runtime requires it). **Caps at should-fix.** This is the honest home of a latent problem: real, shown, reachable.
   - `contrived` — the hole is shown, **but reaching wrong behavior needs abnormal action**: deliberately violating a documented rule or contract, two or more independent edits coinciding, input or scale outside the product's stated reality. **Caps at nice-to-have** — recorded, never blocking. *Ordinary vs contrived is judged against the brief/Contract/conventions, not universally: for an internet-facing service a hostile caller is ordinary reality; for a single-user local tool, self-sabotage is contrived.* If naming an ordinary `trigger` takes rule-breaking or a coincidence, the honest answer is this one.
   - `story` — **no verified hole**: the victim is predicted (an unbuilt consumer, a hypothetical reader), the failure narrated, not run. **Caps at nice-to-have.**
2. **gate2** — does it break something the Contract/AC **explicitly promises** — *shown*, not predicted? **Name the clause.** A shown broken promise lifts gate1's cap **for `mechanism`/`story` — never for `contrived`**: a promise that only breaks under deliberate abnormal action is not a promise the product breaks (and if the demonstration was in-scope-ordinary, the finding was `mechanism` all along).
3. **gate3** — is there a **documented workaround**, or an existing check/signal that already catches this failure and names the real cause? If yes, **one level down**. Name it.

The floor is `nice-to-have`. `proposed: critical` must be anchored — either gate2 is yes, or you name the **harm**: what data is lost or corrupted, or which required input fails.

> **The boundary that matters is should-fix ↔ nice-to-have.** At `strength: 2` a critical and a should-fix block *identically* — demoting between them ends nothing. What ends a loop is a should-fix dying to nice; what feeds one for rounds is a story surviving as should-fix, or a **contrived** mechanism re-shown through ever more elaborate probes, each patched case by case. That demotion is the one these gates exist to force, and it is the triage's first job — pushing unanchored should-fixes down, not protecting grades.
>
> **The same hole re-shown through a different path is not a new finding.** Condense it into a do-not-raise *category* (the hole), not an instance (the path) — a loop that keeps producing new paths to one hole is telling the fixer to remove the hole's source, not the reviewer to keep finding paths.
>
> **This is arithmetic, not advice.** The gate answers are recorded as *fields* on the finding, and **`grovespec validate` recomputes the severity cap from them and fails the record if the grade exceeds it.** So there is nothing to argue and nobody to adjudicate it: state the answers honestly and take the level they give. (Prose said all of this before and it did not hold — a node ran sixteen rounds writing gate answers it then graded past. What the machine counts is what survives.)
>
> **No buttressing** — what a gate dropped stays dropped; don't hunt a different justification to hold the level. Grading *below* the cap is always allowed, and under uncertainty between two answers, take the lower one.

**Rank, and cap blocking at 3** — a fourth means demoting one of the first three.

**Name the victim** — the rule that kills non-findings. Every finding names *who meets the failure first* and *what exactly goes wrong*: the next builder (spec), whoever runs the code, the maintainer who reads it. "This seems unclear" / "what about X edge?" with no victim is a **non-finding** — drop it before triage. If a lens finds nothing, it returns `none` with a one-line note on what it checked. The reviewer's final message **is** the result — no greeting.

Examples — spec:
- ✅ `- [critical] C2 §Contract — the *stats* child can't tell from this contract whether month totals are per-calendar-month or rolling-30d; it owns that and would guess.` *(named victim + decision)*
- ✅ `- [critical] C1 — "invite" and "group" children both appear to own invite-code validity → overlap; neither can own it cleanly.`
- ✅ `- [critical] C1 — the rules use *hire-date* (leave→accrual) and *team·rank* (approval→routing), but no child or foundation owns an employee master that creates them → prerequisite gap the source doc assumed.` *(noun the rules lean on, no owner)*
- ✅ `- [critical] D2 — no node owns *system settings*: core-time hours·rate multipliers·thresholds are regulation values that must be admin-editable, not hardcoded; a rules-driven system needs a settings store the source doc never mentions.` *(infra the domain doc omits)*
- ✅ `- [should-fix] D5 — "approval" is one flat sketch, but routing is org-chart-derived + rank-constrained (the approver must outrank the requester) → it hides a subtree; split it before building, not mid-build.` *(one-liner flattening real complexity)*
- ❌ `- [should-fix] concurrency: what if two users disband at once?` *(mechanism / child-owned → out of scope, do not raise)*
- ❌ `the contract is a bit long` *(no victim/decision)*

Examples — code (the same ladder, graded on *how strongly it must be fixed*):
- ✅ `- [critical] tests/helpers/x.js:88 — the harness drops TIMELOG_FILE before a child's own teardown hook runs (t.after is FIFO), so a child test that writes on teardown hits the developer's real ~/.timelog.json. Reproduced at 6 files / 42 tests — suite still green, exit 0, no temp-dir leak, and the real file is modified.` *(breaks the Contract's promise + destroys the user's data → must fix)*
- ✅ `- [should-fix] tests/helpers/x.js:95 — the exit-hook diagnostic asserts "the home file is still there", but the drift bit also turns on when the baseline file is *deleted*; a committed test prints that false line on every run. Nobody is blocked — a child reading it misjudges one line — but the harness states what it never measured.` *(works, strongly advised to fix → debt, not a blocker)*
- ✅ `- [should-fix] tests/helpers/ — 216 lines of harness against 106 lines of product, and ten straight rounds found defects in the harness rather than in the product. It defends the tests, not the behavior — cut it, don't review it deeper.` *(no lens bounded to one diff can see this; the caller must raise it)*
- ❌ `- [critical] the CLI has no --json flag yet` *(not wrong — absent. A missing want is not a defect; it is scope.)*

## verify — the checklist the lenses fill (don't hunt open-endedly)
A spec passes when this finite list is **affirmatively satisfied** — NOT when "no reviewer can imagine an edge," and **NOT when a reviewer merely 'found nothing'.** Each lens marks **PASS / PARTIAL / FAIL** *with the evidence that earned it*: a bare "looks fine" is **not** a PASS. **An unshown check is PARTIAL, never PASS.** The cycle's verdict is the table.

**Evidence accumulates across the find waves** — the target is frozen, so a check shown in wave 1 stays shown; a later wave fills what is still PARTIAL instead of re-earning what isn't. Each shown check records **what its evidence cites** (`checks[].basis` — the clauses/lines the map or sketch leaned on). Fixes change bytes: a fix **touches** a check when it edits anything that check's `basis` cites, **or adds material the check's instrument must cover** (a new clause enters C1's reverse map · a new edge enters C3's walk) — those checks revert to PARTIAL and the confirmation round re-works exactly them (a *cut* clause therefore un-shows the C1/C3 maps that cited it, and an *added* clause un-shows them too).

**Two classes of check.** C1–C5 (and every D/F check) are *evidence-capable* — a pasted map, a built consumer, a pointed-at AC can show them; there PARTIAL blocks like a should-fix, so nobody passes by not looking. **C6 is *evidence-incapable*** — "reads in one pass" has no finite positive proof, so demanding one only makes a reviewer invent grounds. For C6, **only FAIL blocks** (quote the line, name the misreading it causes); PARTIAL counts as PASS at judgment. **Comparative metrics are banned grounds** — length/density relative to siblings, or to the document's own longest line, manufactures a FAIL against any document (every document has a longest line; shrink it and the next line is the new longest). *(A real gate burned three of ten rounds on exactly this: a round with zero blocking findings failed on "one bullet is 1.6× the siblings' longest line"; two rounds later the same shape returned at a different line — while the round that finally PASSed measured a* worse *average density than the one that PARTIALed.)*

One list, six checks. Written for a `skeleton`; where a **leaf** (`feature`) differs, the **leaf:** clause says how (a leaf *pins* behavior, so its deferral tolerance is lower).

- **C1 Coverage — mechanical, *paste the map*** — enumerate the brief/parent scope items and map each to **exactly one** child role: **0 unmapped (gap), 0 double-owned (overlap)**. And the *reverse*: every Contract clause must trace back to a brief scope item — **a clause outside the brief's Does/Doesn't is scope-creep → flag it** (cut it, or revise the brief; the brief is the scope SSoT). Assert nothing; show the mapping. **leaf:** map the parent-contract clause this node fills + its Requirements onto its Contract·AC — every behavior it owns appears once, nothing double-owned with a sibling. *(coherence)*
  - **Actor & prerequisite closure — map the *nouns the rules lean on*, not just the scope items.** List every actor the spec names (employee · manager · admin …) and every entity/attribute its rules depend on (hire-date · team · rank · auth identity …); each MUST be *owned* by some child or the foundation. A noun the rules use but **no node creates/owns** is a gap — the source doc assumed it, the tree forgot it. Show the noun→owner table. **leaf:** those nouns must be *declared inputs/dependencies* (owned by a sibling·ancestor·foundation), not silently assumed. *(coherence)*
  - **Own structural deliverable — the skeleton must build *something itself*, not only delegate.** Check the AC/Subtasks (not the Contract): does *this* node build the glue/shell its children slot into? For the **root**, that is the **base environment + an empty runnable shell** (smoke-testable — boots / blank page / CLI runs). A **pure-delegation skeleton** — AC/Subtasks are only "grow child X", so `implement` would build nothing — is a **FAIL**; name it. (This is about the *deliverable*, not the Contract — the Contract still stays lean/deferred per C4.) **leaf:** n/a. *(coherence)*
  - **Ref fidelity — fill C1 in the packet.** The draft was written *from* the ref intent records, and every gate after this one reads the Task as its yardstick — so this is the one check that holds the yardstick against its source. Open every packet coordinate and read each clause in its machine-carried `heading` path; do not accept the caller's prose as a substitute. For every canonical clause id return `c1: carried|deferred|divergence|excluded|missing` plus, for `carried`, a **`c1_case` walk** — `<the condition the clause names> -> <what the Task's own lines then make observable>`. **`carried` is reachability, not presence**: walk the case from what the Task *takes* to what it *gives*, and check the line that **admits the case into the output** (the row set · the selection · the quantifier), not only the line that handles its topic. If a selection line excludes the case before the handling line could run, the disposition is `divergence` (deliberate, with the Change Log entry) or `missing` — **never `carried`**. The runtime refuses a `carried` with no walk. Plus `c1_basis`: `Contract:<n>` / `AC:<n>` for carried, an explicit `[→ child/deferred: ...]` Contract/AC line for deferred, `Change Log:<n>` for divergence, `adjudication:<n>` for excluded, or `finding:<id>` for missing. Numbers are 1-based non-empty logical blocks inside that named section. Never change or omit a roster row. `missing` is always a finding; PASS requires zero terminal missing rows. The state file keeps this bounded: `checks[C1].shown` records disposition counts + the round-brief packet pointer, and `basis` names that packet rather than claiming "all clauses." Bounds: only the packet clauses this node covers, never the whole ref; source `(gap)` candidates are already omitted from dispositions but remain bound by `source_digest`; the demand is presence-or-deferral — **never** "an AC that measures it" (that is C5's own bounded rule). An empty roster is honest only with the packet's own state: empty `scope` = intentional no-ref; non-empty `scope` = assigned headings whose candidates are all `(gap)`. **leaf:** this is where it bites — a leaf *pins* behavior, so a silently narrowed clause ships as missing behavior. *(coherence)*
- **C2 Buildability — show it** — name a consumer/child and *sketch building its part* from this contract alone; the only hole is a spot you'd be **blocked** (not one you'd reasonably decide). **leaf:** sketch building the leaf itself. *(consumer-impersonator)*
- **C3 Boundaries & invariants — fill C3 in the same packet.** Are the child boundaries + the cross-cutting invariants all children must respect stated? For **every** packet clause return `c3: handled|deferred|divergence|excluded|not-edge|missing` plus `c3_basis`. `handled`, deferred, divergence, excluded, and missing use the same exact anchor classes as C1; `not-edge` uses that clause's own exact `source` coordinate. A source-stated empty/none-set/failure case cannot become `not-edge`: only handled, an explicit deferral/divergence, a recorded exclusion, or missing is honest. At aggregation the main session joins C1/C3 by stable clause id: carried↔handled, deferred↔deferred, divergence↔divergence, excluded↔excluded; `not-edge` accepts any non-missing C1. A conflict leaves both checks PARTIAL and creates one finding. **leaf:** the standard edges (empty · not-found · failure · none-set) are answered *here* unless explicitly deferred **to implement** with a marker (a leaf has no children to defer to) — unmarked silence weighs heavier than in a skeleton. *(gap-finder, at THE BAR)*
- **C4 Scope discipline** — is mechanism/child-detail deferred (markers), not pinned? **An over-stuffed contract FAILs here** (too detailed for a skeleton → delegate). **leaf:** inverted — is anything here actually a parent's/sibling's job? (Rare.) *(breaker — hunt unbuildable holes AND over-reach)*
- **C5 AC testable** — is each AC measurable/verifiable (NFR as a checkable item)? **An AC states the result required, not the wrong implementations forbidden.** Coverage is judged by **consequence, not completeness**: what must be pinned is where a wrong answer reaches a person *as a plausible-looking value* — a silently wrong number, lost or corrupted state, a normal path wrongly passed or blocked. A promise no AC measures is a finding **only when breaking it produces one of those**; otherwise it caps at `nice-to-have`. **Never ask the AC to enumerate the implementations that must die** — that is *implement*'s job (tests first) and *review*'s (run the tests, compare to the AC), and those two read real code instead of imagining it. *(gap-finder)*
  - **Stop rule — the generator smell.** If a round's findings all read *"rule R isn't measured at spot P"* and the fix is to **widen a coverage rule inside the spec** ("measure every branch" → "…at every spot"), the spec has begun specifying its own test matrix: rules × outputs × sub-cases grows faster than rounds can close it, and each round's tail gets thinner. **Bound the rule instead of widening it** — each promise observed once, from what a consumer sees — and move mutation-killing to implement/review. *(A real node ran four rounds this way: three successive widenings each produced more empty cells than they closed, with 60+ left.)*
- **C6 Confirmable at a glance** *(evidence-incapable — FAIL-only, see above)* — readable in one pass; if a Contract is a dense wall, it's over-specified → FAIL. A C6 FAIL quotes the line and names the misreading it causes — never a length comparison. *(non-expert)*

## verify-tree — the decomposition checklist (D1–D5)
Runs on the whole **sketch tree** (at plan #0, and after a structural plan/`revise`), before any node is built — the cold gate on the *decomposition itself*. Same rule as the spec checklist: each lens marks **PASS / PARTIAL / FAIL** *with shown evidence*; an unshown check is PARTIAL, never PASS. Bounded because sketches are one-liners (a reviewer holds the whole tree at once).

- **D1 Source→node scope assignment — paste the map from `refs`.** Open every exact heading named by every Task's `refs` through current `ref/index.md`. Map each current in-scope ref behavior to ≥1 owning node, and every non-empty Task assignment back to behavior that node actually owns: **0 uncovered, 0 wrongly assigned, 0 unexplained overlap**. A heading may feed more than one node only when the sketches show the responsibility split; name that split. `refs: []` is valid only for an intentionally no-ref node (for example D2 system scaffolding), never an undecided source. A non-empty heading whose included content is all `(gap)` remains assigned scope — deliberately undefined is not no-ref. Also map each brief-only scope item to ≥1 node and every node to brief/ref scope: **0 scope-creep**. (C1, at tree scale.) *(coverage-mapper)*
- **D2 System completeness — the scaffolding the domain doc omits** — a real multi-user / rules-driven system almost always needs infrastructure the *source doc never mentions* (the doc describes the *domain*, not the *system*): **settings/configuration · admin & role management · audit log · org & user management · authentication · notification delivery**. For each: is it needed here, and is there a node for it? A needed-but-absent one is a gap — and the source doc *won't* list it, which is exactly why domain-coverage (D1) misses it and this lens exists. *(system-architect)*
- **D3 Prerequisite & actor closure — tree-wide** — every actor the system names + every entity/attribute its rules lean on (hire-date · team · rank · auth identity) is *owned* by some node. (C1's actor-closure, across the whole tree.) Show the noun→owner table. *(coverage-mapper)*
- **D4 Boundaries & shared-state ownership** — node responsibilities split cleanly (no two nodes own the same thing); each piece of *mutable shared state* (a balance ledger · the audit log · the calendar · the settings store) has exactly one owning node. *(boundary-checker)*
- **D5 Depth sanity — a one-liner hiding a subtree** — does any sketch *flatten real complexity* that should be its own decomposition? An approval *routing* that's actually org-chart-derived + rank-constrained; a *calculation engine* with overlapping rate rules. Name the node **and** the complexity it under-models, so grow splits it instead of discovering it mid-build. *(depth-breaker)*

(Readability is the **non-expert** lens: the decomposition must be confirmable by a human at a glance — flag undefined/duplicate node names, a tangle, or two nodes that are really one.)

## verify-tree fidelity — the survey checklist (F1–F4)
Runs **once per brownfield adoption**, on the mapped all-`done` tree, before any node work — the cold gate on the *survey itself*: the map is an agent's claim too, and every later `revise` computes blast radius by trusting these Contracts. **The criteria is the CODE** — every check is answered by reading (or running) it, never by the map's own say-so. Same rule as every checklist: PASS only with *shown* evidence; unshown = PARTIAL.

- **F1 Code↔tree coverage — paste the two maps** — every source file/module → an owning node, and every node → the real code it names: **0 unowned files, 0 code-less nodes**. *(coverage-mapper)*
- **F2 Contract↔behavior fidelity — sample and show** — pick the highest-risk nodes (entry points · shared state · the biggest), read their code, and check each sampled Contract states what the code *actually does*. A Contract promising what the code doesn't do — or a behavior consumers visibly rely on that no Contract names — is the finding: name node + clause + code line. *(code-reader)*
- **F3 No beautification** — the tree mirrors the real structure: a tangled module maps to a tangled node; shared state appears where it really lives. **A tree cleaner than its code is a falsified survey.** *(honesty-auditor)*
- **F4 Backlog honesty** — what the survey noticed as wrong is actually *parked* (findings/restructuring.md), not smoothed over. Spot-check the code for defects the backlog never names. *(honesty-auditor)*

(Fidelity spawns at most the `standard` lens count — a big survey rounds **up by widening F2's sample**, not by adding lenses.)

## Check assignment by level — every check always has a cold owner (verify & verify-tree)
**Invariant: every check (C1–C6 · D1–D5 · readability) is carried by exactly one spawned reviewer.** The level sets the reviewer *count*, never the checklist's *coverage* — an unowned check would sit PARTIAL forever and block every round (or invite passing by not looking).
- If a check's home lens (tagged in the checklist) isn't spawned at this level, **assign it to one of the spawned lenses** — any of them; the absorbing reviewer applies that check's criteria *as written in the checklist*, not its own lens's framing. What must hold is the count (**exactly one owner, never zero, never two**), not which lens gets it.
- `models[<lens>]` keys keep working — only spawned lenses are looked up.

Which lenses spawn (each level adds to the one above):

| level | verify (spec) | verify-tree (decomposition) | verify-tree (fidelity) |
|---|---|---|---|
| light (2) | consumer-impersonator · coherence | coverage-mapper · system-architect | coverage-mapper · code-reader |
| standard (3) | + gap-finder | + boundary-checker | + honesty-auditor |
| full (5) | + non-expert · breaker | + depth-breaker · non-expert | (capped at standard — widen F2's sample instead) |

(review/code has no checklist — its lenses spawn in fixed order, first *N*; its pass judgment is findings-based.)

## Role lenses — verify (spec) — spawned per the check-assignment table
- **consumer-impersonator** (C2) — *you are a node that will use this contract.* Try to write your code against it alone. A hole = a spot where you'd be *blocked* (can't pick a return shape / don't know who outputs what), not a spot you'd reasonably decide.
- **gap-finder** (C3) — walk the standard edges (empty · not-found · failure · none-set). Flag one **only if** the contract leaves a competent implementer unable to proceed on an *in-scope* case. A child-owned or deferred edge is not a gap.
- **coherence** (C1) — check against global rules + parent/sibling contracts. **(up)** does this node fill the clause its parent assigned it — and does the draft **carry, defer, or note every behavior the ref intent record states for this node's scope** (the narrowing map: a silently dropped/shrunk ref clause is the finding; show the pair)? **The narrowing to hunt is a shrunk *set*, not a missing topic**: the source says *all X* (or *X with no Y is still …*) and the draft answers *X that have Y*. That draft still discusses the topic — often correctly — so a topic-level read passes it. Walk each case against the draft's own row set. **(down)** if a skeleton, do its children's roles cover it cleanly (no gap/overlap), **and does every actor/entity the rules lean on (hire-date · team · auth identity) have an owning node**? — judged from the contract; the children are only sketches (their contracts aren't written yet), so check the decomposition, not their detail.
- **non-expert** (C6) — you don't know the jargon; the spec must be confirmable at a glance. Fail undefined terms, fluff, a dense wall, the same concept under two names. Quote the line.
- **breaker** (C4) — you came to break the contract *and* to catch over-specification. A break counts only if a named consumer is blocked; flag any mechanism/child-detail that's been pinned into the contract (it should be deferred).

## Role lenses — verify-tree (decomposition) — spawned per the check-assignment table
Each reads **the whole sketch tree (including every Task's `refs`) + brief + ref spec** (cheap — sketches are one-liners).
- **coverage-mapper** (D1, D3) — paste two maps: current ref heading/behavior + brief-only scope → node using the Tasks' exact `refs` (0 uncovered/wrongly assigned/unexplained overlap), and actor/entity-the-rules-lean-on → owning node. Treat explicit `[]` as intentional no-ref and keep all-`(gap)` headings distinct from it. A blank cell in either is the finding.
- **system-architect** (D2) — *you are deploying this for real.* What scaffolding does a live multi-user system need that the domain doc never mentions — settings, admin/roles, audit, org/user mgmt, auth, notifications? Name each one that's needed but has no node.
- **boundary-checker** (D4) — two nodes that own the same thing (overlap), or a mutable shared state with no single owner. Name the collision.
- **depth-breaker** (D5) — a one-line sketch that hides a real subtree. Name the node + the complexity it flattens (routing rules, calc overlaps, multi-step workflows), so grow splits it instead of discovering it mid-build.
- **non-expert** — the tree must be confirmable at a glance: undefined/duplicated names, a tangle, the same concept as two nodes. Quote the node.

Fidelity-only lenses (the survey gate — criteria = the code):
- **code-reader** (F2) — *you verify claims against the code.* Read the sampled nodes' code and compare each Contract clause to actual behavior; scale a big survey by widening the sample, never by trusting the map.
- **honesty-auditor** (F3, F4) — *you assume the surveyor wanted the map to look good.* Hunt beautification (a tree cleaner than its code) and smoothing (code defects the backlog never names). Quote the code that contradicts the map.

## Role lenses — review (code) — fixed order, first *N* = `review.scale[level].reviewers`
Each reads **only this node's diff + AC·Contract + test results**.
- **correctness** — does the diff meet the AC·Contract? Logic errors, off-by-one, wrong branch, broken invariant.
- **security** — injection, auth/authz gaps, secrets, unsafe defaults/deserialization/path handling — in this diff.
- **the-6-month-maintainer** — hidden coupling, surprises, and **duplication of code that already exists** (Principle 3 — did this reimplement something?).
- **breaker** — edge·failure inputs the running code mishandles. Same BAR: name the input → wrong behavior.
  > **What the code lenses can't see:**
  > - **Aesthetics · design direction · look-and-feel** — the diff carries no rendered output, so these are **human-confirm only** (implement's reversibility gate handles them up front; review does not re-check).
  > - **Security sees only this node's diff** — an exploit living in the *interaction* with unchanged code (a misused existing sanitizer, a bypassed existing check) is outside its read-scope. That bound is the deliberate cost trade; contract-level security invariants belong in `conventions.md` and are probed at *verify*.
- **test-quality** — are the tests *real* (exercise the path) or hollow/tautological? Every AC item backed by a passing test? A green-but-empty suite is a `should-fix` (or `critical` if it masks a failing AC).

> **A coverage finding must name its clause — review's Stop rule.** "The tests don't measure axis X" blocks only when the Contract/AC **names** X (an expected input · a promised output · a listed edge): cite the clause the missing test leaves unpinned, and fix with the *minimal* test for that clause, not a matrix. An axis no clause names is owed no test — raising it is over-reach (the triage drops it), and *writing* such tests is itself a finding (scaffolding beyond the contract → cut). Combinations follow the same line: a clause that promises behavior per-state owes its `axis-product` cells, but products of *unnamed* axes stay out of scope. This mirrors C5's Stop rule: the spec doesn't enumerate the implementations to kill, and the review doesn't demand tests beyond the contract — both cut off an infinite supply.

> **When the target is a rule someone else will implement, vary the implementations — not just the inputs.** A rule that demands a check ("the AC must carry a test that catches X") is satisfied by more than one test setup: which process it runs in, which environment it starts from, which import order, when it observes. Building *one* setup and finding it sound shows **that setup** works — not that the rule holds. Spread that axis before calling a round clean, and try first the setups a convention-following implementer would naturally reach for: those are where a rule stated as intent-plus-hints goes blind. *(A real round passed clean across 6 code forms × 4 run modes of a single setup; the next round spread the setup axis and found the rule's own recommended setup could not go red at all.)*

## Aggregate
Merge findings; dedupe by (where + what). On a severity clash, take the higher.

When two findings are the same underlying hole through different paths, collapse them to one record, give it one `family`, and keep the clearest `where`/`what`/`measured`.

## Over-strictness triage — the judge phase (mini-form at each confirmation)
Runs **once per cycle**, over the whole found list, when find closes — not per wave (a per-round defender re-buys the same drops every round). **The defender spawns at `standard` and `full`; at `light` (no defender) the caller applies these rules itself** — except dropping a confirmation finding, which always takes a cold defender (§The cycle 3). A confirmation round's new finds get the same gates in mini-form.

Set both the lane fields and the gate fields on every KEEP. For **result** reviews, only `kind: defect` may stay in `open_issues`; move `contract-gap` and `concern` to `followups`. For **spec/tree** reviews, `defect` and `contract-gap` may stay in `open_issues`, while `concern` still belongs in `followups`.

**`followups` has an entry bar — gate1 `behavior` or `mechanism`.** A keep whose gate1 is `contrived` or `story` is *recorded, not queued*: write it as an `adjudications` entry (`accepted-gap`, with its reason) instead of a followup. It re-enters only as live measurement — gate1 `behavior` or gate2 `yes` evidence always reaches a judge (the strike rule's own exception, unchanged). `grovespec validate` enforces the bar. (Why the bar sits at entry: METHODOLOGY §6.)

One more cold reviewer (the *defender*) rules each finding KEEP / DOWNGRADE / DROP / **UPGRADE** (fold a stronger submission attached to an entry into it — the strongest evidence and classification is what gets graded, so a hole first listed as a mere coverage gap and later reproduced live is judged as the live repro).
- **Drop, before scoring**: anything asking for mechanism or child-owned detail (out of scope by the SCOPE rule); anything failing the *name-the-victim* test; anything a competent implementer would reasonably decide; anything in the do-not-raise categories; duplicates.
- **Also drop "the child would stumble, so this node must build scaffolding for it"** — demanding ergonomics on behalf of an unbuilt consumer is the same over-reach as deciding *for* it.
- **Set the gate fields** (above) on every KEEP — `proposed` + `gate1`·`gate2`·`gate3` (+ `clause`·`workaround`·`harm` where the answer demands one). You are not choosing the level; the answers compute it, and `validate` will recheck your arithmetic.
- **Keep** only what a gate-honest reading survives. Rank them; blocking caps at 3.
- **Two strikes closes a shape.** When two findings fall to the same reason — same shape, new instance (a second length-comparison readability complaint · a second no-named-clause coverage demand) — write ONE adjudication at the *shape* level and add it to do-not-raise on the spot; a third instance is struck on sight, unargued. **Two bounds on the strike:** the shape is written **at the altitude of the two instances, no broader**, and it records *why* they fell (the reason profile — "contrived for this product", not just the topic); and an instance arriving with **gate1 `behavior` or gate2 `yes` evidence always reaches the judge** — a strike suppresses re-litigation, never live evidence. Pre-seeded banned shapes: comparative-metric readability grounds · coverage demands naming no clause.

Returns the confirmed list (with gate fields) + the do-not-raise additions.

## Cycle hand-off
If a phase surfaced real but non-blocking later work, record it in `followups` rather than forcing it into `open_issues` — when it clears the entry bar (gate1 `behavior`|`mechanism`, §triage); otherwise it is an adjudication, not a queue item.

> **The confirmation round's diff is assembled by hand — hold the gate records out of it yourself.** `grovespec diff` excludes everything under `paths.review`, but a confirmation pass is scoped to *the fix's own diff*, which no command derives. The fix commit rightly carries the round record it just updated, so handing that diff over raw shows the confirming lens the verdicts and dropped findings of the round it is confirming. Same blankness, same rule: pass the code, never the record.

Write `.grovespec/review/<id>.verify.yaml` (verify), `<id>.review.yaml` (review), or `tree.verify.yaml` (verify-tree) — template `review-state.yaml`. It holds:
- `phase` (find | judge | fix) + one `rounds[]` entry per spawned pass. **A round entry is the countable result, never the story of it**: `n` and `outcome` required, `phase` · `found` · `note` optional (`found` on judge/confirm passes only). The entry is **flat** — every field on one line at its own indent, `found` as a one-line flow map — and the pass's reasoning goes in its own file (`<id>.round<n>.brief.md` · `.judge.md` · `.confirm.md`) with a **one-line** `note` pointing at it. `validate` reads depth, so a block scalar, an indented paragraph and a nested mapping are each refused — and every list in the record is block style (a flow list is refused: it would turn each per-item check off instead of failing it). Unbounded, this is where the narrative actually moved in — 394 lines of it in one node — and every later cold session reading this file had to carry all of it;
- `found` (the raw find list, growing through the waves) + `strategies` (the ledger, with owners and the wave each ran in);
- `checks` (verify/tree: the C#/D#/F# table — per check `verdict` PASS|PARTIAL|FAIL, one-line `shown` evidence, its `basis`, the wave) — the accumulation's persistent home, and what a new session resumes find from;
- for a spec find round, its brief contains exactly one `grovespec-source-evidence/v1` packet generated **before** the cold reviewers from the Task-owned `refs`. The main session persists the exact immutable roster and merges only the C1/C3 disposition fields returned for every clause; `checks[].shown` carries their counts + packet pointer and `basis` names that packet. Before a C1/C3 PASS is persisted, join the two dispositions by stable clause id — an unset, unmatched, missing, or contradictory row is a finding, never prose to reconcile later. Terminal `grovespec pin TASK-N` recomputes the assignment, heading/context evidence, clauses, resolved Task basis content, and Task frontmatter before writing `spec_digest` + `task_evidence_digest`;
- for every tree pass, write `tree_evidence_mode: decomposition|fidelity` in the record before round 1. The complete read-scope above is machine-bound before human approval. `pin tree` stores `source_scope_digest` over D1's visible current catalog, canonical source material, tree order, and assignment state; an all-mapped/no-ref fidelity tree stays code-grounded through spec/result record creation but still observes catalog roster/material as a tripwire, while an actual ref assignment or non-mapped node activates ownership. `tree_evidence_digest` binds everything else the selected lens set read under the persisted mode: decomposition = tree + brief + every full sketch Task (on a built-tree re-verify, only id·name·Overview·`refs`); fidelity = tree + id·name·Overview·Contract + Git-visible src/tests + both backlogs. `approve tree` recomputes both current seals, and `validate` recomputes mode-specific evidence while the verdict is pending. A decided historical record without newer fields remains readable and is never backfilled; a pending legacy verdict cannot be approved, and any changed/partial current seal requires a fresh tree cycle;
- after judge: the verdict (the C#/D# table) + the confirmed `open_issues`;
- the triage's drops appended to `adjudications` — **handed itemized (claim + verdict + reason) to every later wave as the adjudicated list**, alongside the two-strike shape categories.

The next wave/round is a new cold session reading only this file. **Adjudications never leave it**: `reopen` preserves them across cycles — a settled call is a boundary ("don't re-raise"), not evidence, so a new cycle doesn't expire it; and a copy in the Change Log would reach the cold reviewers through the Task file. **One guard, both substrates**: on a `draft` reopen the contract changed — before condensing the kept list into do-not-raise categories, drop every entry whose written reason leans on the old contract (e.g. "the contract table has no such cell" after the table gained one). The **result twin**: on a `result` reopen the code moved — drop every entry whose written reason leans on code that no longer exists ("lock.js serializes it" after lock.js is gone). A reason that died with its substrate must not suppress a now-real finding; this is why every adjudication records its reason, not just its verdict.
