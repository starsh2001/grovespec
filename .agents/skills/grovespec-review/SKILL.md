# grovespec-review

Code review — the step that turns `implemented` → `reviewed` (→ `done` on a clean pass with nothing left to decide). (Verifying the *spec* is `grovespec-verify`.)

Two things, both bounded to **this one node**, so cost never scales with the codebase:
1. **Run the tests + analyse the results** — the deterministic spine. Did every AC-derived test pass? Any AC item with no test? Any measurable NFR target (in the AC) unmet?
2. **Cold code review of THIS NODE'S DIFF only** — a few fresh-eyes reviewers inspect just the diff, with code roles. **Not the whole codebase, not other nodes' code.** This catches what tests can't see (security, hidden coupling, a hollow test).

> review never re-asks *spec* questions ("is the contract complete?") — `grovespec-verify` settled those cold, before any code. Here the spec (AC·Contract) is the *yardstick*, not the subject.

> **Language: read it first.** Read `language:` from `.grovespec/config.yaml` (or `node .grovespec/bin/grovespec.mjs lang`) and write **every** reply in that language (the reviewers' findings too). These files are English; your output is not.

## What it takes in
- **the node** — *if none is named*, take an `implemented` or `fixed` node `grovespec check` reports ready (next step = review). **Claim it:** `node .grovespec/bin/grovespec.mjs claim TASK-N review` — non-zero = **stop** and report what it printed.
- **what you review** — its **diff** + its **AC·Contract** (the criteria) + the **test results**.
  - *The diff, mechanically*: **`node .grovespec/bin/grovespec.mjs diff TASK-N`** computes it — the cycle's `TASK-N:` commits, their file set, and the base→working-tree diff (cycle definition: `FORMATS.md`). **Never assemble the diff by hand** — a hand-assembled diff misses files, and the cold reviewers then review the wrong subject without anyone knowing. It holds the cycle's own gate records out (counted, not named); if a round asks what a held record said, that question is the cold premise breaking — answer it from the Task file, not the record.
- `test` command + `find_streak`·`plan_streak`·`max_rounds`·`scale` from `.grovespec/config.yaml` `review:` (overridable per node).

> **Where it runs (the invocation contract).** Run grovespec-review in your **main agent session** — it spawns the cold reviewers as **subagents**. **Never run a grovespec skill *as* a subagent** — then it can't spawn reviewers and silently degrades to a non-cold self-check. Each reviewer gets one spawn prompt and returns one result — **no queue-only messages after the spawn**; before each wave, residents of the previous wave are cleared from the host's agent list, and a refused spawn is a capacity gap only when no such resident explains it (`reviewers.md` §Spawning).

## State
Result reviews have two finding lanes, split by **category** (`reviewers.md` §Categories — fixed handling, no severity to argue):
- `open_issues` holds the **must-fix** findings in the current diff (crash · requirement-unmet · normal-use-bug · easy-abuse · security-hole) that keep this code gate open. The fix phase works them **one at a time**.
- `followups` is the **record list**: `improvement` · `harmless-bug`, plus a must-fix that belongs to another gate (`kind: contract-gap`). It is never an automatic work queue — nothing here re-enters the build without the user's pick (`validate` enforces the lane split).
- Every open finding needs `kind` + `family` + `category` + `condition`/`impact` (and `requirement` for requirement-unmet). The same `family` may appear only once across `open_issues` + `followups`.
- If the flaw is in this cycle's diff or in the text this cycle is reviewing, classify it as `kind: defect` even if the eventual repair also needs a later spec/contract revise. Do not move a current-target defect to `followups` just because a spec edit would also help.

`.grovespec/review/<id>.review.yaml` (template `review-state.yaml`, `target_type: result`). Separate from verify's `<id>.verify.yaml` — they never collide.

> **Quoted record values stay one strict-YAML line** — in `"…"` write `\` as `\\` and `"` as `\"`; in `'…'` double the `'` (`''`). `validate` notices breakage (`FORMATS.md` "review-cycle state").

## 1. Run the tests (the spine)
Run **`node .grovespec/bin/grovespec.mjs test TASK-N`** — it executes `config.review.test` and records the exit code + log into the node's review state (`last_test` + `<id>.test.log`), so *"the tests passed" is a machine-written fact, not your reading of scrollback*. Your job here is the interpretation (the AC mapping below), not the bookkeeping.
- **Empty?** (greenfield leaves it empty at init — there was no stack yet) → **derive it from the stack/project** (`pytest` for Python, `npm test`/`node --test` for Node, `cargo test`, a `Makefile` target, …), **write it back to `config.review.test`**, then run `grovespec test TASK-N` again. **Ask the human only if you genuinely can't tell** (no clear runner, or several equally-plausible ones) — and then as a *"이게 맞아?"* confirm with your best guess, never a blank "what's your command?".
- **Map the results to the AC — the gate's own evidence duty, finite by definition, with two deadlines.** Every non-`(gap)` AC item needs **a runnable test that observes it** (items marked `(gap)` are excluded — deliberately undefined behavior, `FORMATS.md`). This duty is **the gate's, not a finding**: it never enters `open_issues` and never spins the per-item fix loop. Its two deadlines: **present before find opens** — name the AC item and the missing observation, add the *minimal* test for exactly that item, and correct a test whose *expectation* is wrong (asserting what no requirement says — distinguish that from a product defect), all here at the spine so the first cold wave sweeps final bytes; **passing before the terminal pass** — a test red because the *product* is wrong is not a duty violation but find's evidence (below), and the gate seals only once its item's test passes. And the duty is **satisfied once, finally, for the cycle**: an item whose minimal test exists and passes owes nothing further — a surviving mutation, an untested combination, or future-regression worry never reopens it (those classify as `improvement`, §Categories); only the AC text itself changing (revise) re-arms it. The mirror of the spec checklist's rule: you can't pass by not looking — and you can't be made to keep looking after you've looked.
- **Measurable NFR targets** in the AC (e.g. `p95 < 200ms`) are checked here too. A target with **no runnable check** (no bench/load tooling behind the test command) is marked **unverified** and put to the person as a decision at the close (§3) — never silently counted as met.
- A **red suite splits on one line: can it run at all?**
  - **The suite cannot execute** (import crash, harness abort — nothing is measurable): this is the one fix that *precedes* find, because a target nothing can measure gives the cold waves nothing. Write it as the `crash` item it is (`open_issues`, `status: reviewed`) and hand to `grovespec-fix` — its per-item loop applies as ever; when the suite executes again, the cycle enters **find** on the repaired bytes.
  - **The suite runs and assertions fail**: **find opens anyway — the failure is its first evidence.** First split test-fault from product-fault: a test asserting what no requirement says is corrected **at the spine, before the first wave** (the duty's "present" deadline above; record an `improvement`). What remains red because the *product* is wrong freezes as it is — classify each by cause (`reviewers.md` §Categories: an AC-derived test red → `requirement-unmet`, cite the AC line · a wrong result on an ordinary path → `normal-use-bug`), put the must-fix causes in `open_issues`, and run the waves over the red state; the fix phase closes them per item like any other, and the suite goes green there — before the terminal pass, never as find's entry fee. No fix-first shortcut: sweeping the red state is the point of freezing it.
- **`tdd: false`** node (no tests): note it; this review leans entirely on the cold diff review below — the *only* gate available — the AC-evidence duty above does not apply, and the unmet AC items stay unchecked (reported under *Open* at the close — that choice was made with the node, in `tdd_skip_reason`, and is not re-asked).

Spine settled (suite runs; every non-`(gap)` AC item observed by a runnable test; what stays red is a classified product fault) → go to the cold review.

## 2. Cold code review — the diff only
Scale the reviewer count per wave by the diff's size·risk (`config.yaml` `review.scale` — the SSoT; never restate a number here). When ambiguous, round **up**.

| level | when | review |
|---|---|---|
| `skip` | trivial diff (format·comment·≤2 lines) · a judged-touched candidate whose implement showed the verdict wrong — empty diff (below) | tests only, no reviewers |
| `light` | small diff, no new behavior | cold reviewer waves (count from `review.scale`) |
| `standard` | a normal node's implementation | cold reviewer waves |
| `full` | security-touching / large / contract-bearing diff | cold reviewer waves |

`skip` collapses the cycle, it doesn't skip the record: the caller self-checks the AC mapping, writes the state file itself (one `rounds[]` self entry; `found`/`strategies` may stay empty), and pin/validate/approve run as usual.

> **A judged-touched candidate.** A consumer reopens only after the recheck step judged its origin's contract change REACHES it (grovespec-recheck) — the reach question was settled there and is not re-litigated here. Its implement starts from the named reached use and the normal scale rules apply to its diff; when implement can show the verdict was wrong (the use is not actually reached), it says so, enumerates the use-sites as evidence, and the empty diff reviews at `skip` — an empty diff gives a cold lens nothing to read but evidence prose, and grading prose is not reviewing code. (Why the lane exists and its measured cost: METHODOLOGY §6.)

> Spawn mechanics, the reviewer prompt bodies, findings format, **§The cycle + §Categories + §Classification**, and §Search strategies are in `references/reviewers.md`. Use the **code lens set** in its fixed order: correctness · security · the-6-month-maintainer · breaker · test-quality (take the first *N*). Each reviewer reads **only this node's diff + the AC·Contract + the test results** — never the wider codebase or other nodes.

Run the cycle — **find → fix** (`reviewers.md` §The cycle):
- **find** — cold waves over the diff, *frozen*: nothing is fixed between waves, so every wave reads the same bytes. Each wave gets the lens set + a **search strategy** earlier waves didn't run + the **found list** (*don't re-report; find what's not on it*). **Classify each wave's finds at that wave's boundary** (`reviewers.md` §Classification — category + lane on every keep; run `validate` as you write them). Count the streak **per completed wave**: a NEW must-fix finding (or a record item promoted by new must-fix evidence) resets `no_new_streak` to 0; a completed wave with no new must-fix and no unresolved candidate advances it — **a wave of nothing but re-finds and improvements is a quiet wave**; an unresolved candidate holds the count. Close when **`no_new_streak` reaches `find_streak` (N, config)** — the confirmed `open_issues` is the fix list.
  - **A "the tests don't measure X" finding must name the Contract/AC clause that names X** (`reviewers.md` — review's Stop rule); a coverage demand with no named clause is struck, a mutation-only gap is an `improvement`, and tests beyond the contract are themselves a cut.
  - Must-fix items confirmed → `status: reviewed`, hand to **`grovespec-fix`**. **None → the cycle passes now** (no extra lap — the recall duty was paid by the streak of differently-armed waves).
- **fix loop** — `grovespec-fix` closes the list **one item at a time**: plan → cold plan review (`plan_streak` consecutive clean) → apply → ONE cold confirmation scoped to that item's own diff + its use-sites. A failed confirmation returns to that item's plan; an out-of-scope discovery becomes its own item (must-fix) or a record entry — the current item never silently widens, and find never re-opens. **Every item closed → terminal pass** (each item's own confirmation already was the check; there is no batch re-review).
- **Record-only floor** — when everything left is `improvement` / `harmless-bug`, the gate **passes**: those are recorded, never blocking. §1's evidence duty must be met at both its deadlines — every non-`(gap)` AC item's test was present before find, and by now (the terminal) it **passes** — that duty is the spine's, not a finding this floor weighs.
- **A node whose own test scaffolding grew this cycle is a smell** — helpers·fixtures added to defend the node's *tests* rather than its behavior are to **cut**, not to review deeper.
- `round` (find waves + plan reviews + confirmations) exceeds `max_rounds` → `status: escalated`, issues to the human, **not** done. Reaching the budget is never a pass, and the budget is never quietly raised to avoid escalating.
- **Raising `max_rounds` requires naming what the next round would *learn*.** Can't name it → escalate or close; not one more round.

## 3. Verdict
Lane outcomes in this step:
- Must-fix items (`kind: defect`) stay in `open_issues` and send the node to `grovespec-fix`.
- The record list (`followups` — improvements · harmless bugs · routed contract-gaps) never keeps a result gate open, and never becomes work by itself.
- A clean pass may still carry `followups`; surface them to the human and keep them visible, but do not hold `done` on them — and do not queue them.

- **Must-fix items remain** → `status: reviewed` with `open_issues`; next is **`grovespec-fix`** (per-item loop → `fixed` → re-run `grovespec-review`). review does **not** fix — the diff stays the cold reviewers' subject, and fixing needs no independence (cold already gave that). **This is the whole verdict for confirmed must-fix items, in auto mode too** — never `escalated`, which says only that `max_rounds` ran out (`validate` refuses that word inside the budget). A classification that confirms five items has produced a normal fix queue, not a question for the human.
- **Clean terminal pass** (tests green + the cycle closed: find's streak met, every confirmed item closed with its own clean confirmation) → **seal it**: `grovespec pin TASK-N` (reviewed commit + spec/Task digests, verdict pending; it refuses uncommitted reviewed project input outside this gate's Task/evidence); then run **`grovespec validate`** (must pass — a format/evidence violation blocks `done`) and **`grovespec fresh`**; close with the result + test summary + any fresh signals — **in their words, not the cycle's** (`FORMATS.md` "The step report": no bare codes or round numbers at the person, a plain gloss on any GroveSpec term). **A clean pass with nothing to decide asks for nothing** (`FORMATS.md` *A decision, not a stage*): a person's confirm of a result that passed its tests and its cold review inside the agreed AC is a stage approval, never asked. What *is* theirs is asked **before `pin`**, in the four-part shape (the issue · the options · each option's impact · the recommended one): a measurable target with no runnable check (accept it unverified, or add the check — each with its cost), and any requirement the gate could only pass by narrowing; in auto mode the recommended option is taken and recorded, and a question with no defensible recommendation stops in every mode. A `tdd: false` node's unobserved AC and the fresh signals go under *Open* — not decisions here (the first was made with the node; the second routes to plan at the terminal). **Then take the gate in this same turn** — after the gate commit below, run `node .grovespec/bin/grovespec.mjs approve TASK-N`: it re-verifies the seal against the current committed and working bytes, including the pending Task frontmatter, requires the bound green test run, and flips `status: done` with `approved_by: machine` — the cold verdict on the record, never counted as the person's confirm; `status` names it until they `ratify`. Add one Change-Log line saying the machine took it, and commit those bytes as **`approve TASK-N: <summary>`** (`FORMATS.md` "Commits" — the decision turn's own commit, after the gate commit, never folded into it). Done is not a step of its own: a record left sealed but untaken is only what an interrupted turn leaves behind, and `grovespec next` names this same command for it. A person in the session who says they have looked is a different thing: **`grovespec approve TASK-N --human`** — their look, recorded as theirs (it replaces the machine's test evidence, not the byte binding). **Never hand-edit the status.** The surviving `adjudications` stay in `<id>.review.yaml` — `reopen` preserves them across cycles, so a later cycle's cold rounds read them there instead of re-litigating. **Don't copy them into the Change Log**: the reviewers' criteria come from the Task file, and a Change Log carrying verdicts breaks the blankness it feeds.

**Commit the gate as `review TASK-N: <summary>`** — the Task file's status flip *and* the evidence: `<id>.review.yaml`, this cycle's round files, `<id>.test.log`. An **escalate** stop commits the same way (`review TASK-N: escalated — …`): an escalated record is exactly the evidence a human ruling will read, and `validate`'s untracked notice only watches *passed* records — nothing else would name it. Step name first, so the gate commit stays out of the code cycle's `^TASK-N: ` anchor (`FORMATS.md` "Commits"). This is the exact spot where a result record was left untracked for a whole run — `validate` names it until it is in.

## When it's done
On `done`: the node's tests pass, its diff is cold-reviewed clean, and the gate was taken on the record (the machine on the cold verdict — or a person who looked, by `--human` or `ratify`). A `done` skeleton's children can now be grown (`grovespec-grow`); a `done` leaf ends its branch.

> **Open and close in the step-report shape** (`FORMATS.md` "The step report" — a `## … starting` heading to open; `### Result · Open · Your turn · Next` headings to close, warm full sentences). Here, *Open / Your turn* typically carry: open issues · an escalation · fresh signals · unverified NFR targets.

> **Recommend a new session for the next node** (`grovespec-grow` the next sketch). Each node starts fresh — clean, bounded context is what keeps GroveSpec's cost flat as the tree grows (WORKFLOW §5). *(Driving with `grovespec next` in a loop? `@new` already starts that session — this recommendation is for a person going step by step, and it is never a reason to end the loop.)*
