# grovespec-verify

Cold verification of a node's **draft spec** — the step that turns `draft` → `approved`. (Reviewing *code* is `grovespec-review`.)

The leverage: spend the multi-persona scrutiny *here*, on the spec, before any code exists. A contract or decomposition error caught now costs nothing; caught after building, it costs the build. **This is the one place the cold persona review lives for a spec** — code review (`grovespec-review`) does *not* re-ask spec questions.

## Two scales: the node, and the whole tree
verify is the cold gate at **two scales**, same engine (`reviewers.md`), different target:
- **`spec` — one node's draft** (the common case): `grow` detailed a sketch into a draft contract; verify cold-checks it (**C1–C6**) → `draft` → `approved`. Everything below is written for this.
- **`tree` — the whole tree** (at plan #0, after a structural/source-assignment `plan`/`revise`, and once per brownfield adoption): **two questions share the target**, picked by the tree's state (`grovespec next` names which). A **sketch tree** gets the *decomposition* question (**D1–D5**) — *is anything missing · mis-bounded · hiding a subtree, and is every current source heading assigned to the right node(s)?* — before any node is built. A **pristine mapped (brownfield) tree** gets the *fidelity* question (**F1–F4**) — *is the survey an accurate photograph of the code?* — criteria = the code itself, before any node work.
  - It catches what the producing agent and a human glance miss: system scaffolding the domain doc never mentions (settings·admin·audit·org-mgmt), a naively-flat feature, an actor nobody owns.
  - Clean pass + human approval → the tree is cleared and the per-node build begins.

The mechanics below (cold subagents, THE BAR, categories, the streak, the per-item fix loop) are **identical** for both scales; only the **lens set + checklist** differ (spec → C1–C6 spec lenses; tree → D1–D5 decomposition lenses), both in `reviewers.md`.

> **THE BAR — *sufficient*, not exhaustive.** A flaw is real only if a **competent implementer/child** would be **blocked or build the wrong thing** — *name who, and on what decision*. **It cuts both ways:** a check PASSes only when a reviewer *shows* it holds — "found nothing" is **not** a pass. *Lenient on imagined edges; strict on shown sufficiency.* Both directions are needed here — both live in step 2 (judge). **The SSoT for both is `reviewers.md` — §THE BAR (full text) and §SCOPE (what a spec may and may not contain, incl. what a skeleton defers). Load them; don't restate them here.**

> **Language: read it first.** Read `language:` from `.grovespec/config.yaml` (or `node .grovespec/bin/grovespec.mjs lang`) and write **every** reply in that language (the cold reviewers' findings too). These files are English; your output is not.

## Why cold · several · different
An open-ended "just review it" gets rubber-stamped, and exhaustive flaw-hunting never converges. So we stack: ① cold reviewers (didn't see how it was written), ② *different* roles **and differently-armed waves** (§Search strategies), ③ *several* in parallel, ④ each **filling a bounded checklist at THE BAR** (not open hunting), ⑤ every wave's finds **classified by category at that wave's boundary** (fixed handling — no severity to argue), ⑥ fixes applied one item at a time and confirmed against their own edits — then a human approves. Find ends on **`find_streak` consecutive waves confirming no new must-fix** (with the checklist fully worked); fix ends when the confirmed list is closed.

## What it takes in — auto-routing
When invoked *without an explicit target*, **decide tree-vs-spec automatically**:
1. Check: is a **tree gate armed** — `sketch` nodes (→ *decomposition*), a pristine mapped tree straight from brownfield init (→ *fidelity*), or an undecided `tree.verify.yaml` carrying an explicit `tree_evidence_mode` from `reopen tree`? `grovespec next` names which. → **`tree` mode**, with the matching checklist (D1–D5 / F1–F4).
2. Otherwise → **`spec` mode**: run `grovespec check` and take an unblocked `draft` node (lowest id if several).
3. An explicit target overrides: `verify TASK-N` → spec; `verify tree` → tree.

**Claim before round 1:** `node .grovespec/bin/grovespec.mjs claim TASK-N verify` in `spec` mode, `claim tree verify` in `tree` mode (`approve tree --human` ends that one) — non-zero = **stop** and report what it printed.

- **`spec` — the node** (`target_type: spec`). Criteria: the parent's **Contract** + the decomposition clause this node must fill + **the original ref intent headings assigned in this Task's `refs`** + `conventions.md`. Run `grovespec source TASK-N` with no coordinates: the runtime reads/validates that assignment, proves it is current through `ref/index.md`, and turns it into the canonical source-evidence packet. Reviewer-written summaries are navigation only, never criteria.
- **`tree` — the whole sketch tree** (`target_type: tree`). Criteria: the **brief** + the **ref detailed spec** + every Task's structured `refs` assignment (the source→node map the tree must cover). Brownfield fidelity remains code-grounded; its mapped Tasks carry explicit `refs: []`.
- `find_streak`·`max_rounds`·`scale` from `.grovespec/config.yaml` `verify:` (the tree review reuses these — for a big tree, round the level **up**).

> **Where it runs (the invocation contract).** Run grovespec-verify in your **main agent session** — it spawns the cold reviewers as **subagents**. **Never run a grovespec skill *as* a subagent** — then it can't spawn reviewers and silently degrades to a non-cold self-check, defeating the point. Each reviewer gets one spawn prompt and returns one result — **no queue-only messages after the spawn**; before each wave, residents of the previous wave are cleared from the host's agent list, and a refused spawn is a capacity gap only when no such resident explains it (`reviewers.md` §Spawning).

## State
Spec/tree verify files use the same category lanes (`reviewers.md` §Categories):
- `open_issues` may hold `kind: defect` or `kind: contract-gap` — must-fix categories only. At spec altitude that is `requirement-unmet`: a user requirement omitted, contradicted, silently narrowed, or a decision this node owns left unbuildable — **never a demand for execution evidence from code that doesn't exist yet**.
- `followups` is the record list (`improvement` · `harmless-bug`, or a routed contract-gap); `kind: concern` lives there. It is never an automatic work queue.
- Every open finding needs `kind` + `family` + `category` + `condition`/`impact` (and `requirement` for requirement-unmet), and the same `family` may appear only once across `open_issues` + `followups`.
- If the flaw is in the text under review right now, keep it as `kind: defect` even when the eventual repair also needs later revise/verify work elsewhere.

> **Quoted record values stay one strict-YAML line** — in `"…"` write `\` as `\\` and `"` as `\"`; in `'…'` double the `'` (`''`). `validate` notices breakage (`FORMATS.md` "review-cycle state").

`.grovespec/review/<id>.verify.yaml` for a node (`target_type: spec`), or `.grovespec/review/tree.verify.yaml` for the whole tree (`target_type: tree`). Template `review-state.yaml`. Round 1 creates it; a new tree record **must write `tree_evidence_mode: decomposition|fidelity` before the first round**, matching the question `grovespec next` selected. A reopened tree already carries that marker from `grovespec reopen tree …`; preserve it. Later rounds update the record in place so rounds accumulate. (Code review keeps a **separate** `<id>.review.yaml` and `<id>.review.round<n>.*` round files; they never collide.)

## Depth scales with reach
verify picks the level from checkable inputs — ① does it change a contract other nodes **already use** (a new node's first contract changes nothing anyone uses) ② how many nodes consume it ③ is it a skeleton ④ does it touch security. The reviewer **count per wave** lives in `config.yaml` `verify.scale` (the SSoT — never restate a number here). A new node is `standard` unless ②–④ say otherwise.

| level | when | review |
|---|---|---|
| `skip` | trivial spec edit (format·comment) | self-check only, no reviewers |
| `light` | small, contract unchanged | cold reviewer waves (count from `verify.scale`) |
| `standard` | a normal new node | cold reviewer waves |
| `full` | an already-used contract changes / 3+ consumers / a skeleton / security-touching | cold reviewer waves |

`skip` collapses the cycle, it doesn't skip the record: the caller self-checks against the checklist, writes the state file itself (one `rounds[]` self entry; `found`/`strategies` may stay empty), and pin/validate/approve run as usual.

For every **spec** find round (including `skip`), create that round's brief first and run **`node .grovespec/bin/grovespec.mjs source TASK-N`**. Paste its stdout fence **once, unchanged** into `<id>.round<n>.brief.md`. The command derives scope from Task `refs`; coordinates supplied on the command line are only an optional assertion and must match the derived canonical list exactly — they never override it. It rejects invalid/non-current headings and a non-mapped legacy Task with neither `refs` nor an explicit `ref/<file> §N` citation. It is the immutable roster C1/C3 must account for; do not hand-build or summarize it. Explicit `refs: []` produces an intentional no-ref packet. A non-empty assigned heading containing only `(gap)` clauses produces an empty clause roster but retains its non-empty scope and heading/context evidence; never collapse the latter into no-ref.

## The cycle — find → fix
> Spawn mechanics, the reviewer prompts, **THE BAR + the SCOPE rule**, the findings format, the **checklist (C1–C6 for a node · D1–D5 for the tree)**, **§The cycle + §Categories + §Classification**, and §Search strategies all live in the sibling `../grovespec-review/references/reviewers.md` — load it and use the **spec lens set** (`spec`) or the **decomposition lens set** (`tree`).

1. **find — cold waves over the frozen draft.** Nothing is fixed between waves, so every wave reads the same bytes. Spawn a wave of cold reviewers in parallel (subagents, empty context), as many as the level sets — for `spec`, the spec lenses; for **`tree`**, the decomposition lenses filling **D1–D5**. Which lenses spawn comes from `reviewers.md`'s **check-assignment table**, whose invariant is that every check still has exactly one cold owner.
   - **Give each**: the target + criteria, **THE BAR**, the **checklist to fill**, the **do-not-raise list** (settled claims + user exclusions from `adjudications`), the **found list**, the **strategies already run**, and — for a spec — the **entire exact source-evidence packet** generated for this round. Never send excerpts. Every reviewer opens the packet's original coordinates itself. Do not replace them with a summary made in this session; if a source cannot be opened, its check remains PARTIAL.
   - **Never give**: how it was built, any author reasoning, or a clean-claim ("this part is verified").
   - **Aggregate + classify** each wave into the C#/D# table and the found list at that wave's boundary (`reviewers.md` §Classification) — category + lane on every keep, strikes to `adjudications`, no fixes yet. For a spec, the C1 owner returns only `c1`/`c1_case`/`c1_basis` and the C3 owner only `c3`/`c3_basis`, once for **every packet clause**; all immutable fields stay byte-for-byte as generated. Merge those five fields into the one packet in the round brief. A `carried` owes its **`c1_case` walk** (`<condition> -> <observable>`) — the runtime refuses one without it, because `carried` means the case *reaches output*, not that the topic appears somewhere (`reviewers.md` C1). `missing` gets a real `finding:<id>` now, never a blank row. Before recording either check PASS, join C1/C3 by the packet's stable clause id; a missing or contradictory disposition becomes one finding. **Evidence accumulates**: a check shown in an earlier wave stays shown (the bytes didn't move); later waves work what's still PARTIAL, armed with a strategy the earlier waves didn't run.
   - **Count the streak per completed wave**: a NEW must-fix finding (or a record item promoted by new must-fix evidence) resets `no_new_streak` to 0; a completed wave with no new must-fix and no unresolved candidate advances it — **a wave of nothing but re-finds and improvements is a quiet wave**; an unresolved candidate holds the count. **Close find** when the checklist is fully *worked* (every evidence-capable check shown or FAILed into a finding) **and `no_new_streak` reaches `find_streak` (N, config)**.
2. **The verdict follows the classification — nothing is re-graded at the end.** `(gap)` rulings happen here, before fixing — for gaps the waves newly surfaced (one grow already knew was asked there), each a decision in the four-part shape (§Closing the gate). Run **`grovespec validate`** (it enforces the category lanes).
   - **Record-only floor**: everything left `improvement` / `harmless-bug` / deferred / out-of-scope → **PASS**, *provided every evidence-capable check (C1–C5 · D · F) is affirmatively shown*. **C6 blocks only on FAIL** (`reviewers.md` §checklist — PARTIAL counts as PASS there); an unshown evidence-capable check still blocks like a must-fix, so you can't pass by *not looking*.
   - **Empty `open_issues` AND every evidence-capable check still affirmatively shown → the cycle passes now**: seal it (step 5) — no extra confirmation lap. If a check's only *worked* status was a FAIL whose finding was then struck, that check reverts to PARTIAL — **reopen find for it** instead of passing: an empty list earned by dropping the evidence is not a pass.
3. **fix — one item at a time, cut-first.** Work the confirmed list item by item — for each: state the intended edit and why it removes the item's cause (a sentence or two — a spec fix's plan is that small), apply it, then confirm it (step 4) **before starting the next item**. Never apply the whole list and review the pile. **`plan_streak` (M) is deliberately not spent here** — it is a result-cycle knob (`reviewers.md` §The cycle): a document edit is cheap, and each item still gets its own cold confirmation. This step's default is *subtract*.
   - **Prefer DEFER/CUT over ADD.** For an unspecified detail, add a **deferral marker `[→ child/deferred: …]` or cut** — not a new clause. Add a clause *only* for a genuine in-scope structural gap (C1–C3). A deferral points **down only** (own child/implement — `validate` flags a non-child name); a detail **another open node** must define is a **wait**: `node .grovespec/bin/grovespec.mjs wait TASK-N TASK-M <need>`, the same fact as a Change-Log line, commit as `verify TASK-N: waiting — …` (the ledger rides along), and **stop — the cycle freezes**; `next` returns the turn. On resume read the counterpart's entry first (`grovespec wait`) and `wait resolve` what got answered; your own question coming back means the answer exists nowhere yet — decide it (this node's domain) · ask the human · or `grovespec-revise` (tangled boundary). (Why: METHODOLOGY §6.)
   - **A skeleton Contract that grew this round is a smell** — the root should get *leaner*, not more detailed (over-specification is itself a C4/C6 FAIL).
   - **Never let a spec grow a rule about how its own AC must be written.** A coverage rule ("measure every branch · at every spot") is a *generator*: it multiplies out and every later round finds new empty cells. If this round's fix is *widening* such a rule, that is the smell — bound it instead (`reviewers.md` C5 **Stop rule**), and leave killing wrong implementations to implement/review, which read real code.
   - **`(gap)` AC items** (spec-silent spots grow marked — `FORMATS.md`): an in-scope gap on a leaf is a real finding — resolve it with the user into behavior, or rule it `accepted-gap` with them: the item then *stays* `(gap)` (consumers should see what's undefined), the adjudication reaches the Change Log at approve, and later rounds don't re-raise it.
   - **`spec` mode at `full` only — prune `conventions.md`.** Every node reads it and only `implement` ever appends, so it is the one project doc that grows unbounded. Cut entries this node's contract makes **redundant · contradicted · obsolete**, plus any node-local implementation detail that leaked in. **Cut only, never add** — recording a *new* cross-cutting rule is `implement`'s job. (Not in `tree` mode: there is no "this node", and at init `conventions.md` is empty or freshly seeded.)

   Fixing in this main session is fine — the confirmation round is cold either way. A Task edit changes `spec_digest`: re-run `grovespec source TASK-N` so the same Task-owned `refs` scope is derived again, replace only the packet's generated immutable fields with that current skeleton, and have the cold confirmation re-fill/re-confirm every disposition whose Task basis moved. The terminal packet must describe the current Task bytes; copying an old digest is not evidence. Changing `refs` is not a local fix: it changes the source→node map, so return to plan/revise; for an already approved tree they run `grovespec reopen tree decomposition` before the explicit tree verify.
   - **The class isn't yours to bend.** Each confirmed finding carries its `category` + `condition`/`impact` (+ `requirement`), and **`grovespec validate` enforces the lanes** — a record category cannot sit in `open_issues`, and a bare must-fix cannot hide in `followups`.
4. **Confirm each item — one cold round, scoped to that item's own edits.** After an item's edit lands, spawn one cold confirmation on **the edit + the item it claims closed + the clauses that use what it changed** — not the whole draft again: did the edit close its item (re-run the finding's own measurement)? did it open a new hole *in what it touched*? do the checklist rows the edit touches still hold? A failed confirmation returns to that item's edit — name first whether the cause was mis-read, the symptom merely reworded, or the edit itself wrong. A confirmation reviewer who stumbles onto a real problem outside its scope still reports it — classified like any find: a new must-fix becomes its **own** item, worked after this one; record-only finds go to `followups` (`reviewers.md` §The cycle). Its *assignment* never widens beyond the edits, and find never re-opens. **Every item closed with a clean confirmation ends the cycle.**
5. **On the terminal pass, seal it**: `node .grovespec/bin/grovespec.mjs pin TASK-N` (spec) or `pin tree`. A new spec cycle's `pin` opens exactly the highest `rounds[]` find brief and machine-checks its one packet against the current Task `refs`, resolved heading/context bytes, `ref/index.md`, exact field roster, C1/C3 compatibility, and resolved Task basis content; it also binds the Task frontmatter as `task_evidence_digest`. `UNSET` or terminal `missing` refuses with no write. Tree `pin` binds (a) parsed structure + the visible current catalog, canonical source material, and every assignment as `source_scope_digest`, and (b) the complete mode-specific input the tree reviewers just read as `tree_evidence_digest` under the cycle's already-written `tree_evidence_mode`: decomposition = brief + full sketches (built Tasks use only id·name·Overview·`refs`); fidelity = id·name·Overview·Contract + Git-visible src/tests + findings/restructuring. An all-mapped, all-empty-scope fidelity tree remains code-grounded when spec/result records appear, but still observes catalog roster/material as a tripwire; only an actual ref assignment or non-mapped node activates ownership. Seals are write-once: matching re-pin is read-only, while changed/partial evidence or a pending legacy verdict requires a fresh cycle. Only the first pin marks `approved_by: pending`; approval recomputes every current decision binding instead of trusting session memory.
6. **Stop safety**: `round` counts every spawned pass (find waves + confirmations); if it exceeds `max_rounds`, set `status: escalated`, take the open issues to the human, do **not** approve — reaching the budget is never a pass.
7. At every wave boundary — and at each item's confirmation — append the strikes to `adjudications`, **handed itemized (claim + verdict + reason) to every later wave as the adjudicated list** (so fresh reviewers don't re-find them), alongside the shapes of the **two-strike rule** and the user's exclusions (`reviewers.md` §Classification).

## Closing the gate — a decision, or nothing
What reaches the person at a clean terminal pass follows `FORMATS.md` "The step report" (*A decision, not a stage*): **a gate with nothing to decide asks for nothing.** "Is this what you want?" over a draft that passed its cold checks inside the agreed requirements is a stage approval — the rubber stamp this method exists to remove — so it is never asked. **Say whatever you do say in their words, not the cycle's** — no bare check code, round number or `PASS` reaches the person, and a GroveSpec term gets a plain gloss the first time it appears in the message.
- **Something is the person's to decide** — a `(gap)` on a leaf (behavior, or `accepted-gap`), a requirement the only fix would narrow or drop, an ambiguity the source leaves open, a question no recommended default can settle: ask it in the four-part shape (**the issue · the options · each option's impact · the recommended one**) **before `pin`** — a sealed verdict must not carry an open decision, and in a loop the unanswered ask ends the turn (`grovespec-next` §4). In auto mode the step takes the recommended option and records it; a question with no defensible recommendation stops in every mode. The answer lands in the record (`adjudications` · the `accepted-gap` ruling · a Change-Log line), and the cycle continues to its seal.
- **Nothing to decide — `spec`** → seal it (step 5), commit (below), and **take the gate in this same turn**: run `node .grovespec/bin/grovespec.mjs approve TASK-N`, which verifies both the Task seal and, for a new cycle, the completed source-evidence packet in the exact find round stored by `pin`, then flips `status: approved` with `approved_by: machine` — the cold verdict on the record, never counted as the person's approval; `status` names it until they `ratify`. Add one Change-Log line saying the machine took it, commit those bytes as **`approve TASK-N: <summary>`** (`FORMATS.md` "Commits" — the decision turn's own commit, after the gate commit), and close with *Your turn* saying there was nothing to decide. Approval is not a step of its own: a record left sealed but untaken is only what an interrupted turn leaves behind, and `grovespec next` names this same command for it. A person in the session who says they have looked and approve is a different thing: run **`node .grovespec/bin/grovespec.mjs approve TASK-N --human`** — their look, recorded as theirs. Never print the raw command at the human, and **never hand-edit the status** (a refusal means the spec or its source evidence moved after the pass — re-verify, don't override). Surviving `adjudications` stay in `<id>.verify.yaml` — `reopen` preserves them, same as the tree gate's rule below; don't copy them into the Change Log.
- **`tree`** → the one gate that is always a decision: a decomposition *is* a scope choice, so the person decides it in every mode, and the ask carries the tree as its issue. Show what the human is actually deciding. **First cycle** (no earlier human-approved pass in this record): the **whole tree** (+ the D-table with its source→node assignment — or, fidelity, the F-table with the code↔tree evidence), for a decomposition also **the order `next` will build it in** and the first node at which the person can see a result, and the matching question: **"is this the right decomposition?"** / **"is this an accurate survey?"**. **Re-verify** (the record carries earlier approved cycles): the decision object is the **delta since the last approval, in the person's terms** — for each changed node, what it will now do this milestone and what it will not, and what dropped out or came in against the last approval (or the disposition table plan confirmed); the `refs` coordinates and check verdicts behind it stay in the record (`tree.verify.yaml`, the round files) and are shown on request, as is the whole tree, and never point at `tree.md` bare — a Task `refs` edit leaves that file byte-identical, and "look at an unchanged file" reads as a broken gate (METHODOLOGY §6). Ask **"is this change what you intend?"** → Yes: run **`grovespec approve tree --human`** — it verifies the sealed structure, source scope, and current mode-specific reviewer input, then opens the gate; this gate is **never machine-taken**, in any mode. Surviving `adjudications` stay in `tree.verify.yaml` (a later structural/source-assignment re-verify reads them from there — no need to copy elsewhere; brief.md has no Change Log section). The human is now confirming an *already cold-vetted* tree — not doing the vetting themselves.
- **Escalated, or human rejects** → fix the draft / the sketch tree and loop back; nothing advances.

## When it's done
- **`spec`**: the pass is sealed and the gate taken in the same turn (`grovespec approve TASK-N` — machine, or `--human` for a person who looked) → `approved` → **next: `grovespec-implement`**.
- **`tree`** (decomposition): cold-verified + human-approved → **the per-node build begins**: `grovespec-grow` the root (detail its sketch → draft), then `verify` (spec) → `implement` → `review`, top-down.
- **`tree`** (fidelity): the survey is confirmed accurate → **`grovespec-plan`** (plan #1) structures the parked backlog into the first milestone; `revise`/`grow` execute it.

> **Open and close in the step-report shape** (`FORMATS.md` "The step report" — a `## … starting` heading to open; `### Result · Open · Your turn · Next` headings to close, warm full sentences). Here, *Open / Your turn* typically carry: open issues · an escalation · gap rulings waiting on the human.

**Commit as `verify TASK-N: <summary>`** (tree gate: `verify tree: …`) — and an **escalate** stop commits the same way (`verify TASK-N: escalated — …`): the whole cycle's evidence is uncommitted at that point (a verify cycle has no fix commits), it is what the human ruling reads, and `validate`'s untracked notice only watches *passed* records. On a pass — everything this gate wrote: the Task file (tree gate: `tree.md` and any sketch Tasks, including `refs`, its fix rounds edited), the gate's evidence — `<id>.verify.yaml` / `tree.verify.yaml` plus **every round file of this cycle** (a verify cycle has no fix commits; this commit is the only ride they get) — and, at `full`, the `conventions.md` pruning. The step name goes first so the commit stays out of the code cycle's `^TASK-N: ` anchor (`FORMATS.md` "Commits"). A passed gate whose record never entered git is a verdict whose subject is one `git clean` away from gone — `validate` names each one until it is in.

> **Recommend a new session for the next step** (implement, or the first `grow`). Clean, bounded context per step keeps GroveSpec's cost flat and its next reviewers cold (WORKFLOW §5). *(Driving with `grovespec next` in a loop? `@new` already starts that session — this recommendation is for a person going step by step, and it is never a reason to end the loop.)*
