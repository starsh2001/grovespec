# GroveSpec

**A spec methodology for agentic coding that keeps spec and code from drifting apart — by changing only a small *partial tree* at a time.**

GroveSpec is a set of skills + templates for [Claude Code](https://claude.com/claude-code) and [OpenAI Codex](https://developers.openai.com/codex/). You grow a project as a **tree of nodes**, where each node publishes a **Contract** — what it guarantees to the outside, so other nodes can rely on it without reading its internals. The spec stays *one node ahead* of the code, and every change is gated by a **cold, multi-reviewer** pass.

> **Scope:** GroveSpec is for building *software*. Its core — interface Contracts, an entry-point tree, tests, code search, spec↔code drift — assumes code. It is not a general workflow for documentation or planning.

## The problem it targets

At scale, spec-driven workflows tend to fail in two ways:

- **Specs a human can't actually review** — vast documents full of terms a person can't follow, so review degrades into a rubber stamp.
- **Drift** — the spec and the code slowly disagree, because one change ripples through a document nobody re-reads.

GroveSpec fights both: keep each change inside a **small partial tree** — the node you change plus the few nodes its contract touches (its children and its consumers), never the whole tree — so it's cheap to review deeply; and keep specs **plain enough to confirm at a glance**.

Working with *no* method has its own failure shape: every session starts from zero — context re-explained, architecture re-derived, the same decision re-made slightly differently each time — and review happens only when you remember to ask. GroveSpec's answer to both is the same thing: small files on disk that carry the state, and gates that don't depend on anyone remembering.

## How it works

```
init (once: setup; brownfield also maps code)
  → plan #0 (greenfield: intent → whole tree as sketches + source assignment)
  → verify the decomposition (cold) → human approve
  → per node:  grow (detail) → verify → implement → review ⇄ fix → done
  → revise                     change an already-done node later
```

- **Tree of contracts.** A project is a tree. Each node is a `Task` with a **Contract** (what it takes, gives, and guarantees). Consumers depend on the Contract, never the internals — so a change reaches only as far as the contracts it touches.
- **Whole tree, sketched first.** The first planning pass (`plan` #0) lays out the entire tree as one-line *sketches* from a detailed intent record, and records each node's exact source headings in Task `refs`; the tree gate reviews and seals that source→node assignment before each node's full contract is detailed (`grow`). The tree is a *hypothesis*, refined as you build — not a big design locked in up front.
- **Cold gates at every scale.** The whole **decomposition** is cold-reviewed before any node — is a feature missing, a sketch hiding a subtree, an actor unowned? (On existing code, the **survey** gets the same medicine: is the mapped tree an accurate photograph of the code?) Then each node's **spec** is cold-**verified** before any code, and its **code** is gated by **tests + a cold review of just that node's diff** — several fresh-eyes reviewers with different roles, never the whole codebase, so review cost stays flat as the project grows. Effort scales to the change.
- **Propagation on change.** Changing a done node asks whether its Contract changed: if not, fix just that spot; if so, find the nodes that used it and re-review them. Source ownership is tracked separately — changing Task `refs` reopens the spec and the tree's source-assignment gate even when the Contract wording has not moved.
- **Milestones, not a dead end.** Gates block only on must-fix problems in their own target; everything else real is *recorded* (followups, the brownfield backlogs) — and when the tree is all done, `plan` structures the parked work into the next milestone: cluster, human disposition (reopen · restructure · consciously drop), reopens the driver picks up again. Known work never ends a run silently — but the record list is not a queue: improvements become work only on your pick, and an auto run with nothing else left **ends** rather than opening a cleanup session.

## The eight skills

One per step of a node's life — `sketch → draft → approved → implemented → reviewed ⇄ fixed → done` — plus the planning pass between milestones.

| Skill | What it does |
|---|---|
| `grovespec-init` | Setup (once): the fixed interview → config. On existing code it also *surveys* the codebase into an all-`done` mapped tree + parked backlogs, ending at the survey **fidelity gate** (is the map accurate to the code?). It records what *is* — deciding what to build is plan's. |
| `grovespec-plan` | The planning pass. #0 (empty tree): draw out the intent → frozen intent record + brief → the whole all-`sketch` tree. #N (all done + parked work): cluster followups·backlogs by family → human-confirmed dispositions (reopen · restructure · consciously drop) → a new dated intent record → reopens/grows the driver picks up. Ends at the tree gate. |
| `grovespec-grow` | Detail one node's *sketch* into a full *draft* spec (no code), from the intent records — the per-node step of the initial build, and the tool for later expansion. |
| `grovespec-verify` | Cold, multi-role, parallel review of the **draft spec** → the gate (`draft → approved`), with the person asked only where a decision is theirs. The anti-rubber-stamp gate, spent where a flaw is cheapest. At `full` it also prunes entries this node made stale from `conventions.md` — only `implement` adds there, so nothing else would ever remove. |
| `grovespec-implement` | Turn an approved spec into code: pre-check → tests first → code → confirm the node's decomposition (`approved → implemented`). |
| `grovespec-review` | Run the **tests** + cold-review **only this node's diff** (not the codebase) → confirmed issue list (`implemented → reviewed`). |
| `grovespec-fix` | Apply the review's issues to this node's code → re-review (`reviewed ⇄ fixed`), until clean → `done`. |
| `grovespec-revise` | Change a node that already passed a gate (`done`, or an `approved` spec) — behavior (reopen + propagate), structure (split·merge·move), or promote a leaf to a skeleton. |

Plus a driver over them: **`grovespec-next`** runs whichever step is due, once, and stops — so you can keep going without tracking which node or which skill is next, or drive the build from a script. It carries no rules of its own. When nothing can proceed without you, its last line is `NOTHING_TO_WORK — <reason>`, which a queue runner or `@loop until=…` stops on.

It stops at **decisions, not stages**. A gate that came out **clean and sealed** — nothing left that is yours to decide — is taken on the record in every mode, after the runtime re-verifies the seal against the current bytes (and, for a result, that a green test run is bound to exactly that code): recorded as `approved_by: machine`, never as your approval, and `status`/`validate` name every such gate until you look and `ratify`. The verification result and your decisions are kept apart. What stops the loop is a decision that is genuinely yours — an ambiguous requirement, a product behavior or scope choice, accepting an unmet or unverifiable requirement — asked with the issue, the options, each one's impact and a recommendation; no issue, no ask. It has two modes only there: by default (**ask**) every such decision stops for you; ask for **auto** in that same invocation and a decision carrying a recommended option is taken as recommended, so only a question with no defensible default stops. Both modes refuse to approve past an escalation, an open issue, or any binding mismatch, and the tree gate stays yours in both. The trade is exact — **you keep the cold-review quality and spend your attention only on decisions**, because reviewers see the spec and the code, never what you meant.

## Artifacts

```
docs/
  brief.md           direction · scope · risks
  tree.md            the node tree (ids only)
  conventions.md     glossary · common rules
  tasks/TASK-N.md    one node each: refs source assignment · Overview · Requirements · Contract · AC · Subtasks · Change Log
  ref/               the frozen intent records (one per planning pass; brownfield: brought-in docs) + a location map that always points at current truth
.grovespec/
  config.yaml         paths · review settings · language
  schema              the format contract (machine SoT; FORMATS.md mirrors it)
  templates/          fill-in templates + FORMATS.md (the parser contract)
  bin/grovespec.mjs   deterministic checks — validate · status · check · next · approve · reopen · ratify · wait · diff · files · test · fresh · followups · source · pin · id · claim · lang · locale · interview · hooks · uninstall · amend · recheck · retro · impact · tree · version
  VERSION             the runtime bundle version — compare an install against this repo
```

**Headers and field names are fixed (English) — the parser contract. The content is written in your project's language** (`config.language`, set once at init). A Korean team writes Korean specs under English headers; an English team writes English. Plain language — in whatever language you work in.

## Using it

GroveSpec ships the same skill bundle for Claude Code and Codex. To adopt it in a project:

1. Copy `.grovespec/` plus the skill directory for your host: `.claude/skills/grovespec-*` for Claude Code, `.agents/skills/grovespec-*` for Codex, or both for a dual-host repo. Copy the *whole* `.grovespec/` directory, dotfiles included: it ships its own `.gitattributes` so the runtime checks out byte-stable (schema/templates are read byte-wise), and its own `.gitignore` so a project rule like `bin/` or `*.log` can't keep the runtime or the review logs out of git. Your project's own `.gitattributes` and `.gitignore` aren't touched.
2. Ask the agent: **"grovespec init"** — it configures GroveSpec (brownfield also maps your existing code). On greenfield, `plan` #0 then draws out the detailed intent, lays out the sketch tree, and assigns exact current ref headings to every Task. In Codex, `$grovespec-init` is the explicit form; the natural-language form works on both hosts.
3. After the tree gate, proceed per node: **"detail the next node"** (grow) → **"verify it"** → **"implement it"** → **"review it"** (→ **"fix"** if issues), top-down.

**Keeping installs in sync.** A project carries a *copy* of the skills + `.grovespec/`, so it can fall behind. `node .grovespec/bin/grovespec.mjs version` prints the installed runtime's version (`.grovespec/VERSION`); compare it against this repo's before trusting an old install. Claude-only, Codex-only and byte-identical dual-host installs produce the same fingerprint; a dual-host install whose skill trees drift is refused as a conflict.

**Parallel worktrees.** Several worktrees of one repository (`git worktree add`) can each run a GroveSpec session at once. Each session uses its own worktree's runtime and ledger — the ledger is committed on that branch and merges with the code, as always. What the worktrees share lives in the repository's git common directory, in one runtime-owned file that is never committed (`<git-common-dir>/grovespec/state.json` — `.git/grovespec/` in a plain checkout):
- **The id floor** — `grovespec id` never issues one number to two worktrees, uncommitted ones included.
- **Node claims** — every node step (grow · verify · implement · review · fix · revise) first runs `grovespec claim TASK-N <step>`, and `next` in every other worktree skips that node, naming who holds it and how to release it. A claim lasts across the node's steps in its worktree; it ends when a person runs `grovespec claim release TASK-N` or when its worktree leaves `git worktree list` (removed, or deleted and prunable) — never by age.
- **Done marks** — at `done` the claim becomes *done on branch X at commit C*: a worktree whose HEAD does not contain C still skips the node and says to take that merge in first. The mark stops applying to a worktree once C is in its HEAD, and ends for everyone when C is reachable from no branch (that work was abandoned — the node counts as open) or a person releases it; not by age, and not when its worktree goes — merged work outlives the worktree that made it.
- **The tree claim** — the tree-wide steps (the tree gate · plan · recheck · retro) take one claim, `grovespec claim tree <step>`; another worktree's tree-wide step is refused, naming the holder and the release. plan, recheck and retro release it as their last act; a tree gate ends it at `approve tree --human`.

`run.lock` stays per checkout, and a single checkout works as before. `grovespec version` prints `capabilities: parallel-worktrees` so a host can tell a runtime that supports this. What stays manual:
- **Shared ledger files merge as text.** Two branches that both edited `tree.md`, `waits.yaml`, `candidates.yaml`, the backlogs or `ref/index.md` conflict at merge like any file: keep both sides' nodes and entries (each node once in `tree.md`, one live wait per pair), then run `validate`. There is no stored derivative to regenerate — `files` · `diff` · `impact` · `tree` · `status` and the next id are computed on demand. Seals are the opposite of derivable: when the merged tree's shape or a Task's `refs` no longer match what the tree gate sealed, `validate` names the mismatch and the repair is `grovespec reopen tree decomposition` + a tree verify, never an edited digest. A test log a merge carried in (`<id>.test.log` · `last_test`) is its branch's evidence; `grovespec test TASK-N` re-records it against the merged code.
- **A dependent node waits for the merge.** A node whose parent, `blocked_by` or wait target was finished on another branch starts only after that branch is merged into this one — the result lives there, and `next` here keeps the node blocked until then.
- **A done mark covers the worktrees that exist.** Once every live worktree has C, the mark is dropped; a worktree added later from an older commit does not see it — take the integration branch in before starting new nodes there.
- **Every worktree needs a runtime with the capability.** An older runtime in one worktree neither reads the id floor nor honors claims. Separate clones share nothing; only worktrees of one repository do.

**Cold-review capacity.** `verify` and `review` need as many concurrent child slots as the selected scale's `reviewers` value in `.grovespec/config.yaml`. For Codex, set `agents.max_concurrent_threads_per_session` to at least that value; GroveSpec stops rather than silently serializing or shrinking a cold wave when the host cap is lower. Reviewers are spoken to once (their spawn prompt) and never by a queue-only message afterwards — on hosts that reap a finished child only when its inbox is empty, such a message pins it to a slot — and a wave checks the host's agent list for its own leftovers before it blames the cap.

**When it pays.** Every node asks the human for two confirmations — approve the spec, confirm the result. That's deliberate friction, spent where drift starts. For software you'll keep and grow it's cheap insurance; for a throwaway script it's overkill — GroveSpec is built for the first case.

**See a complete worked project:** [examples/expense-cli](examples/expense-cli) — a **brownfield** mini-CLI: its existing code *documented* as filled brief · tree · Tasks (real Contracts, honest gaps). The best way to see what good specs look like before you start.

**Optional deterministic checks** ship in `.grovespec/bin/grovespec.mjs` (no install — needs only **Node 18+**: node builtins only, no `package.json`, no `npm install`):

- `validate` — format + graph coherence (including canonical Task `refs`; duplicate Task/review YAML keys; orphans, cycles, impossible states) + **status ↔ evidence**. An advanced status must show the passed gate records that let it advance; present source-evidence/tree-scope seals and pending Task-frontmatter seals are recomputed, so changed decision input, source heading/context, resolved basis, tree structure, or source→node assignment is flagged stale. Duplicate mapping keys also block every project command before routing, because “first value” and “last value” parsers would otherwise see different states. Prints an **`examined:`** line before the verdict, so "I did not look" (a wrong path, an empty tasks dir) can never read as "I looked and found nothing". Exits non-zero with fixes.
- `status` — each node's state + which are unblocked, **what's waiting on the human** (approvals · confirms · escalations), and what's next.
- `check [TASK-N]` — is a node ready to work (parent done + blocked_by done), and what's the next step (verify/implement/review/fix/grow)? The top-down gate `grow`/`verify`/`implement` run, so the build can't drift bottom-up.
- `next [--auto]` — the single step due now, decided mechanically (so a driver never assembles it by hand, and never picks differently twice). A gate that came out *clean and sealed* is taken by its own gate skill in the same turn (`grovespec approve TASK-N`, `approved_by: machine`) in every mode — a verdict with nothing to decide is not a human wait; `next` names that command only for a seal left untaken. What still parks a node is an escalation (and the tree gate): **skipped, never picked**, and named node by node when nothing else is runnable. `--auto` changes what a step does at a decision (takes the recommended option) and what the terminal does with the record list. If a process dies after writing `status: passed` but before `pin`, the unsealed pass is routed back to its verify/review step instead of becoming a false human wait. A node another worktree holds — or finished on a branch not merged here — is skipped and listed with the reason and the release command; a tree-wide step due while another worktree runs one ends the run with the holder named (*Parallel worktrees* above).
- `approve <TASK-N|tree> [--human]` / `ratify TASK-N…` / `reopen TASK-N draft|approved` / `reopen tree decomposition|fidelity` — deciding a sealed gate, and its bookends. `approve` **writes no evidence**: it verifies the seal still covers the current bytes (spec + Task frontmatter; result: the reviewed project input and final Task frontmatter; a *machine* result additionally needs a green `last_test` bound the same way) and only then flips the state — bare is the driver's take of a clean gate (recorded as the machine's, in either mode), `--human` records a person who looked (a status is never hand-edited), and `approve tree` is **human-only in every mode**. `ratify` stamps machine-taken gates as yours. Task `reopen` restarts the gate cycles of a node that already passed one; tree `reopen` starts an explicit fresh mode after an approved structure/source-assignment change, so an already-built tree cannot be mistaken for the one-time brownfield fidelity gate. A past cycle's `passed` never doubles as the new cycle's evidence (`reviewed_commit` survives only as the next diff's base).
- `diff TASK-N` — the node's **cycle diff, computed**: its `TASK-N:` commits, their file set, base → working tree, with everything under `paths.review` held out (counted, never named — the cold round must not read the previous rounds' verdicts). This is what review reads — never hand-assembled (a hand-assembled diff misses files silently).
- `files TASK-N` — which code belongs to the node, across every cycle — the screen, the endpoint, the migration a feature actually spans. Derived from history each time, never stored, so it can't drift. Use it to *bound a read*: what these objects do and what calls what is then a question about these files, not about the codebase.
- `test [TASK-N]` — runs `config.review.test`; with an id, records the exit code + log as the node's evidence (`last_test` + `<id>.test.log`) — "the tests passed" is a machine-written fact.
- `fresh` — out-of-band signals: src/tests changes that never went through the skills (uncommitted edits, non-`TASK-` commits). A report, not a gate — the answer is `revise`. Merge commits are not classified: a merge's content arrives via its branch's own commits, which this report already answers for (a conflict resolution's own hand-content is the stated blind spot). Committed history is classified from the **adoption anchor** — the commit that first brings `.grovespec` into history (so squash merges and hand adoption still anchor), else the first `TASK-` commit — and only when the project root is the repository toplevel; nested in a larger repo (a monorepo subdir), `fresh` reports **uncommitted** changes only and says so.
- `followups` — every **parked** non-blocking finding across all gate records + the brownfield backlog counts, in one listing, **grouped by category**: must-fix work routed to another gate first (rule on these item by item), then `improvement` · `harmless-bug` (worked only on your pick), unclassified legacy items last. The aggregate surface that keeps parked work visible after the gates close — a report, not a gate, and never an automatic queue: `next --auto` ends when only record-category items remain.
- `source TASK-N [spec.md@4 …]` — emits exactly one canonical `grovespec-source-evidence/v1` JSON fence. Target-only is normal: scope comes from Task `refs`; optional coordinates must exact-match it and cannot override it. The runtime proves that scope is current through `ref/index.md`; the packet binds selected/nested heading context, every logical source candidate (including excluded `(gap)` and fenced body), and stable clause ids. Spec reviewers fill C1/C3 dispositions; `pin` additionally seals the **current content behind every Task/finding/adjudication basis**, not just its label.
- `pin <TASK-N|tree>` — the **seal**, run once at a cycle's pass: spec pin binds the Contract/AC, completed source packet, and Task frontmatter; result pin binds the reviewed commit, Contract/AC, and final Task frontmatter; tree pin binds structure, source scope, and its review substrate. `approved_by: pending` means a verdict exists but nobody decided. `source_scope_digest` covers every node's assignment and the current catalog/source material, so even an all-mapped no-ref fidelity tree records catalog changes as a tripwire; an actual ref assignment or non-mapped node switches the catalog from observed-only to active ownership. Paired `tree_evidence_mode` / `tree_evidence_digest` covers what the tree reviewers actually read: decomposition = brief + full sketch Tasks (or the bounded id·name·Overview·`refs` view of built Tasks); fidelity = id·name·Overview·Contract + the Git-visible src/tests files + both backlogs. The mode is written before round 1 and survives interruption. A matching re-pin is read-only; a changed/partial completed seal refuses and requires a fresh cycle. While a result verdict is pending, its commit binding covers the whole project except the current Task, its gate evidence, and the run lock, plus any path outside a nested project previously touched by a `TASK-N:` commit; the Task itself is covered by `task_evidence_digest`. `approve` applies the same committed and dirty-input checks for human and machine decisions; after a decision the Task digest is historical, so normal later role confirmation or tree-only dependency rewrites do not freeze the workflow; `diff` uses `reviewed_commit` as the previous cycle's closing line.

**Source-scope/evidence migration boundary (candidate behavior):** copy the runtime, `.grovespec/schema`, `FORMATS.md`, and both host skill trees together. `refs` is optional only for compatibility; all newly produced Tasks write a canonical flow list (`[spec.md@4, spec.md@5.4]`) or explicit `[]`. For a field-absent Task the runtime derives only an adjacent explicit `ref/<file> §N` citation cluster; a mapped Task with none is legacy no-ref, while a non-mapped Task with none refuses rather than guessing. New spec/result pins also write `task_evidence_digest`; a decided historical seal without it stays readable and is never backfilled, while a still-pending legacy verdict must run a fresh gate before approval. A new/reopened draft cycle must produce the source packet, after which `pin` adds paired `source_evidence_digest` / `source_evidence_round`; records with neither retain legacy behavior, one without the other is invalid. New tree cycles write `tree_evidence_mode` before round 1, then pin adds `tree_digest`, `source_scope_digest`, and `tree_evidence_digest`. A decided historical tree record without the newer fields remains readable and is never backfilled. A still-pending legacy tree verdict cannot prove which brief/Task/code bytes its reviewers saw, so it must run a fresh tree cycle before approval; after a decided tree changes, use `grovespec reopen tree decomposition|fidelity` rather than resetting its YAML by hand.
- `id` — the next node id, **derived, never counted by eye**: the highest number that left a trace + 1. It reads the current tree, task files and gate records, and — across **every reachable ref**, not just the current branch — both convention subjects (`TASK-N:` / `grow TASK-N:`) and the *path* of every task file any commit touched. So a merged-away node's number stays burned, including one that lived on another branch or arrived under an ordinary commit subject and was deleted; reusing it would hand its commits to the new node as that node's cycle diff. It prints where it looked, and what it cannot look at: history no ref reaches (a deleted branch, a commit dropped by a rewrite) is unreadable to any tool. Needs git ≥ 2.31 (merge-aware paths) **and a full clone** — cut history reads successfully and is wrong, so a shallow clone is refused outright (`git fetch --unshallow`); the history-reading commands (`diff` · `files` · `fresh` · validate's history checks) share that contract. In a git repository every issued number is also recorded in the repository's shared state, and the next id is never below it (`max(scan, issued) + 1`): a number handed out but not yet committed — in another worktree, or by an earlier `id` here — is never handed out again, and the extra line `already issued: …` says when that floor, not the scan, decided the number.
- `claim [list|<TASK-N|tree> [step]|release <TASK-N|tree>]` — which worktree of the repository holds which node, or the tree (*Parallel worktrees* above). `claim TASK-N <step>` is what each node step runs first (`claim tree <step>`, each tree-wide step): it takes the target for this worktree (or keeps it — the same worktree re-takes at every step), and exits 1 naming the holder when another live worktree has it, or when the node is done on a branch not merged here. `claim list` shows every claim and done mark with its worktree, branch, time and step (a mark: whether its commit is merged here); `claim release <TASK-N|tree>` ends one — this worktree's own, one a stopped worktree left, or a done mark whose work was abandoned. When the node reaches `done`, `approve` (or `amend` on a done node) turns the claim into a done mark — or simply ends it when no other worktree lacks the commit; a claim whose worktree is gone — removed, or its folder deleted — has lapsed. Writes go through a short lock in the shared directory: a second writer waits a few seconds, and a lock still held after that is named by path, never reclaimed.
- `impact TASK-N` — the consumer set a contract change reaches (the blast radius).
- `tree` — the id-only tree rendered with names + status. `version` — the installed runtime's version **plus a content fingerprint** (compare two installs by bytes, not labels) and a `capabilities:` line (`parallel-worktrees`) a host can check before relying on a feature.

> On Windows, invoke it through **PowerShell** (`node .grovespec/bin/grovespec.mjs …`) rather than Git Bash — Git Bash pays ~290ms per process to emulate Unix. And never wrap it in a `.ps1`: the execution policy applies to `.ps1` files, while `node script.mjs` is not subject to it at all.

Together they are the deterministic floor under the AI gates: the runtime owns the bookkeeping facts (what the diff is, whether tests ran, whether a status has its evidence, whether approved bytes changed), and the skills spend the AI's judgment on meaning. Run `validate` + `fresh` in CI to catch drift and out-of-band edits between sessions; the core loop runs on the skills + cold review without them.

## Influences

GroveSpec stands on earlier spec-driven work, with thanks. Its *explore* stance is influenced by [OpenSpec](https://github.com/Fission-AI/OpenSpec)'s explore mode. The cold, multi-reviewer gate and the one-node-ahead tree are GroveSpec's own response to the rubber-stamp reviews and spec↔code drift that every spec workflow meets at scale — territory charted by [BMAD-METHOD](https://github.com/bmadcode/bmad-method) and [Spec-Kit](https://github.com/github/spec-kit). Different bets, shared lineage.

## Status

**v0.21.0 — what a step starts, it owns; a touched verdict reopens; GroveSpec's files stay in git.** Five leaks measured across real projects, each closed where it opened. **Experiments:** a code reviewer built a deliberately runaway test with no time or memory limit, the session ended its turn "waiting for the reviewer", and the orphaned process grew overnight until the whole machine ran out of memory, taking every session on it down. A reviewer's experiment — and the main session's own measuring in verify, fix, recheck and retro — now runs in a temp copy of its own, gives each process a time limit (and a memory limit where it can grow), touches nothing it did not start, and cleans up before reporting; a turn never ends while anything its step started is still running (a wave, a test, a measurement); and driving the person's mouse, keyboard or windows, or changing the registry, settings or services, waits for the person's OK. **`recheck open` reopens the node:** a touched verdict used to record "opened" and tell the session to reopen through revise — one session didn't, the node stayed `done`, and the regression the verdict had named shipped until the milestone's retro found it. `grovespec recheck open TASK-N [TASK-FROM] draft|approved "<the reached use>"` now reopens it in the same command (`draft` when the reach needs the spec to change, `approved` when only the code does; a later `draft` verdict widens an earlier `approved`), and a node already mid-cycle just records the verdict. **Review round files are `<id>.review.round<n>.*`:** verify and review were both told to write `<id>.round<n>.*`, so a review round could overwrite the brief a spec seal had pinned and break that seal; most projects had already improvised the `review` infix, now the rule. **`blocked_by` never lists the node's own descendant:** a child already waits for its parent, so a parent waiting on its child deadlocks the moment both reopen — a mapped facade listed every module it calls, and later plans could not reopen it at all. `validate` refuses it (one line per node), and its wait-cycle check now follows parent edges too. **GroveSpec's files stay in git:** a `.gitignore` written for the project's stack swallowed the runtime (`bin/`) and the review test logs (`*.log`) while `validate` passed. The bundle now ships `.grovespec/.gitignore`, which re-includes both (a nested rule outranks the root one, so your `.gitignore` is untouched); `validate` names any GroveSpec file git still ignores, and any sketch/draft node its next spec verify would refuse for a missing ref assignment — said before that gate, not by it; init commits the hook registrations with its config. **Upgrading:** copy the whole `.grovespec/`, the new `.gitignore` included. If `validate` now refuses a `blocked_by` that lists the node's own descendants, delete those ids from that node's `blocked_by` — frontmatter only; no seal covers it. Minor, not patch: `validate` refuses a shape it used to accept, and `recheck open` now changes state.

**v0.20.1 — a gate's question is asked in the message, in the person's terms.** A tree re-verify asked for approval three times before it landed: the changed assignments were written as `refs` coordinates and put in the question tool's option preview, a field the host never drew. A tree re-verify asks about each changed node — what it will now do this milestone, what it will not, and what dropped out or came in since the last approval; the `refs` coordinates and check verdicts stay in the record and are shown on request. The unit that runs from a plan to its retro is now a **milestone**. "Round" had named both that and one pass of a cold review — a dashboard showed "round 2" beside "round 3/30" — so the review pass keeps the word (it is spelled into the records) and the plan-to-retro unit takes a new one. Not "sprint": a team's sprint is a fixed time box, and a milestone ends only when every node is done. `next`, `retro`, `fresh`, `followups` and the edit hook reword their output to match. Every step report is now laid out in markdown headings — the opening and closing anchor as `##`, then `### Result` · `### Open` · `### Your turn` · `### Next` — instead of label lines run together into one block. Wording only — records, formats and commands are unchanged.

**v0.19.1 — what a product is made of has an owner too.** A game's tree passed the decomposition gate with every screen that shows its sprites assigned and nothing that makes them — no node, and no process outside the tree named — so an all-`done` tree could have shipped without pictures. **v0.19.0 — worktrees of one repository build in parallel.** Each worktree's session uses its own runtime and ledger — committed on that branch, merged with the code — and four facts used to fall between them: a node id handed out but not yet committed (the derivation reads only what exists, so two worktrees could take the same `TASK-N` and meet again at merge), a node in progress (each `next` read only its own branch, so two worktrees could start the same node), a node finished but not yet merged (the other branch still reads it at its old status and starts it over), and a tree-wide step (two plans at once edit the same ledger files from two branches). All four now live in the one directory every worktree of a repository shares — `<git-common-dir>/grovespec/state.json`, runtime-owned, never committed, written under a short lock that waits a few seconds and is never reclaimed by age. **ids:** `grovespec id` still derives, and never issues below the repository's shared floor — `max(scan, issued) + 1` — so concurrent and uncommitted numbers never repeat; output is unchanged unless the floor decided the number (`already issued: …`). **claims:** every node step runs `grovespec claim TASK-N <step>` first; `next` in every other worktree skips that node and prints who holds it and how to release it; a claim spans the node's steps in its worktree and ends by `grovespec claim release` or when its worktree leaves `git worktree list` (removed, or deleted and prunable). **done marks:** at `done` the claim becomes *done on branch X at commit C*, and a worktree whose HEAD lacks C skips the node with "take that merge in first" — until C is in its HEAD, C is reachable from no branch (abandoned work: the node is open again), or a person releases it. **the tree claim:** the tree gate, plan, recheck and retro take `grovespec claim tree <step>`; another worktree's tree-wide step is refused with the holder named; plan · recheck · retro release it as their last act, `approve tree --human` at the gate. `run.lock` stays per checkout, a single checkout works as before, and `version` prints `capabilities: parallel-worktrees`. Minor, not patch: the runtime now writes under the repository's git directory. No format change, no migration — the first `id` or `claim` creates the file. The merge itself stays manual; the limits are listed under *Parallel worktrees* above. Regression: temporary repositories with `git worktree add` — two `id`s held overlapping inside the lock come out distinct, an uncommitted number is never re-issued, a claimed node is skipped with its holder named, removing or deleting the holding worktree releases it, a node done on one worktree is skipped by the next of another until the merge arrives (and comes back when the branch is deleted or the mark released), and a tree-wide step is refused while another worktree holds the tree; every existing golden passes unchanged except the two `version` ones (the new line) and the five that print the usage line (the new `claim` entry).

**v0.18.1 — the gate is taken where it was sealed, not one turn later.** 0.18.0 removed the stage question but left the *taking* of a clean gate to the driver's next turn: verify and review ended at `pin`, and `grovespec next` named `grovespec approve TASK-N` as a step of its own. Under `grovespec next` that costs nothing; driven by hand (`grovespec review TASK-3` on a testbed) the clean pass closed with "nothing to decide" and then stopped anyway, waiting for a command that had nothing to ask — a stage by another name, and a regression against 0.17, where the review session itself flipped `done` after the person's confirm. Now the gate skill takes its own gate: a clean pass runs `pin` → the gate commit → `approve TASK-N` (machine) → the `approve TASK-N:` commit, in every mode, in the same turn. `next` still names `approve` — only for a seal left untaken by an interrupted turn or an older runtime. Docs only (verify · review · next · FORMATS · WORKFLOW); the runtime's `approve` checks and goldens are unchanged. The modes still differ only at decisions.

**v0.18.0 — the loop stops at decisions, not at stages.** Measured on the launcher's default (ask) loop: every spec verify and code review that came out clean still stopped the run with "shall I record this as done?" — a question with no issue in it, so the person had nothing to add but a yes, and the loop had become manual stepping that bought no scrutiny. Now a gate that passed its cold cycle within the agreed requirements is **taken on the record in every mode** — `grovespec next` names `grovespec approve TASK-N` for a sealed clean gate, and the runtime writes `approved_by: machine`: the verification result, never the person's approval, named by `status`/`validate` until they `ratify`. What stops the loop is a decision that is genuinely the person's — an ambiguous requirement, a product behavior or scope choice, accepting an unmet or unverifiable requirement — asked in four parts (the issue · the options · each one's impact · the recommended one), and asked **before `pin`**, so a sealed verdict never carries an open decision. No issue, no ask. The two modes now differ only there: ask stops at every decision, auto takes the recommended option and stops only where none is defensible; the tree gate stays the person's in both. One SSoT paragraph (`FORMATS.md` "The step report" — *A decision, not a stage*) carries the rule; verify and review close against it, the driver reads it, and the step-report example — whose closing line was itself a stage approval — is rewritten. Minor, not patch: ask mode now writes `approved_by: machine` into gate records it used to leave pending; no format change, no migration — a pending clean gate on an existing project is simply taken on the next `grovespec next`. Regression: the ask-mode `next`/`status` goldens move with the rule, and a new ask-mode `gatework` sequence pins the acceptance criterion — a clean review with nothing undecided continues to the next step.

**v0.17.3 — a finished reviewer is not a free slot.** Measured on a multi-agent host whose finished child is reaped only when its inbox is empty and whose message tool only enqueues (never starts a turn): the main session sent two first-wave reviewers several messages around their completion, the messages were never read, the two stayed resident, and a three-reviewer second wave then hit the host's cap on its fourth spawn — which the session read as `reviewers.md` §Spawning's "capacity gap" and stopped the whole job. Three rules close the class, written by host capability rather than host name. **(1)** A reviewer is spoken to once — its spawn prompt — and never by a queue-only message afterwards; a short prompt is replaced by a fresh spawn, and a follow-up, if truly needed, goes only through a turn-starting tool. **(2)** "Over the limit" is two cases: a real cap below the reviewer count stops the wave as before; the skill's **own residue** (earlier-wave agents still in the host's agent list) is cleared with one closing turn each and the wave retried exactly once — a resident is never reused as a reviewer. **(3)** Wave hygiene: before each wave the agent list is read and leftovers cleared; a host without a list tool skips the check. Invocation contracts in verify · review · plan · retro and WORKFLOW §5 carry the same three sentences.

**v0.17.1 — the machine retreats to the provable side.** A cold external review of v0.17.0, run the day it shipped, reproduced four normal-path repairs in the new lane machinery — and all four fixes subtract or narrow rather than patch. **(1)** amend's anchor safety borrowed the whole continuous packet validator, whose first comparison (current spec digest vs the pinned one) every documentation edit legitimately fails — so nodes sealed with a source-evidence packet, i.e. every node the current verify produces, were refused the very lane built for them. amend now asks its own question — do the sealed anchors still resolve to the sealed content? — and on yes **re-seals the packet consistently** (its one legitimately-moved field, the spec digest, updated in brief and record together; `validate`'s continuous re-proof passes on the amended state). **(2)** amend's content normalization (list markers, wrapping, whitespace) erased meaningful bytes inside inline code and fenced blocks — `"a  b"` → `"a b"` re-sealed as "same content". **v0.17.0 — the lanes: candidates, not cascades.** Measured on the launcher and raised by its user: a two-item revise cost **48 commits across 12 nodes while exactly one node changed code** — a documentation edit forced full verify waves, and a contract change reopened every dependent on the spot, with validate's inversion rule dragging in even contract-strangers. The change splits what used to be one lane into three, each decided by the machine, never by an agent's feel. **(1) `grovespec amend`** — a documentation-only edit to a sealed node (Contract and AC content proven unchanged against HEAD, list markers and line-wrapping normalized away) re-seals in place: `done` stays, no cycle runs, dependents untouched; a re-wrap that would renumber a sealed evidence packet's `AC:n` anchors is refused toward the own-gates lane, so a sealed verdict never points at moved evidence. An **AC content change is never "just documentation"** — it changes what verification measures — and runs the node's own gates only, because consumers read the Contract and it didn't move. **(2) The candidate ledger** (`.grovespec/candidates.yaml`) — a contract change declares its dependents as **candidates** (`grovespec recheck declare`): they keep `done` and their seals; when the origin lands back at `done`, `next` arms **one recheck step ahead of new node work**. **(3) `grovespec-recheck`** (the tenth skill) — the machine closes provable non-users first (a footprint spelling none of the origin's contract names cannot observe the change), differently-armed waves (use-site · behavior) judge the rest under the same `find_streak` rule every gate uses, untouched candidates close in place with the shown miss as the record — nothing to re-approve, their seals were never broken — and **only judged-touched nodes reopen, their own dependents becoming candidates the same way, one layer at a time**. validate's inversion rule now passes a done node above an open dependency **when the ledger explains it**, keeps an unexplained one visible as a notice, and still refuses done above `sketch`. Both mechanical judgments keep the conservative asymmetry: false-"documentation" and false-"untouched" are the silent-drift direction, so the machine decides only the provable side. Applied to the measured batch, 48 commits become roughly twenty and eleven no-op propagation cycles become one recheck step.

**v0.15.0 — the routing hook, graded fresh, and a clean uninstall.** The question that drove it: in a repo with GroveSpec installed, does "fix this" actually enter the pipeline? Measured answer: skill triggering is probabilistic, and no other pre-hoc layer existed — only `fresh`'s after-the-fact catch was solid. The fix follows the economics of the debt, not blanket routing. **Visibility total, absorption lazy**: every src/tests edit is now *detected and graded*, but only contract-touching changes are steered to an immediate revise (stale-contract debt compounds the moment a next gated consumer reads it), while inside-the-contract changes can wait for a later cleanup batch. Three pieces. **(1) The edit-routing hook** — an advisory PostToolUse hook (installed per-project into `.claude/settings.json`, opted in at init's new Q4) computes on each edit what an agent would otherwise have to judge: which node owns the file (latest `TASK-N:` commit) and whether the edit text touches that node's Contract surface (backticked identifiers), then injects the answer as context. **v0.14.0 — a sideways obligation freezes the node: the wait ledger.** Measured on a proof run: two consumer nodes were built and closed *before* the producer node defined the contract value they were told to read — each parked the obligation as a sideways `[→ child/deferred: TASK-N]` note, the gates read the marked deferral as resolved delegation, and "every node is done, 100%" went up over a live obligation nothing would ever re-read (a child deferral is re-entered by `grow`; a sideways note has no way back — and the same promise had already slipped one milestone earlier). The class fix: mid-step, on discovering that another **open** node must define something first, the node **declares a wait** — `grovespec wait TASK-A TASK-B <need…>` — and freezes in place (status unchanged, cycle record open, not schedulable), with the same fact written in both nodes' Change Logs. Scheduling follows one rule, **the turn follows the newest declaration**: a counter-declaration wakes the other node instead of deadlocking (exactly one node of a chain is awake; a mutual wait is a turn-pass), a third node's declaration passes the turn onward, and the resumed node's first move is reading the counterpart's recorded need — its own question coming back means the answer exists nowhere yet, so it switches from waiting to producing/asking/revising (ownership never moves by time). Structurally enforced ends: a frozen node cannot reach `done`, `approve` refuses a gate over a live wait, a `done` node holding a live wait is a validate problem, a landed value (target went done) reprints as a notice until resolved, and a wait onto a node the declarer itself holds shut (its own dependent) is refused — that arrow is evidence for a revise. **v0.13.6 — the strict-YAML sweep now sees structure, not just quotes.** The v0.13.4 check covered malformed quoted scalars — and the worse damage axis turned out to be structural: a list item fallen to **column 0** ends the list for every line reader here, so the item and everything below leave grovespec's own sight — a settled adjudication silently gone is a settled finding free to re-fire (measured: 3 files · 4 items in one repository, `validate` passing). **v0.13.5 — the format version is now the documented negotiation handle.** v0.13.4's outside consumer raised the next question: how does an external parser (a dashboard cold-parsing `config.yaml` · `tree.md` · Task frontmatter · the review records) tell *"version mismatch — migrate"* from *"broken data"*? **v0.13.4 — quoted record values must survive a strict YAML reader.** Found through an outside consumer (a dashboard partial-parsing the review records): in one real project **6 of 39** review-state files were unreadable to js-yaml — every one a free-text field (`reason` · `issue`) quoting a document sentence or citing a Windows path: an unescaped `\` inside `"…"` (an undefined YAML escape) or a bare `'` inside `'…'` (the value closes early). grovespec itself never noticed, by design — its readers are line-based and interpret no escapes ("these records are read line by line"), so the breakage surfaces only outside. **v0.13.0 — findings are classified, not graded: fixed-handling categories, a qualified no-new-finding streak, and one-item-at-a-time fixes.** Measured on a real `next auto` driver run (a Windows tray launcher): the severity ladder's `mechanism` ruling turned mutation-shown *test gaps* into mandatory fixes — four consecutive fixes changed no product code, a state × error test matrix grew to a self-inflicted 1,225 combinations, the agent then set about optimizing the runtime of the tests it had itself demanded, and a scope the user had explicitly excluded was resurrected because "this cycle touched related code". Every step was locally defensible under the ladder; the product was done the whole time. Three changes, shipped together because each keeps the others honest. **(1) Categories with fixed handling** replace critical/should-fix/nice-to-have + `strength` + the three severity gates: five categories are always must-fix — blocked run/crash · requirement-unmet (citing the *user's* requirement) · normal-use bug · easy abuse · realistic security hole — and two are always record-only (improvement · harmless bug). A mutation-only test gap is an improvement; reproduction proves a problem real but never raises its class; a reviewer-invented verification duty never becomes a requirement; `validate` enforces the lanes instead of recomputing severity caps. **(2) Find ends on a qualified streak** — `find_streak` (N) consecutive cold waves confirming no NEW must-fix finding. Only a new must-fix resets the counter; re-finds and record-only items don't, and an aborted wave or an unresolved classification doesn't advance it — which is what removes the old streak's coin-flip without re-arming the strategy ledger as a terminator (the ledger survives as an aid: differently-armed waves; no node owes a mutation campaign, a combination walk, or a reference model by default, and v0.12.1's first-fix full-space sweep rule is withdrawn). **(3) Fix works one item at a time**: a plan (cause · change · blast radius · closure measurement) is cold-reviewed and applied only after `plan_streak` (M) consecutive clean passes — a plan edit resets the count — then the item is applied and confirmed alone, scoped to its own diff; a failed confirmation returns to *that item's plan* with the failure named first (mis-diagnosed cause · symptom-only patch · implementation slip), never a stacked patch. No batch fix, no terminal re-sweep — "review came back clean" is no longer anybody's termination condition. The record list (`followups`) is never an automatic queue: `next auto` and planning passes adopt an item only on the user's explicit pick, and an `excluded-by-user` adjudication survives every reopen until the user reverses it or live must-fix evidence goes back to them. **Migration**: copy the new `.grovespec/` in with the runtime (the schema's finding/review keys changed; an old schema fails the preflight by design). Two surface changes for scripts: `followups` output now groups by category, and `interview`'s second question asks the find streak instead of the blocking strength.

Check `paths.review` against your other `paths` too: an overlap is now refused rather than silently filtered — the review dir is GroveSpec's own region, and anything in it is held out of every cycle diff. A list written in **flow** style (`followups: [ {...} ]`) is now refused: these records are read line by line, so flow style used to switch every per-item check off silently. `diff` output changes shape for cycles that touched the review dir (fewer files, plus a held-out count line — two of them when records are both committed and dirty) — a script parsing it sees the change.

**v0.8.1 — early, partly proven.** A binding fix in the runtime, no format change. The result gate compared the reviewed commit to HEAD **by id**, so any commit made after the seal broke it — including the one the workflow asks for. The third proof run hit it head-on: a review cycle passed, `pin` sealed the verdict to that commit, and committing the cycle's own record (the gate yaml, its round briefs, the test log, the Change Log line) moved HEAD one step and made the node unapprovable. Not a code change: the diff between the sealed commit and HEAD was four record files and a log line. And there was no way out — `--human` hits the same check, and the remedy the refusal named (re-run the gate) lands in the same state unless *nothing whatever* is committed between `pin` and `approve`, a window that in the default flow spans the human's look. The seal now measures what the verdict is about: **the code**. HEAD may have moved, as long as nothing under src/tests did — the same coordinates the clean-tree check already uses, so both halves of "is the tested code the current code?" now measure the same paths instead of one asking about the whole repository. A moved code path is named in the refusal, which says *what* moved instead of only *that* something did. `last_test`'s binding is relaxed the same way, and a seal that is a moving name or a foreign line of history is refused explicitly rather than by the accident of an id mismatch. The bound is stated rather than papered over: a non-code commit that changes what the recorded run means (a dependency bump, a CI edit) is not caught here — the working-tree check has the same bound, and widening only one half would make one question answer differently depending on whether the change happened to be committed yet.

**v0.8.0 — early, partly proven.** The cold-review cycle is restructured: **one gate = find → judge → fix**, replacing "pass `repeat` rounds in a row". The third proof run measured what the old terminator cost: two nodes of a 364-line product took 46 cold rounds, including a 13-round code review whose passes at R4·R6·R8 were each broken by the next round's fresh eyes — a coin-flip terminator that resets on tails pays most of its rounds for the streak, not for the code. Three structural findings drove the shape. (1) *Re-finding*: 109 of 125 triage verdicts across the run were drops, many re-killing a shape a prior round had already killed — so finders now receive the **found list** ("don't re-report these or their shape") while still never seeing how the target was built or any clean-claim. (2) *Strategy correlation*: a real data-loss defect survived 8 rounds and 205 planted mutations because every lens swept one axis at a time and the defect lived in a two-axis cell — so the find phase ends by **exhausting a named strategy ledger** (single-axis · axis-product · reference-model fuzz · boundary · harness audit …), never by rounds going quiet, with `repeat` keeping its recall duty as the *minimum wave count*. (3) *Manufactured evidence*: the one checklist check with no finite positive proof ("readable in one pass") failed zero-blocker rounds on comparative metrics — 1.6× the siblings' longest line — while the round that finally passed measured *worse* average density; C6 now blocks **only on FAIL** (quote the line, name the misreading), comparative metrics are banned grounds, and a shape dropped twice is struck on sight. The find target is **frozen** (nothing fixed between waves), **judge runs once** over everything found, and each fix gets a cold confirmation **scoped to the fix's own diff**. A coverage finding must name the Contract/AC clause the missing test leaves unpinned — review's Stop rule, mirroring C5's.

Migrating to 0.8.0: the review-state format gains optional fields (`phase`, `strategies[]`, `found[]`, `checks[]`, `rounds[].phase`) — **existing records stay valid** (`consecutive_passes` is still written and still schema-required — validate checks the field exists; nothing reads its value). A cycle caught mid-legacy-loop keeps its judged state (open issues · adjudications), and the find requirement binds to the **final bytes**: legacy rounds that read exactly those bytes count as waves; earlier ones don't (fixes moved the bytes under them) — run whatever waves are still missing, judge anything unjudged, and continue. `repeat`'s config values keep their meaning by reinterpretation (2 = at least two differently-armed waves), so no config change is needed.

**v0.7.0 — early, partly proven.** The lifecycle gains milestones: **init and plan are now two skills, split by truth criterion.** init records what *is* (config; on existing code, a *survey* into an all-`done` mapped tree) — and the survey now gets its own cold gate (**fidelity**, F1–F4: is the map an accurate photograph of the code? — it used to pass on a human glance alone). plan decides what to build *next*: plan #0 is the greenfield exploration that used to live inside init (intent record + brief + the all-`sketch` tree), and plan #N structures the **parked work** — the followups the gates deliberately don't block on, the brownfield backlogs, `fresh` hand-edits — into the next milestone: clustered by family, human-confirmed dispositions (reopen · restructure · consciously drop), translated into reopens/grows the driver picks up again. New runtime command `followups` (the aggregate listing); `next` now routes an empty tree to plan #0 and an all-done tree with parked work to plan — **the driver no longer ends silently on top of known work.** ref/ is formalized as a *series* of frozen intent records (later records supersede sections by name; `ref/index.md` points at current truth).

Migrating to 0.7.0: **no Task or review-record format change** — existing records are untouched. Copy the new `grovespec-plan` skill along with the rest (the install step already copies all of `.claude/skills/grovespec-*`). Three behavior changes to know: (1) a **mapped (brownfield) tree with no node-level gate records** now arms the fidelity gate and blocks node work until the survey is cold-verified + human-approved — a project already mid-build (any node gate record exists) is exempt; (2) `next` exits 0 with a `plan` routing where it used to exit 1 at "the tree is empty" (config present) and at "every node is done" (when parked work exists) — a script keying on those exit codes sees the change; (3) `validate` no longer requires `brief.md` while the tree is empty (the pre-plan state is valid).

**v0.6.2 — early, partly proven.** A retention fix in the runtime, no format change. `reopen` used to reset a node's gate records to fresh cycles *including* `adjudications` — the settled don't-re-raise calls — on the assumption they had been copied into the Task's Change Log. The first proof run broke that assumption at scale: 22 review rounds left 134 settled calls against a Task file already at 126KB, and the cold reviewers' criteria come from that same file — so the copy hands every prior verdict to precisely the reader whose blankness the method depends on. The resolution: what a reset wipes is *evidence* (rounds, open issues, the pass itself), and a settled call is not evidence but a boundary, which a new cycle doesn't expire. `reopen` now preserves `adjudications` (like `reviewed_commit`) and nothing is copied into the Change Log. One guard travels with the keep: on a `draft` reopen the contract changed, so the caller prunes kept entries whose written reason leaned on the old contract before handing the list to the next round — a dead reason must not suppress a now-real finding. This is also why every adjudication records its reason, not just its verdict.

**v0.6.1 — early, partly proven.** A write-scope fix, no format change. `fix` fenced only another node's *code*, so a finding whose real owner was a **not-yet-built** node could be cleared by writing the rule into that node's Task. That edit lands in the *fixing* node's own cycle diff, which makes each fix the next cold round's reading material — and prose specifying a mechanism can always be found under-specified, because the check that would settle it cannot exist until that node is built. The proof run showed it plainly: the child's Task file was edited eight times, **six by the parent's commits and never once by its own work**, and the parent's last five review rounds all ran on that one planted line while its product code had not moved in nineteen. The principle was already stated (*concern for an unbuilt child is over-reach*) — it just had no fence. Now `fix`'s write-scope covers another node's **Task**, not only its code: reading another node is fine, writing it is that node's own turn. What the node genuinely learned still travels — a global rule to `conventions.md`, the measurement to its own record — and the unbuilt node reads it on its own turn, when it can answer with a test instead of a paragraph.

**v0.6.0 — early, partly proven.** The evidence status from v0.5.1 still applies, and this release changes the review-state format again: result reviews now split findings into blocking `defect` items and non-blocking `followups`, with required `kind` + `family` fields on each open finding.

v0.6.0 splits review findings into two lanes. `open_issues` now holds only defects in the current review target, while spec/contract revision work found during code review moves to `followups` for later revise/verify. The runtime also rejects the same underlying hole being re-raised through a second path in the same review file.

**v0.5.1 — early, partly proven.** The cold-review engine is the piece with real evidence behind it: a controlled cold-spawn multi-reviewer run on a planted-flaw sample caught the planted flaws, emergent ones, *and* flaws its own fixes introduced (no false convergence) — and the brownfield mapping (code → tree + contracts) was validated on a sample too. What has **not** been run end-to-end is the greenfield full cycle (grow → verify → implement → review → done) on a real project, or init on a large codebase. Expect rough edges there; the skills and formats may still shift before 1.0.

v0.3.0 added the **deterministic floor** (and moved the runtime from bash to Node): the runtime computes the review's diff, records test runs, requires every advanced status to show its passed gate records, pins approved specs to content digests, and reports out-of-band edits — the facts a session could misreport are now recomputed, not trusted. v0.4.0 adds the **driver**: `grovespec-next` runs whichever step is due (`next` · `files` locate the work; `approve` · `ratify` record a machine-taken gate honestly), so the build can be repeated from a script without a person tracking what comes next. Nothing about the gates changed — auto mode leaves a trail that says a machine took them. v0.4.2 fixes an asymmetry the first greenfield proof run exposed: the *cut-first* discipline lived only in `verify` (the spec review), so the code side had no brake — six consecutive rounds went to a node whose product code never moved while its test scaffolding grew to 4x the product, each round finding real-but-marginal flaws in scaffolding the previous fix had added. `review` and `fix` now default to subtract, a round of only nice-to-have findings passes, and blocking severity has to answer three gates (can you exhibit it in code that exists · does the contract explicitly promise it · is there a documented workaround) with no re-justifying what a gate lowered. v0.5.0 makes the severity gates **arithmetic the runtime checks** instead of prose a round can write down and then grade past. Every confirmed finding now records its gate answers as fields, and `validate` recomputes the cap from them, **failing the record if the grade exceeds it**. The gate that does the real work is `gate1` — *what can you exhibit today, by running committed code, and how is the wrongness reached*: `behavior` (the wrong behavior itself runs — critical-capable), `mechanism` (the defect is verified by probe/mutation AND one *ordinary* step reaches it — a natural future edit, an in-scope consumer doing the documented thing, named in a required `trigger` field — caps at should-fix), `contrived` (the hole is shown but reaching it needs abnormal action — deliberately violating a documented rule, two independent edits coinciding, input outside the product's stated reality — caps at nice-to-have), or `story` (no verified hole; the victim is predicted — caps at nice-to-have). Ordinary-vs-contrived is judged against the *brief*, not universally: a hostile caller is ordinary reality for an internet-facing service and contrived for a single-user local tool. `gate2` (a *shown* break of an explicitly promised clause — named) lifts the cap for mechanism/story but never for contrived — a promise that only breaks under deliberate abnormal action is not a promise the product breaks; `gate3` (a documented workaround or an existing signal that already catches it — named) drops one more. Without the `contrived` split, verified-but-absurd probes block forever: a hole that only opens under an outlandish reproduction can be re-demonstrated through a new path every round while case-by-case patches feed it — ten rounds of should-fix with no end. The fix side gets the mirror rule: block the *cause*, not the demonstration. A `yes` that leans on nothing is rejected, and `proposed: critical` must be anchored by a clause or a named harm, so nothing starts at the top for free. The design aims at the one boundary that actually ends or feeds a review loop: at the default strength, critical and should-fix block identically, so **the demotion that matters is a should-fix dying to nice-to-have** — the proof run's sixteen rounds were fed precisely by story-grade findings surviving as should-fix, in a node where the three gates were *stated* every round and then not followed. The only rules that held across those rounds were the ones a machine counted; now this one is counted too. This changes the review-state format — see Migrating. v0.5.1 adds one rule to the code-review engine, from the same proof run: **when the reviewed change is a rule someone else will implement, vary the implementations — not just the inputs.** A round had passed clean across six code forms × four run modes of a *single* test setup; the next round spread the **setup** axis — which process it runs in, which environment it starts from, which import order, when it observes — and found the rule's own recommended setup could not go red at all. Breadth on the wrong axis reads exactly like breadth, and a rule stated as intent-plus-hints goes blind first in the setup a convention-following implementer would naturally reach for. v0.4.3 fixes what v0.4.2 only braked: the severity ladder itself was written in *spec* vocabulary — `critical` meant "a named consumer cannot build its part" — and both gates shared it, so **running code was barely gradeable**. Code is already built; nothing in a diff ever "can't be built", so every real code defect got pushed up into `should-fix`, and at the default `strength: 2` each one stopped the gate. That is the mechanism behind the same proof run's fifteen rounds. The ladder is now one axis — *how strongly must this be fixed* (`critical` must · `should-fix` works today but strongly advised · `nice-to-have` optional) — with the old "cannot build its part" kept as one **case** of `critical` on the spec side, and code cases and code examples added (the section previously had none). v0.4.1 closes a hole in that binding: a project placed inside a git repository that *ignores* it still answered "yes, I am in a repo," so a result gate sealed itself to that repository's HEAD — a commit no change to the project's own code can move, which made the seal's later check pass for free. `pin` and `approve` now refuse it and `validate` names it.

Migrating to 0.6.0: any **open** finding in `open_issues:` or `followups:` needs the lane fields added — `kind: defect|contract-gap|concern` and a `family` name for the underlying hole. In **result** reviews, `open_issues` may contain only `kind: defect`; move spec/contract revision work to `followups` as `contract-gap`, and move non-blocking notes to `followups` as `concern`. The same `family` may appear only once across `open_issues` + `followups`. Records with both lists empty need nothing, and closed rounds already in `rounds:`/`adjudications:` are untouched.

Migrating to 0.5.0: any **open** finding in a `.grovespec/review/*.yaml` needs the gate fields added — `proposed`, `gate1: behavior|mechanism|contrived|story`, `gate2: yes|no`, `gate3: yes|no` (plus `trigger` when gate1 is mechanism, `clause` when gate2 is yes, `workaround` when gate3 is yes, `harm` for a `proposed: critical` with no clause). `validate` names each missing or invalid field and the file it is in, so run it once and fill in what it lists. Records with `open_issues: []` need nothing, and closed rounds already in `rounds:`/`adjudications:` are untouched.

Migrating a pre-0.3.0 tree: add `origin: mapped` to each brownfield-mapped node's frontmatter (the evidence checks exempt those), and change calls from `bash .grovespec/bin/grovespec` to `node .grovespec/bin/grovespec.mjs`. Nothing else changes for 0.4.0 — the new commands and the driver are additions.
