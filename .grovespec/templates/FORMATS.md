# GroveSpec artifact formats (the parser contract)

So that tools can read these files and process them mechanically, **the format is fixed**. Don't change header names·order, field names·types, or the date format on a whim. (This is itself GroveSpec's *contract* to outside tools.)

> **Machine source of truth:** the checkable lists (frontmatter fields · enums · sections) are defined in `.grovespec/schema` and enforced by `.grovespec/bin/grovespec.mjs validate`. This doc is the human-readable contract; the lists below mirror `schema` — if they ever differ, `schema` (what `validate` reads) wins. Edit `schema` first.

> Headers and field names are fixed and English. The *content* (prose) is written in the project's language (`config.language`).

> **How the prose is written.** Every artifact here is read by a **person and an agent, from the same file** — so write for a competent person who does *not* know this project and is reading it months later. This is the same bar the `non-expert` reviewer applies (C6), so writing to it is what gets a spec through:
> - **Plainest exact word wins.** Don't coin terms, labels, or tier names — say the thing. A term you genuinely can't avoid goes in `conventions.md` *Glossary*, and then it's always the same word (search finds letters, not meanings).
> - **Established names travel as names.** GroveSpec's and the stack's existing terms (cold review, skeleton, gate…) keep their established form in every output language — transliterated (콜드 리뷰) or kept in English — never re-invented as a translation (냉정 검토): an invented rendering is a second name for the same concept, and different runs will invent different ones.
> - **Register: a document vs. addressing the person.** Artifacts are documents — write them in the language's documentary register (Korean: plain `~한다`/`~이다`). The step report, and anything else spoken *to* the person, uses that language's respectful-address register — Korean: formal polite **`~합니다`/`~하겠습니다`**, not casual `~해요`, and never plain `~한다`, which addressed to a person reads as rude. Warmth lives in *what gets explained*, not in the endings. (The fixed setup-interview strings keep their own register.)
> - **No filler.** Cut anything that survives deletion — throat-clearing, a restated header, "it is important to note".
> - **Readable in one pass.** If a line needs a second read to parse, split it or cut it. Applies to the running record too: a Change-Log entry says *what changed and why* in a sentence, not a transcript.
> - **The machine lane stays in the machine's file.** Round numbers, check codes (`C4`, `D2`, `F1`), finding ids, `PASS`/`FAIL`/`PARTIAL`, `open_issues` — that is the cold cycle's bookkeeping, and it has a home: the gate record under `paths.review`, which is where anyone auditing the cycle looks. In a Task file it is noise a reader cannot decode and cannot act on. Say what was found, not what it was filed as.

## The format version — how a reader decides it may read

Everything below this line is **format `1`**. The declaration is `.grovespec/config.yaml` top-level `version:` — spelled **exactly once, in that file and no other** (a copy elsewhere would create the state "the two declarations disagree", which no reader should have to adjudicate). That one field is the negotiation handle for **every** reader — grovespec's own runtime and any outside tool cold-parsing these artifacts (a dashboard reading `tree.md` · Task frontmatter · the review records under `paths.review`) — and it exists so that a reader meeting a different format can say *"version mismatch — migrate"* instead of *"broken data"*. The gate, implementable from this document alone:

1. **No `.grovespec/config.yaml`** → not an initialized GroveSpec project; nothing here claims these formats.
2. **Top-level `version:` more than once** → the format boundary is ambiguous: refuse to read and name the duplicate — never pick one. (The runtime refuses every command on this.)
3. **No `version:` line** → a **pre-versioning install**: read it as format `1`. That is the runtime's own reading (`validate` advises adding `version: 1`; nothing refuses), so an outside reader treats it as format `1` and may surface the same advisory — it is not a migration case.
4. **`version:` ≠ the format you implement** → version mismatch: refuse to interpret the artifacts and say migration/upgrade — never render what you did not read as damaged data.
5. **`version:` = the format you implement** → every shape in this document holds.

**What the number promises.** An incompatible change to any externally-parsed artifact — a `config.yaml` key's meaning, `tree.md` structure, Task frontmatter required fields or the meaning of an enum value, review-record required fields or enums, any byte shape this document fixes — **bumps the format version**. Same number = same reading rules. **Additive changes do not bump it**: a new optional field or a new enum value may appear within the same format, so a reader must pass unknown fields through untouched and render an unknown enum value as an opaque state, never as an error — the version moves only when an existing correct reading would go wrong.

`version` is the **format axis**, not the runtime: `.grovespec/VERSION` (and the `grovespec version` fingerprint) name the installed runtime bundle — many runtime releases read the same format, so a format decision reads `config.yaml` `version:` and nothing else. The runtime's spelling of the current format is the `FORMAT` constant in `bin/lib/project.mjs`; the number there, here, and in the config template move together.

## How it reads when rendered

The artifact is not a data file that a person occasionally tolerates — it is **the document they open**, in a Markdown renderer, on a laptop or a phone. The rules above govern the words; these govern the page. They are checkable, and `grovespec validate` checks them (the numbers live in `.grovespec/schema` under `read.*`, so code and this doc share one source). Like the sideways-marker rule, a violation is **a problem at `sketch`/`draft`** — where the text is free to edit — and **a notice once the spec is sealed** (demanding the tidy would demand breaking the seal); tidy each sealed node the next time it opens at draft:

| rule | limit | why |
|---|---|---|
| **Frontmatter must not become the title.** Leave **one blank line before the closing `---`**. | — | Without it CommonMark reads the closing fence as a setext underline and renders the entire frontmatter as the document's largest heading. Every YAML reader — and `grovespec` itself — is indifferent to the blank line; every renderer is not. |
| **A title, then a lede.** First body line is `# TASK-N · <name>` (id and name exactly as the frontmatter spells them), then one `>` blockquote line saying what the node is responsible for. | lede ≤ `read.lede.max` | The page needs a name at the top and a sentence that tells a reader whether to keep reading. Without them the first thing rendered is `## Overview`, and the node's name is visible only inside the metadata block. |
| **One list item = one claim.** | ≤ `read.item.max` chars | An item is measured whole — its own continuation lines included, its nested children not — so hard-wrapping the source cannot buy room. Over the limit means the item is carrying two thoughts: the second one is a **nested item**, not another sentence. |
| **One paragraph = one point.** | ≤ `read.paragraph.max` chars | Past that it stops being read and starts being skimmed. |
| **No machine-lane vocabulary** (`read.jargon`). | — | See the prose rule above. |

Measured, in a real project, before these limits existed: one node's Change Log was **402 of the Task's 762 body lines**, its longest entry **2466 characters** — a single bullet nobody could read, in the section a person opens the file *for*.



## tasks/TASK-N.md
YAML frontmatter + a title + a lede + fixed sections.

**frontmatter** — closed by a blank line and then `---` (see "How it reads when rendered"; every reader here tolerates the blank line, and `validate` asks for it).

| field | type | value |
|---|---|---|
| `id` | string | `TASK-N` — immutable, same as the filename. New ids come from `grovespec id` (highest number that left a trace + 1: tree · files · gate records, plus convention subjects **and** task-file paths across every reachable ref); **a retired id is never reused** — its commits would become the new node's cycle diff. Unreachable history (deleted branch, rewritten commit) is beyond any tool's reach; the command says so. In a git repository the result is also never below the shared issuance floor (*Shared worktree state*), so a number issued but not yet committed — by another worktree or an earlier call — is never issued again |
| `name` | string | node name — may change (rename) |
| `role` | enum | `skeleton` \| `feature` |
| `status` | enum | `sketch` \| `draft` \| `approved` \| `implemented` \| `reviewed` \| `fixed` \| `done` |
| `blocked_by` | list | `[TASK-2, ...]`, `[]` if none — cross-tree nodes only: never the parent, never the node's own descendant (`validate` refuses one) |
| `refs` | list, optional for migration | the exact current ref headings assigned to this node, as one canonical flow list sorted by file + numeric heading: `[spec.md@4, spec.md@5.4]`. Paths are relative to `paths.ref`; coordinates inside one Task may not duplicate or overlap. `[]` means **intentionally no ref source**, never “unknown yet.” Every new sketch/draft and every brownfield-mapped Task writes this field; absence is accepted only through the legacy rule below. |
| `tdd` | bool | `true` \| `false` |
| `tdd_skip_reason` | string | required when `tdd: false` |
| `origin` | enum, optional | `mapped` — brownfield only: born `done` from existing code (code-to-tree), no gate records behind it. Absent on every built node. |

**Status lifecycle** (defined here once — skills point here, don't restate). Each status = a completed gate; a node advances one skill at a time:
- `sketch` — **greenfield only.** Placed in the tree with a one-line responsibility + rough I/O + exact `refs` source assignment, no full contract yet. Created by *plan* (`spec-to-tree`) for the whole tree at once. Detailed into `draft` by *grow*. (Brownfield nodes skip this — they're born `done`.)
- `draft` — full contract written (by *grow* detailing a sketch, or by *revise*). A grounded hypothesis, not yet verified.
- `approved` — spec passed *verify* (cold multi-persona) + human-approved → ready to implement. *verify* sets this.
- `implemented` — code written by *implement*; the node's own tests pass. Not yet reviewed.
- `reviewed` — code passed *review* (tests + cold code personas on the diff). Awaiting human confirm, or `fix` if issues remain.
- `fixed` — *fix* applied review's issues; needs another *review*. Ping-pongs `reviewed ⇄ fixed` until clean.
- `done` — reviewed clean + human-confirmed. A `done` skeleton's children (already sketched) are now unblocked to detail.

At any pre-`done` status a node may additionally be **frozen by a live wait** (`waits.yaml` below) — a mid-step discovery that another open node must define something first. Freezing changes no status: the node keeps its place in the lifecycle, its open cycle record, and simply is not schedulable until the turn returns. A frozen node therefore cannot reach `done`, which is what keeps "every node is done" honest against parked obligations.

A greenfield node is born at `sketch` (the whole tree, mapped by *plan* from the detailed spec); *grow* preserves its `refs` and details it to `draft`. A brownfield node is born at `done` (existing code, mapped by *code-to-tree*) with explicit `refs: []`, because its criterion is code. **`sketch` and `draft` are pre-commitment** — not yet verified, so you edit or delete them *freely* (edit the file, or drop it from `tree.md`): no skill call, no propagation. The tree gate still owns their **source assignment**: changing `refs` after that gate requires a fresh tree verify and seal. **Commitment begins at `approved`** (verify passed): from there a change goes through *revise*, and propagates to consumers if the contract moved. *revise* reopens a `done` node to the earliest status its change touches: `draft` if the spec/contract or `refs` changes (needs re-verify), else `approved` (spec still valid → re-implement → re-review).

**`refs` assignment and legacy resolution.** Its byte shape is strict: `refs:` begins at column 1, followed by one space and either `[]` or unquoted `file@number` tokens separated by comma + one space; tokens contain no `§` or surrounding whitespace and appear in canonical file/numeric-heading order. The field is structurally optional only so existing projects can cross the format boundary without a bulk rewrite. Runtime consumers resolve one authoritative assignment in this order:

1. Field present → use exactly its canonical coordinates; `refs: []` is explicit no-ref.
2. Field absent → derive only an adjacent citation tail shaped `ref/<file> §N` (optionally more coordinates joined by `·`), canonicalize the set, and call this `legacy-citations`. Intervening prose or punctuation ends the tail; a later `§N` on that line is not borrowed by the file mention.
3. Field absent, no citation, `origin: mapped` → legacy mapped no-ref.
4. Field absent, no citation, not mapped → refuse. A model may not guess which source the Task meant.

All non-empty assignments must still be current through `ref/index.md`. Empty source and empty clause roster are different states: `refs: []` has **no assigned source**; `refs: [spec.md@4]` whose logical candidates all begin `(gap)` has assigned scope whose behavior is deliberately undefined. The latter keeps its non-empty scope and source digest even though `clauses` is empty.

**`role` & decomposition** — `role` says whether the node has children:
- `skeleton` — has children (a container/dispatch holding sub-nodes); greenfield, its children are **already sketched** in the tree (from init), detailed one at a time after this node is `done`.
- `feature` — a leaf: terminal behavior, no children.

`role` starts as a hypothesis (from the sketch), is scrutinised at `verify`, and is **confirmed by `implement`** — building the node reconciles its *sketched* children against reality: a sketched child that's now wrong is revised/dropped, a newly-revealed one is added as a sketch. The confirmed **decomposition** is recorded in the node's **Change Log**. Turning a `done` `feature` into a `skeleton` later (it grew to need children) is a *revise*.

**title + lede** — between the frontmatter and `## Overview`, in this order: `# TASK-N · <name>` (one `#`; id and name exactly as the frontmatter spells them — `validate` compares them, so a rename touches both), then one `>` blockquote line, ≤ `read.lede.max` characters, saying what this node is responsible for. The lede is the sentence a reader decides on; it is neither a copy of the Overview's opening nor a restatement of the machine fields.

**body sections** — this order, all `##`:
`Overview` · `Requirements` · `Contract` · `AC` · `Subtasks` · `Change Log`
- `Contract`: states what a consumer can **observe and rely on** (takes·gives·guarantees — public names, boundary shapes, errors, ordering, observable atomicity), never the unobservable inside (algorithms · private structure · how a transaction is done); may carry **deferral markers** `[→ child/deferred: <what>]` for detail intentionally left to a child or to implement — correct delegation, not a gap (verify treats a marked deferral as resolved; markers seed grow). **A deferral points down only** — this node's own child or its own implement. A marker naming a node that is not this node's child is a sideways IOU nothing re-reads: `validate` flags it (a problem at `sketch`/`draft`, where the text is free to edit; a notice once the spec is sealed — demanding that edit would demand breaking the seal); the tool for that dependency is a **wait** (`waits.yaml` below).
- `AC`·`Subtasks`: `- [ ]` / `- [x]` checkboxes. An AC item prefixed **`(gap)`** marks behavior *deliberately left undefined* (the spec/code is silent there): *verify* probes it (resolved into behavior, or adjudicated `accepted-gap` — then the item stays, and the Change-Log adjudication stops re-litigation); *implement* builds nothing for it; *review* excludes it from the every-AC-has-a-test mapping. A later *revise* turns a gap into behavior.
- `Change Log`: `- YYYY-MM-DD — text` (ISO date). `text` = **what changed and why, in one plain sentence** a newcomer can follow — not a transcript of the review. One line per entry, ≤ `read.item.max` characters, no continuation lines and no round-by-round codes: the cycle's own account of itself already exists under `paths.review`, and this is the section a person actually opens the file for. Written at every step that touches the node (`verify` approve · `implement` decomposition · `review` done · each `revise`), so it is the running record a person reads to understand why the node is the way it is: the prose rule above applies to it as much as to the Contract.

## tree.md
2-space indented list. Items are `id` only. Indent depth = tree depth.
```
- TASK-1
  - TASK-2
```
The single source of truth for parent-child structure. (Task files don't record their parent.)
**It holds every node that has a task file** — greenfield, that's the whole tree from init (the `sketch` nodes too); a node's id and its task file appear together. (implement may drop or add a sketched child when it reconciles the decomposition against the build, so the tree still reflects the present.) `grovespec validate` requires every id here to have a task file and vice-versa.

## brief.md
frontmatter `name`. Sections (`##`, fixed): `Direction` · `Scope` · `Risks`.

## conventions.md
Sections (`##`, fixed): `Glossary` · `Common Rules`.

## ref/ — the intent-record series
ref/ holds **frozen intent records** — plan #0's detailed spec, then one *dated* record per later planning pass (its new wants, deltas, and the confirmed disposition table). **Never edit an existing record**: a later record states *deltas only*, each naming what it supersedes ("this section replaces spec.md §4.1's X"). A wrong intent is a new record, not an edit — the series is the history of intent (the brief stays the current summary; Change Logs hold each node's history).

## ref-index.md
Exactly one visible table. Fixed columns: `Topic | File | Location`. Tables inside HTML comments or Markdown fences are examples, not authority; two visible exact tables are ambiguous and fail closed. **The living catalog over the frozen series**: when a later record supersedes a section, the *index row* moves to the current record — records never change, the index does. Task `refs` assigns exact headings from that catalog to nodes; grow reads the assignment and verify makes the runtime prove each non-empty coordinate is still at/below one unambiguous current row. A clearly prose-like legacy Location is ignored by the numeric protocol; a Location beginning with a digit or `§` but not canonical fails closed instead of disappearing.

## Source-evidence packet (spec verify)
`grovespec source TASK-N [spec.md@4 ...]` is the read-only bridge from a Task-owned source assignment to a cold spec gate. Normally pass **only the target**: the runtime derives scope from Task `refs` (or the bounded legacy rule above). Optional coordinates are an assertion for scripts/migration and must exactly equal the derived canonical scope; they never override it. Each coordinate names a file **under the configured `paths.ref` only** plus a literal numbered Markdown heading: `@4` resolves `## 4 ...`; `@5.4` resolves `### 5.4 ...`. A catalog row may point at a containing number (`§5` makes `§5.4` current, but never `§50`); the longest dot-boundary match is authoritative. Absolute paths, `.`/`..` segments, symlink escapes, missing/duplicate headings, duplicate or overlapping coordinates, duplicate catalog coordinates, and a coordinate outside that current catalog ancestry are refused. On success stdout is exactly one fenced JSON skeleton (no prose):

````markdown
```grovespec-source-evidence/v1
{
  "protocol": "grovespec-source-evidence/v1",
  "schema": 1,
  "target": "TASK-N",
  "spec_digest": "<current sha256>",
  "scope": [{ "file": "spec.md", "location": "§4" }],
  "source_digest": "<canonical roster sha256>",
  "clauses": [{
    "id": "SC-<24 lowercase hex>",
    "source": "spec.md@§4:1",
    "heading": "4 Rules > Empty days",
    "text": "<canonical source clause>",
    "c1": "UNSET", "c1_basis": "UNSET",
    "c3": "UNSET", "c3_basis": "UNSET"
  }]
}
```
````

These are the **exact fields**; missing, duplicate, or unknown fields are a refusal at `pin`. `scope` may be empty only when the resolved assignment is no-ref. For a non-empty coordinate, the selected numbered heading owns everything until the next heading at its depth or above; nested headings remain inside it and each clause carries its canonical heading path (`4 Rules > Empty days`). HTML comments do not become source. Markdown fences cannot create/select/end headings, but their literal body remains source content — a fenced example must not disappear from the digest just because it is not Markdown structure.

Ref text is BOM/CRLF/NFC/whitespace-normalized, split into logical blocks and then sentences. A non-fenced clause beginning `(gap)` is deliberately absent from `clauses`, but it remains a source candidate in `source_digest`. Selecting a heading with **no logical candidates at all** is refused; selecting one whose candidates are **all `(gap)`** is valid and yields `clauses: []` with non-empty `scope`. This is how all-gap remains distinct from explicit no-ref.

Clause identity is `SC-` + the first 24 hex characters of sha256 over `grovespec-source-clause/v2\0<file>\0<§location>\0<1-based included-clause ordinal>\0<canonical heading path>\0<canonical text>`. `source_digest` is sha256 over `grovespec-source-roster/v2\n` + compact JSON of each selected coordinate's canonical selected/nested heading roster and **every** logical candidate (`heading` · `text` · fenced/not · excluded-as-gap/not). It therefore goes stale when heading context, an excluded gap, or fenced source content changes, even if the remaining visible clause text happens to stay the same.

Once completed, `pin` stores `source_evidence_round` and a `source_evidence_digest`: sha256 over `grovespec-source-evidence-seal/v1\n` + compact JSON rebuilt in the displayed top-level/clause order **plus every basis resolved to its current content**. `Contract:n`/`AC:n`/`Change Log:n` bind the current logical block; `finding:id` and `adjudication:n` bind the current normalized item; a source basis binds its `source` + `heading` + `text`. JSON whitespace or key order therefore does not matter, while changing the line behind an unchanged-looking anchor does. `approve` and `validate` re-resolve the same anchors continuously.

The main verify session puts the skeleton in the current find brief and hands that **whole packet** to the cold reviewers. They may fill only the four disposition fields. C1 is `carried|deferred|divergence|excluded|missing`; C3 is `handled|deferred|divergence|excluded|not-edge|missing`. Every filled disposition has a machine-resolved basis: `Contract:<n>` / `AC:<n>` (1-based non-empty logical block inside that Task section), `Change Log:<n>`, `finding:<id>`, `adjudication:<n>`, or — for `not-edge` only — that clause's exact `source`. `carried`/`handled` require Contract or AC; `deferred` additionally requires the resolved line to contain `[→ child/deferred: ...]`; `divergence` requires Change Log; `missing` requires a current finding; `excluded` requires a current adjudication. The compatible C1↔C3 pairs are carried↔handled, deferred↔deferred, divergence↔divergence, excluded↔excluded; `not-edge` accepts any non-missing C1 disposition. A zero-clause no-ref/all-gap packet needs no invented disposition rows; its different scope/digest state remains sealed.

## waits.yaml — the sideways-dependency ledger (optional)

`.grovespec/waits.yaml`, created by the first `grovespec wait` declaration; absent in a project that never declared one. It records **mid-step discoveries that another open node must define something first** — the node freezes (its status stays put, its cycle record stays open) and the turn passes; a deferral marker is never the tool for this (markers point down; the ledger points sideways). Runtime-owned: declare and resolve through `grovespec wait`, never by hand-editing.

One top-level `waits:` block list (block style, `[]`-free; every value one strict-YAML line). Entry fields, all fixed:

| field | value |
|---|---|
| `from` | the node that froze — `TASK-N` |
| `to` | the node it waits on — `TASK-N`, never itself, never a node whose blocked_by/parent chain runs through `from` (that wait could never be served — the arrow is evidence for a revise) |
| `declared` | ISO-8601 UTC (`2026-09-24T05:00:00Z`) — **the turn is ordered by this value** |
| `step` | optional — which step froze (`verify` · `implement`) |
| `need` | what is being waited for, one plain sentence |
| `resolved` | `''` while live; ISO-8601 UTC when closed |
| `answer` | `''` while live; what answered it, written at `wait resolve` |

Scheduling reads the ledger with one rule — **the turn follows the newest declaration**: a node holding a live wait (unresolved, target not `done`) is asleep, *unless* a live wait pointing at it is newer than every live wait it holds — the counter-declaration is the wake signal, so exactly one node of a chain is awake and a mutual wait is a turn-pass, never a deadlock. **Re-declaring a pair that already has a live entry refreshes that entry's `declared` (and `need`) in place** — the woken node's way of yielding back after answering. The ledger therefore holds each pair's **current** state, never its history: superseded clocks and wordings live in the Change Logs and in git, because the ledger rides every freezing step's commit. A wait whose target went `done` stops blocking (the value landed) and is surfaced by `validate` until the waiter resumes and resolves it. A `done` node holding a live wait is a validate problem — that done was earned over an open obligation. `approve` refuses a gate while the node holds a live wait. Both sides of every declaration and resolution are also written as Change-Log sentences by the step that made them — the ledger orders the turn; the Change Logs tell the story. The ledger file rides in the freezing step's own commit, like every other artifact a step writes.

## findings.md / restructuring.md  (brownfield backlog — optional)
Lightweight checklists `code-to-tree` parks while mapping existing code into the all-`done` tree; they hold what's *wrong with* that reality, kept **out** of the tree and **worked off by `grovespec-plan`, one milestone at a time** (a single item may go straight to `grovespec-revise`). **Not** strict frontmatter artifacts — documented here but deliberately **not** in `.grovespec/schema`/`validate` (a checklist-shaped optional backlog; strict validation would be ceremony). Created only when non-empty (absent for greenfield or clean code). Content in `config.language`; a board may read them as draft issues.
- **findings.md** — node-level. `##` sections: `Bugs` · `Duplications` · `Doc ↔ code mismatches`. Each item a `- [ ]` line naming *where* + the resolving step (`grovespec-revise`, or extract via `grovespec-grow`). Template `.grovespec/templates/findings.md`.
- **restructuring.md** — tree-level structural debt. A flat `- [ ]` list, each naming the structural problem + the proposed `grovespec-revise` split·merge·move. Template `.grovespec/templates/restructuring.md`.

## candidates.yaml — the reopen-candidate ledger (optional)
`.grovespec/candidates.yaml`, created by the first `grovespec recheck declare`; absent in a project that never had a contract change with dependents. It records **dependents of a changed contract as candidates, not reopens**: each keeps its `done` and its seals, and when the origin lands back at `done`, ONE recheck step (`grovespec-recheck`) judges reach for the armed set — differently-armed waves, with the machine's grep line as material, never a verdict — and only judged-touched nodes reopen. A settle names its pair: `grovespec recheck close TASK-N [TASK-FROM] <verdict>` or `grovespec recheck open TASK-N [TASK-FROM] draft|approved <verdict>` closes one (node, origin) entry — the judged question is that origin's change, so another origin's entry (armed or waiting) is untouched by it. `open` also reopens the node: a `done` one to the named lane, an `approved` one (an earlier verdict's) widened by a `draft` verdict; a node already mid-cycle only records the verdict, and a refused reopen leaves the entry open. Runtime-owned like `waits.yaml`: declare and settle through `grovespec recheck`, never by hand. Entry fields: `node` · `from` · `need` (why the change could reach it) · `declared` · `closed` (`''` while open) · `verdict` (`untouched — …` / `opened — …`). One live entry per (node, from) pair — a re-declaration refreshes it in place; settled entries are the record, history lives in git and the Change Logs. `validate` reads it to EXPLAIN a done node above an open dependency (the candidate lane's legal state); an open entry whose node moved off `done`, or naming a node that no longer exists, is flagged.

## recheck-N.md  (a reach-check's record — appears with the first armed recheck)
`<paths.review>/recheck-N.md`, written by `grovespec-recheck`: frontmatter `origins:` (the from-nodes judged), body = per candidate the machine reach line, each wave's finding (the shown miss or the reached use — never "looks fine"), and the settle. Markdown on purpose, same reasoning as `retro-N.md` below. Commit `recheck #N: <summary>` carries it with the settled ledger.

## retro-N.md  (the milestone's closing record — appears when the first milestone closes)
`<paths.review>/retro-N.md`, written by `grovespec-retro` when every node is done and TASK- work landed since the last record (`grovespec retro` derives the owed-state and the milestone's numbers). Frontmatter: **`anchor: <commit sha>`** — the HEAD the retro's own commit lands on top of; TASK- work after this anchor is what owes the *next* retro (the retro commit is not TASK-shaped, so a closed retro never owes itself). Body in `config.language`: the measured numbers, the milestone's story in plain sentences, the findings table with dispositions, the lessons a next milestone should read. **Markdown on purpose, not a gate record**: it is prose for a person and vetoes nothing — its must-fix findings live as backlog items in `findings.md`/`restructuring.md` (the surface plan already reads), so `validate`'s yaml record sweep never adopts it.

## Shared worktree state — `<git-common-dir>/grovespec/state.json`
**Not a project artifact.** It lives in the git common directory every worktree of the repository shares (`.git/` in a plain checkout), is never committed, and only the runtime writes it — `grovespec id`, `grovespec claim`, `approve`/`amend` when a node is done, and `approve tree --human` — under the short lock `<git-common-dir>/grovespec/lock/` (a second writer waits a few seconds; a lock still held after that is named by path, never reclaimed). JSON, one object:

| field | value |
|---|---|
| `version` | `1` — a runtime that reads another version refuses the file instead of guessing |
| `ids` | `{ "<project>": N }` — the highest id ever issued for the project at `<project>` (its path below the repository toplevel; `.` at the top). `grovespec id` issues `max(scan, N) + 1` and records it |
| `claims` | one entry per held target: `project` · `node` (`TASK-N`, or `tree` for the tree-wide steps) · `worktree` (the holder's toplevel path) · `branch` (`''` = detached HEAD) · `step` (`''` if none was given) · `since` (ISO-8601 UTC) · and, on a node that reached `done` there, `done: { commit, at }` — a **done mark** instead of a claim |

A claim is live while its worktree is on `git worktree list` and not prunable; a lapsed one counts as released and is dropped at the next claim write. A done mark is not tied to its worktree: it holds for every worktree whose HEAD lacks `commit` while that commit is still reachable from a ref or a worktree, and it is dropped once the commit is reachable from nowhere (abandoned work) or in every live worktree (nothing left to protect), or when a person releases it. Unknown top-level keys survive a write. Deleting the file drops every claim and the floor — safe only once every issued id is committed. `uninstall` leaves it in place (other worktrees may still be using it); it is inert without a runtime.

## config.yaml
Location: `.grovespec/config.yaml`. Keys: `version` (the format version — declared here, top-level, exactly once, in no other file; the whole contract is *The format version* at the top of this document), `language`, `paths` (`brief·tree·conventions·tasks·ref·findings·restructuring·src·tests·review` — only the locations are changeable; the structure is fixed; `findings·restructuring` are brownfield-optional). **Every path is relative, inside the project, and spelled as the filesystem spells it** (case included): absolute · drive-relative (`C:src`) · `..` escaping the project · the project root itself (`.`) are refused, because these paths are compared against git's own output and a spelling git never prints reads as "nothing to report" rather than as an error. `./x/`, `x//`, `a/../x` are accepted (one canonical form). Also: `verify` (`find_streak` · `max_rounds` · `scale` · optional `models` — the spec cold-review) and `review` (`find_streak` · `plan_streak` · `max_rounds` · `scale` · `test` command · optional `models` — the code diff-review). `find_streak` = how many consecutive no-new-must-fix waves end the find phase; `plan_streak` = how many consecutive clean cold reviews a fix plan needs before it is applied. `models` (optional, either block) maps a lens name — or `default` — to a host-accepted model id; **omit it and every reviewer inherits the session model** (the portable default). A configured id the host cannot select is an explicit stop, never a silent fallback to another model.

## Commits (the node diff boundary)

**A step does not commit an artifact that reads badly.** Before the commit, run `grovespec validate` and clear whatever it says under *hard to read rendered* about the files this step wrote — that check is the rendered-readability contract above, measured. It is cheapest here, while the step still has in mind what it was trying to say; a wall of text ships once and is then re-read by every person and every cold round after.

**Every step and every decision turn ends by committing what it wrote — whatever the outcome, whatever the target.** A pass, an **escalate stop** (`<step> TASK-N: escalated — …` · tree: `verify tree: escalated — …`) and a decision all commit the same way; a node and the tree alike. The step is not finished while its output sits only in the working tree, and an escalated record is exactly what the human ruling will read. The table names the shapes; the skills' enumerations are examples, never fences:

| step | commit subject | why this shape |
|---|---|---|
| `implement` · `fix` | **`TASK-N: <step> — <summary>`** | the `TASK-N: ` prefix is the **cycle-diff anchor**: these are the commits `diff` collects |
| `grow` · `verify` · `review` · `revise` · `amend` · `plan` · `recheck` · `retro` · `init` — the gate flip, an escalate stop, any non-cycle step | **`<step> TASK-N: <summary>`** (`grow TASK-3: …`, `verify TASK-3: …`, `revise TASK-3: …`, `amend TASK-3: …`; tree gate: `verify tree: …`; no node: `plan #N: …` · `recheck #N: …` · `retro #N: …` · `init: …`) | the step name comes *first* precisely so it does **not** match `^TASK-N: ` — a spec-cycle commit inside the code cycle's anchor drags spec edits into the diff a cold round reads |
| a **decision turn** — `approve [--human]` · `ratify` (the gate skill runs `approve` right after its gate commit; `next` runs it only for a record left sealed and untaken) | **`approve TASK-N: <summary>`** · `approve tree: …` · `ratify TASK-2 TASK-5: …` (one commit may name every id the run stamped) | approve writes the Task status *and* the record, ratify the record, both *after* any gate commit — those bytes need an owner too, in the same non-anchor shape |

A step's commit carries **everything that step produced** — the enumerations in the skills are examples, not fences: anything else the step wrote goes in the same commit. For a gate that means its record under `paths.review`: the yaml plus **every round file of this cycle not yet in git** (brief/plan/confirm files, the test log — a verify cycle has no fix commits, so the gate commit is the only ride those files get). A gate whose evidence never enters git is a verdict whose subject is one clean-up away from gone. `validate` notices an untracked **passed** record yaml on every run; an escalated record and the round files ride on this rule alone — nothing warns about them. (Measured: two records passed their gates and stayed untracked for the rest of a run, because `git add src tests` was the habit.)

A node's **cycle diff** — what *review* reads — is everything since the parent of the cycle's first `TASK-N:` commit, plus uncommitted changes, limited to the node's files. A cycle starts when the node leaves `approved`; a *revise* reopening starts a new cycle. (*implement* starts from a clean working tree, so nothing unrelated blurs the boundary.) `grovespec diff TASK-N` is the one mechanical derivation of this — skills read the cycle from it, never assemble it by hand.

**The gate records are held out of that diff.** A *fix* commit rightly carries the round record it just updated — so `diff` excludes everything under `paths.review` (counted in the output, never named — a filename alone tells a cold reader which record to go open). That is why `paths.review` may not overlap any other configured path: everything in its region is held, so an overlap would hide real code under a held-out count. `validate` refuses such a config. Otherwise the next **cold** round opens the diff and reads the previous rounds' verdicts, reasons and dropped findings, and the blankness the method rests on is gone before it reads a line of code. Commit discipline cannot close this one: the record belongs in that commit; the diff is what must exclude it.

## review-cycle state (verify & review)
*verify* (spec) and *review* (code) each run the cold-reviewer cycle and keep state at `paths.review` (default `.grovespec/review/`). Because both act on the **same** node id at different stages, they write **separate** files so they never collide:
- `tree.verify.yaml` — a whole-tree cycle (`target_type: tree`): `tree_evidence_mode: decomposition` for a greenfield or changed structure/source assignment, `fidelity` for the initial brownfield survey. The mode is written when the cycle starts, before round 1.
- `<id>.verify.yaml` — the spec-verification cycle (`target_type: spec`).
- `<id>.review.yaml` — the code-review cycle (`target_type: result`, diff-scoped).

Fields (all): `target`, `target_type` (`tree|spec|result`), `level` (`skip|light|standard|full`), `find_streak` (N — consecutive no-new-must-fix waves that end find), `plan_streak` (M — consecutive clean plan reviews before a fix is applied), `max_rounds`, `round` (total spawned passes), `no_new_streak` (the live find counter — reset by a new must-fix, held by an unresolved candidate), `phase` (`find|fix` — find waves over a frozen target, each wave's finds classified at its boundary → per-item fix: plan → plan review → apply → confirm; `reviewers.md` §The cycle), `current_item` + `item_phase` (`plan|confirm`) + `plan_clear_streak` (the fix phase's live position — a resumed session continues the same item at the same step; an edited plan resets its counter), `status` (`in-progress|passed|escalated` — **`escalated` means one thing: the cycle spent `max_rounds` without closing, so a human must rule.** Confirmed must-fix items inside the budget are `in-progress`/`reviewed` + `open_issues`, which is ordinary progress into the fix step; `validate` refuses `escalated` at a round inside `max_rounds`, because that word stops an auto loop over work the machine could have done — and reaching `max_rounds` is never a pass), `approved_by` (`pending|human|machine`), Task gate seal `task_evidence_digest`, spec seal fields `spec_digest` + optional legacy-compatible pair `source_evidence_digest`/`source_evidence_round`, tree seal fields `tree_digest` + optional legacy-compatible `source_scope_digest` + paired `tree_evidence_mode`/`tree_evidence_digest`, `reviewed_commit`, `strategies[]` (which waves ran which search strategy), `found[]` (raw finds, classified at each wave boundary), `checks[]` (verify/tree: the C#/D#/F# table with shown evidence + basis — what a resumed session reads find's progress from), `rounds[]` (per-pass outcome: `n` · `outcome` required, `phase` · `found` · `item` · a **one-line** `note` optional — the pass's reasoning lives in its own round file (`<id>.round<n>.brief.md` · `.plan.md` · `.confirm.md`; the result gate's as `<id>.review.round<n>.*`, so a review round never overwrites the brief a spec seal pinned) and the note points at it. An entry is **flat**: every field on one line at the entry's own indent, `found` written as a one-line flow map. `validate` reads depth, so a block scalar, a plain multi-line scalar and a nested mapping are each refused, as is any field the schema doesn't list). **Every list in this record is block style** — one **indented** `- ` item per line (an item fallen to column 0 ends the list for every reader here — it and the items below vanish from every per-item check, so a settled adjudication can re-fire — and a YAML mapping refuses a top-level sequence entry); a flow list (`followups: [ {...} ]`) is refused, because these records are read line by line and flow style switched every per-item check off silently rather than failing it (`[]` for an empty list is fine), `open_issues[]`, `followups[]`, `adjudications[]`, plus the seal fields below. Template: `.grovespec/templates/review-state.yaml`. **A quoted value is one line of strict YAML.** The free-text fields (`what` · `reason` · `note` · `shown` · …) quote documents and cite Windows paths, and grovespec's own readers strip a surrounding quote pair without interpreting escapes — so a malformed scalar fails nothing here and fails only the outside consumer reading the record as real YAML (measured: 6 of one project's 39 records unreadable to js-yaml). So: inside `"…"` a literal backslash is `\\` and a literal quote `\"`; inside `'…'` a literal quote is doubled (`''`) — single quotes are the friendlier style for prose citing `%LOCALAPPDATA%\...` paths, since they escape nothing else; a value needing neither stays plain. A block scalar (`|`) is **not** the alternative: these records are read line by line, and a scalar's indented body is exactly the depth the flat-entry rule refuses — the text would silently vanish from every per-item check instead of failing one. `validate` sweeps each record's single-line YAML shapes and names every spot strict YAML cannot read — or grovespec's own line readers cannot see (a column-0 or mis-parented list item, a block scalar's hidden body, a tab indent, an unclosed flow value, a plain value YAML reads as syntax: a leading `*`/`&`/`!`, a `: ` inside) — as a **notice, never a problem** (decided cycles' records are already written; the line reprints every run until the spot is repaired). **Every Task frontmatter key and review-state top-level key appears once**; `validate` reports duplicates and every other project command refuses before routing, rather than choosing whichever duplicate a particular parser happens to prefer. **A record is evidence only for the node its filename names** — `validate` requires filename ↔ `target` ↔ `target_type` to agree, and flags an orphan record (no such task).

**The gate binding model.** A gate's verdict must say *who decided it, which bytes it covers, and (for code) which run proved it* — and each binding is written **at the moment it becomes true**, by the runtime:

An all-mapped no-ref tree remains code-grounded when either a spec or result record appears. A lifecycle record is not a source assignment: only an actual `refs` coordinate or a non-mapped node activates catalog ownership. The current catalog roster and material are still observed as a tripwire, so newly introduced intent cannot remain invisible behind the no-ref boundary. A Contract revise that brings intent into scope therefore writes the exact `refs` and takes the tree gate; merely entering its ordinary spec cycle does not invalidate the already-approved fidelity seal.

- **Seal — `grovespec pin` at the cycle's pass.** When a cold cycle terminally passes, the gate skill runs `pin TASK-N` (spec: `spec_digest` + `task_evidence_digest` into `<id>.verify.yaml`; result: `reviewed_commit` (HEAD) + both digests into `<id>.review.yaml`) or `pin tree`. `task_evidence_digest` binds the complete Task frontmatter with only lifecycle `status` normalized; `spec_digest` separately binds Overview…AC, while Subtasks and Change Log remain mutable. A tree pin stores `tree_digest` (parsed structure, so indentation/comments don't invalidate approval) and `source_scope_digest`: sha256 over `grovespec-source-scope/v1\n` + compact JSON `{catalog,nodes,sources}`. `nodes` follows canonical tree order and carries each `target`, assignment mode (`explicit` · `legacy-citations` · `legacy-mapped-no-ref`), and canonical scope. `catalog` records every visible numeric current `ref/index.md` row and `sources` binds canonical material at every catalog/assigned coordinate. An all-`origin: mapped`, all-empty-scope fidelity tree marks that catalog observed-only rather than active ownership; spec/result record existence does not change the criterion, while assigning a ref or adding a non-mapped node activates it. The same cycle writes `tree_evidence_mode` (`decomposition|fidelity`) before round 1; pin adds `tree_evidence_digest` over `grovespec-tree-evidence/v1\n` plus the mode-specific reviewer projection. Decomposition binds tree structure + the brief + every full sketch Task; on a built-tree re-verify, each non-sketch Task is bounded to id·name·Overview·`refs`. Fidelity binds structure + every Task's id·name·Overview·Contract + both optional backlogs + src/tests paths, types, executable modes, and bytes. With Git, that code inventory is tracked plus non-ignored untracked files (ignored generated output is outside the reviewers' canonical scope); without Git every filesystem entry is bound. Symlinked code is refused because the followed bytes cannot be bound without a containment policy. For a **new draft verify cycle**, spec `pin` opens exactly the highest `rounds[]` find brief, requires one completed source-evidence packet, and recomputes the Task assignment, current heading/context roster, Task digest, current catalog, exact field roster, C1/C3 compatibility, and resolved basis content before any write. `UNSET`, terminal `missing`, an invalid basis, a C1/C3 conflict, or stale/altered evidence refuses with no write. A result pin additionally requires the reviewed project input to be clean: the project except this gate's Task/review evidence/run lock, plus any path outside a nested project previously touched by a `TASK-N:` commit. **Every completed seal is write-once per cold cycle:** an exact re-pin is read-only; changed or partial evidence requires a fresh cycle. One deliberate pre-seal state is not partial: result `reopen` keeps old `reviewed_commit` only as the next diff base until the fresh terminal pin replaces it. `approved` and `done` never acquire or refresh evidence. Decided historical seals without newer fields stay readable and are never backfilled; still-pending legacy verdicts lack the reviewed-input binding and must run a fresh cycle before approval. The first pin marks `approved_by: pending`. The spec digest has one spelling (`bin/lib/core.mjs specSpanText`): sha256 over `## Overview` … `## AC` (headers included, CRLF-normalized).
- **Decide — `grovespec approve` writes no evidence.** It verifies the seal still covers the *current* input (spec + pending Task frontmatter + any exact source packet; tree structure + source scope + required pending mode-specific evidence; result project input + pending final Task frontmatter at `reviewed_commit`) and only then flips state and stamps `approved_by`: `--human` or machine. `--human` substitutes for machine test evidence, never for binding. `validate` continuously checks source evidence and tree structure/source scope; it recomputes Task and mode-specific tree evidence while that verdict is `pending`. After a decision, fidelity code/backlogs and the brief may legitimately evolve, implement may confirm a different Task `role`, and a tree-only merge may update a done node's `blocked_by`, so those digests remain historical rather than permanent freezes. A pair with one missing field is invalid. Decided historical records without newer fields retain compatibility; pending ones cannot be approved without a fresh gate. For a pending result, HEAD may move only when every changed committed path remains outside the reviewed project-input domain; the same domain must have no dirty bytes. A moved input path, non-canonical/unrelated commit, or dirty input is refused. A **machine result approval additionally requires** `last_test` with `exit: 0` bound the same way. `approve tree` is human-only. All checks run before writes. A process interruption after `passed` but before pin routes back into its gate; an interrupted two-file approval is completed by re-running `approve`.
- **Reopen — `grovespec reopen TASK-N draft|approved` / `grovespec reopen tree decomposition|fidelity`** (revise's transition): gate records restart as fresh cycles, so a past cycle's `passed` can never double as new evidence. A `draft` reopen clears `spec_digest`, `task_evidence_digest`, `source_evidence_digest`, and `source_evidence_round` together, so the new verify cycle must build and seal new evidence. A structure or `refs` change uses the tree form; it preserves `adjudications` and writes the explicit mode before round 1, preventing a built tree from falling into the initial-fidelity heuristic. `reviewed_commit` survives only as the next `diff`'s base, and **`adjudications` survive in the record itself** (a settled call is a boundary, not evidence — before the next round the caller prunes entries whose written reason leaned on the old substrate: the old contract on a `draft` reopen, code that no longer exists on a `result` reopen). Everything else — old rounds, open issues, followups, narrative — lives on in git history.

**`approved_by` states.** `pending` = sealed verdict not yet taken — the gate skill takes a clean one in the same turn it sealed it (`grovespec approve TASK-N`), in every mode, and `next` names that command for one left behind, since a verdict with nothing to decide is not a human wait (what *waits on you* is an escalation, or the tree gate). `machine` = taken on the cold verdict alone — the verification result, kept apart from any person's decision; `status`/`validate` name every such gate until `grovespec ratify <id>…` stamps it `human`. `human` = a person looked (`approve --human` in the session, or `ratify` after). **Absent = legacy** (written before this model): it binds nothing — not shown as awaiting, not approvable; re-run the gate to seal a fresh cycle. The tree gate opens only on `human` (legacy tree records stay open for old projects).

**Evidence outside git.** A record that passed a gate but is not tracked is a verdict whose subject is one clean-up away from gone. `validate` says so as a **notice, never a problem**: a record is born untracked and every gate passes before anything stages it, so blocking there would fail at the moment each gate first succeeds. The line reprints every run until the record is added, the same way an unratified machine gate keeps reprinting.

**Status ↔ evidence.** A Task's `status` is a claim about gates passed, and `validate` checks the claim against these records: `approved`+ requires `<id>.verify.yaml` `passed` and not `pending`; `done` also requires `<id>.review.yaml` `passed` and not `pending`; a `passed` record may not still carry `open_issues`; a machine-approved `done` must show its bound green `last_test`. `origin: mapped` nodes with **no** review files are exempt — brownfield init maps existing code straight to `done`; the rules bind from the first gate a reopened node enters.

**`last_test` + `<id>.test.log`.** `grovespec test TASK-N` runs `config.review.test` and writes the machine record itself: a `last_test:` block in `<id>.review.yaml` (`command` · `exit` · `when` · `commit` — the HEAD it ran on) plus the full output in `<id>.test.log`. "The tests passed" is this record — including *which code* it passed on — not a session's reading of its scrollback.

## The step report (what a skill says to the person)

Every step skill **opens and closes in the same shape**, so the person finds the same information in the same place on every run — a human gate only works if the report feeding it reads the same way the tenth time as the first. The headings are fixed English (like every header in this file); the prose between them is written in `config.language`, **warmly and in full sentences** (in the language's respectful-address register — the writing rules at the top of this file), for the same reader as the setup interview — someone who may not code. The artifact rules at the top of this file cut filler because artifacts are re-read; a report is spoken once to *orient a person*, so here the explanation is the payload — never compress it into a telegram line ("R2 pass, no issues" fails this format even when it's true).

**Written so the reader has never read these docs.** This is the one place GroveSpec asks a person for something, and it is the place its vocabulary leaks hardest — the step has spent its whole run inside check codes, round numbers and lens names, and they come out sounding like words. They are not words to the reader. So:
- **Never a bare code.** `C4`, `R11`, `F-D`, `PASS`, `normal-use-bug` — none of these reach the person alone. Say what was found and what it means for them. The code is available in the record if they ask.
- **A GroveSpec term gets a plain gloss the first time it appears in that message** — "콜드 리뷰(이 코드를 쓰지 않은 검토자가 처음 보는 눈으로 다시 읽는 것)". The term keeps its established form (the naming rule at the top of this file); the gloss is what makes it land. Once glossed, use it plainly for the rest of the message.
- **The gate question is asked in the person's terms, about their thing** — what it now does, what it will not do, what they are agreeing to. "Is this the right decomposition?" is the *skill's* question; the person's is "이 구조로 지으면 원하시는 게 나오는지".
- The test: read your closing aloud to someone who has never heard of GroveSpec. Every sentence they would stop on is a sentence to rewrite.

**A decision, not a stage — what may stop for the person.** A step stops for the person only where a decision is genuinely theirs: **an ambiguous requirement** (the source or the person left it open — a name, a policy, a constraint, a question with no defensible default), **a product behavior or scope choice** (a `(gap)` ruling, a planning disposition, the decomposition), or **accepting an unmet or unverifiable requirement** (a requirement the only fix would narrow or drop, a measurable target nothing can check). A gate that came out clean within the agreed requirements is **not** one: its verdict is recorded (`approved_by: machine` — the cold verdict, never the person's approval) and the flow goes on. Every ask has four parts — **the issue** (what is undecided, in one line) · **the options** · **each option's impact** · **the recommended one** with its one-line why — and always allows a free-form answer. **The four parts go in the message, not in the question tool**: when the ask goes through a host's question tool mid-turn (`AskUserQuestion` · `request_user_input_async`) rather than the closing *Your turn*, write all four in the message body before calling it, and give the tool only the question and short option labels — hosts show the tool's other fields unevenly (an option's `preview` or description may never appear), and nothing the whole decision rests on (the list being approved, the delta) goes in one option's field. **No issue, no ask**: "shall I record this as done?" over nothing to decide is a stage approval, and a stage approval is the rubber stamp this format exists to prevent. The verdicts (the gate records) and the person's decisions (`adjudications`, Change-Log lines, `ratify`) are kept apart — one never stands in for the other.

Fails this format, though every word is true — a *Result* reading `R2에서 C4가 PARTIAL로 남았고 normal-use-bug 하나가 open_issues에 있습니다.` Passes — `두 번째 검토에서 한 가지가 걸렸습니다. 목표를 세운 당일의 달성 여부를 세는 규칙이 스펙과 코드에서 서로 다르게 읽혀서, 지금 상태로는 스트릭 숫자가 하루 어긋날 수 있습니다.`

**Markdown headings, not label lines.** The anchor is a `##` heading and each slot a `###` heading with its prose underneath — never `Result: …` run on as a label line, which buries the slots in one block of text. Inside a slot, a list or a short table is fine where it reads better than a paragraph (the items of a decision, the nodes that changed).

**Opening** — the first message when the skill starts:
```
## [grovespec <skill> <target>] starting

<what this step is for · what it is about to do on this target · what the person will have when it ends>
```
The paragraph is short (2–4 sentences) and in plain words — even if the person has seen it ten times.

**Closing** — the last message of the run: the anchor heading, then all four slot headings, this order, no slot ever dropped (an empty slot is information — write the sentence that says so):
```
## [grovespec <skill> <target>] done — <the outcome in half a line>

### Result
<what actually happened, with its evidence — rounds, tests, counts, decisions taken.>

### Open
<what this step leaves unresolved — open issues, parked findings, accepted gaps, unverified targets. "Nothing open" is a claim: say it only checked.>

### Your turn
<what now waits on the person — a decision in the four-part shape above (the issue · the options · each one's impact · the recommended one), or the sentence that nothing does and what that means for the flow (a clean gate is recorded and passed through; a look of their own is `ratify`). A file path or command comes after the substance, never instead of it.>

### Next
<the next step and where to run it — including the new-session recommendation when the workflow calls for one.>
```
A run that ends without reaching its normal end (escalated · blocked · refused) closes the same way with **`stopped — <why>`** instead of `done`. The structure is what's fixed; the content must be **this run's facts** — every sentence checkable against what just happened, no stock reassurance.

Filled, it reads like this (prose in the project's language):
```
## [grovespec review TASK-3] done — the aggregation code is written, reviewed and clean; 14 of 14 tests pass

### Result
TASK-3 is the part that adds your records up per day and decides whether a goal was met. It is now built and all 14 of its tests pass. Reviewers who had not seen it being written read it twice over, raised nine concerns, and three of those turned out to be real: a record crossing midnight was counted on the wrong day, a goal set today reported a streak of one, and an empty day returned nothing instead of zero minutes. All three are fixed, and a fresh reading of just those fixes found nothing new.

### Open
Nothing is left open here — the three are closed and the other six were ruled out with reasons, which are kept with the review so they do not come back round after round.

### Your turn
Nothing here needs a decision from you: the three problems were real and are fixed, and nothing the reviewers raised asks you to choose between behaviors or to accept a gap. So the gate is recorded as passed by the review — not as approved by you — and the build moves on; if you want to look it over yourself, say so and I will record that you did.

### Next
TASK-4 — the weekly report screen — is the next one to spec out, and the loop goes there on its own. Best started in a fresh session, so the reviewers come to it without having watched it being written.
```
